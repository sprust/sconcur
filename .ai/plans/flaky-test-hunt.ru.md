# Неуловимый флаки-тест в полном сьюте

Статус: **закрыто** по обоим серверным случаям — ws 2026-07-24, см.
[«Развязка»](#развязка-2026-07-24); socket на Rust-ядре 2026-09-03, см.
[«Сокет-аналог на Rust-ядре»](#сокет-аналог-на-rust-ядре-2026-09-03).
Наблюдение велось с 2026-07-04 (ветка `feature/optimization`).

Третий случай, другой природы, — AMQP, 2026-09-04, — **закрыт правкой теста** в
тот же день, см. [«AMQP: код закрытия канала»](#amqp-код-закрытия-канала-2026-09-04).
К drain он отношения не имеет.

## Развязка (2026-07-24)

- **Тест**: `WsServerMaxConnectionsTest::testServerExitsAfterReachingMaxConnections` —
  падал на втором `pong` (`assertSame('pong', null)`), пойман в первом прогоне после
  тяжёлой wrk-сессии (профиль «первый прогон после встряски» подтвердился).
- **Причина**: гонка «drain против первого сообщения» у лимитирующего соединения.
  При достижении `maxConnections` serve-цикл (`src/Scheduler/Scheduler.php:319`)
  начинает drain на следующей итерации после диспатча лимитирующего соединения —
  его drain-канал закрывается, пока `ping` клиента ещё в пути. `messageState.Next()`
  брал ветку drain → EOF, хендлер завершался без `pong`. Это второе окно той же
  гонки: первое («сообщение уже в буфере, select выбрал drain») чинилось в `f117bcb`.
- **Воспроизведение**: 2 фейла на 40 прогонов одиночного теста при 8 busy-циклах
  на хосте; сокет-аналог (`SocketServerMaxConnectionsTest`) чист — 0/40.
- **Фикс** (расширение 0.7.1): `ext-go-legacy/internal/features/wsserver/message_state.go` —
  соединение, ещё не доставившее хендлеру ни одного сообщения
  (`deliveredCount == 0`), при drain получает ограниченное окно
  (`firstMessageDrainGrace` = 250 мс) на первое сообщение и только потом EOF;
  после первой доставки EOF мгновенный, как раньше. Юнит-тесты — в
  `message_state_test.go`.
- **Верификация**: 0 фейлов на 60 прогонов под той же нагрузкой (до фикса — 2/40).

Гипотеза 1 (тайминг-чувствительный серверный тест) подтвердилась в связке с
гипотезой 2: буферизация results-канала сама по себе ни при чём, но окно гонки
живёт именно вокруг drain при остановке серверного flow.

## Сокет-аналог на Rust-ядре (2026-09-03)

Ветка `spike/rust-core`, расширение 0.12.0.

**Наблюдение.** `SocketServerMaxConnectionsTest::testServerExitsAfterReachingMaxConnections`
упал с `Failed asserting that null is identical to 'pong'`
(`tests/feature/Features/SocketServer/SocketServerMaxConnectionsTest.php:35`) —
это **второй** roundtrip, то есть лимитирующее соединение. Подпись совпадает с
закрытым ws-случаем дословно.

Условия — ровно профиль «первый прогон после встряски»: первый `make test` сразу
после `make ext-build`. Изолированно тест чист (**0/25**), два полных прогона
следом зелёные.

**Почему это не просто повтор закрытого случая.** Тот был про ws, а сокет-аналог
раздел «Развязка» прямо записал как чистый (0/40). И фикс тогда лёг в прежнее ядро.
Разбор обоих ядер:

| | окно на первое сообщение при drain |
| --- | --- |
| прежнее ядро, ws | есть, окно на первое сообщение 250 мс |
| Rust ws (`ext/src/ws/message_state.rs`) | есть, `FIRST_MESSAGE_DRAIN_GRACE` + `biased` select + `try_recv` вперёд |
| прежнее ядро, socket | нет, и не нужно: drain там полузакрывал сокет |
| Rust socket (`ext/src/socket/message_state.rs`) | **нет, и механизм другой** |

Ключевое различие в последней строке. Прежнее ядро при drain полузакрывало соединение на
чтение (`ext-go-legacy/internal/socket/connection.go:45`), а `read()` обязан
сначала отдать байты, уже лежащие в буфере, и только потом вернуть EOF — кадр «в
полёте» потеряться не может. Rust вместо этого гасит `CancellationToken` и делает

```rust
tokio::select! {
    _ = self.read_stopped.cancelled() => return self.finished(),
    outcome = read => outcome,
}
```

`tokio::select!` без `biased` выбирает среди готовых веток **случайно**, и ветка
отмены может выиграть у чтения, которое вот-вот вернуло бы кадр. То есть у
сокет-порта окно той же гонки шире, чем было у оригинала, — а не уже.

**Воспроизведение.** Спокойного прогона не хватало (0/25), но под той же
нагрузкой, которой ловили ws — восемь busy-циклов на хосте, — гонка вышла:
**1 фейл на 40** прогонов одиночного теста, та же подпись и та же строка
(`SocketServerMaxConnectionsTest.php:35`). Гипотеза подтвердилась.

**Фикс** (`ext/src/socket/message_state.rs`, расширение 0.12.0, версия не
поднималась — протокол не менялся). Две части, обе нужны:

1. `biased` select, чтение первым. Кадр, который уже готов, выигрывает у сигнала
   drain, а не разыгрывается с ним в орлянку. Плюс `tokio::pin!` на футуре
   чтения: ветка drain дожидается **той же** футуры, а не бросает её вместе с
   тем, что она уже сняла с сокета.
2. Ограниченное окно на **первый** кадр, если drain пришёл, пока вызов стоял
   припаркованным: соединение, которое уже что-то отдало, завершается сразу, а
   то, которое не отдало ничего, получает `FIRST_FRAME_DRAIN_GRACE` = 250 мс —
   его запрос может быть ещё в пути. Одного `biased` мало: в момент drain чтение
   честно `Pending`, байты не пришли, и без окна отмена выигрывает законно.

Окно **только серверное**. Клиент получает `Duration::ZERO`: у него тот же токен
означает «соединение кончилось», а не «сервер перестал принимать новое», и держать
поток лишнюю четверть секунды после этого — регрессия, а не починка.

Заодно исправлен докблок `PendingConnection::close_read()` (`ext/src/socket/mod.rs`),
который утверждал, что отмена футуры чтения заканчивает цикл хендлера «тем же
способом», что полузакрытие в расширение. Не тем же — в этом и была вся разница.

**Верификация**: **0 фейлов на 70** прогонов под той же нагрузкой (до фикса —
1/40). Полный сьют зелёный, 730 тестов.

**Что осталось замеченным.** У прежнего ядра эта гонка была покрыта юнит-тестом
(`ext-go-legacy/internal/features/wsserver/message_state_test.go`), а в
Rust-ядре юнит-тестов нет вовсе — ни одного `#[test]` во всём `ext/src`.
Поэтому проверять пришлось сьютом под нагрузкой, то есть статистикой, а не
детерминированно.

## Симптом

`make test` (416 тестов) изредка падает ровно с одним фейлом:

- зелёный прогон: `Tests: 416, Assertions: 22511, Incomplete: 1`;
- флаки-прогон: `Tests: 416, Assertions: 22509, Failures: 1, Incomplete: 1` —
  на 2 assertion'а меньше, то есть тест падает до последних проверок.

Имя теста поймать не удалось: в testdox-хвосте вывода маркер не попался, а все
повторные прогоны (в том числе с `--stop-on-failure`) — зелёные.

## Хронология наблюдений (2026-07-04)

Всего ~20 полных прогонов за день, 3 фейла:

1. Первый фейл — первый `make test` сразу после `make ext-build` с буферизацией
   results-канала (коммит `78a9d06`) и заменой `uniqid` на счётчик. Немедленный
   повтор и ещё 2 прогона — зелёные.
2. Второй фейл — прогон вскоре после остановки/подъёма контейнера `sc-mysql`
   (проверка 500-логики `/all`, коммит `6f91811`) и убийства тестовых серверов
   в контейнере. Повтор — зелёный, затем 3 прогона подряд с
   `--stop-on-failure` — зелёные.
3. Третий фейл — первый `make test` сразу после полной серии wrk-бенчей
   (12 серверных процессов + wrk, машина под полной нагрузкой за минуты до
   прогона). Следом 5 прогонов подряд с `--log-junit` — зелёные.

Общее у всех случаев: фейл случается только в первом прогоне после «встряски»
окружения (пересборка расширения / рестарт бэкенд-контейнера / тяжёлая
нагрузка на хост), второй и дальнейшие прогоны — зелёные. На «спокойной»
машине не воспроизводится. Это усиливает гипотезу 1 (тайминг-чувствительный
тест) против гипотезы 2.

С 2026-07-04 `make test` всегда пишет `--log-junit /tmp/sconcur-phpunit.xml`
(внутри контейнера `php`) — при следующем фейле имя теста будет в отчёте:
`grep -B1 '<failure' /tmp/sconcur-phpunit.xml`.

## Контекст ветки (что менялось незадолго до появления)

- `0ff717f` — suspend-first dispatch (границу ушёл со стеков фиберов), дефолт
  `maxConcurrency = 0`. После этого коммита прогоны были зелёные (3 подряд).
- `78a9d06` — буферизация общего канала результатов (1024) + дроп «протухших»
  результатов остановленных flow + чистка `pending` в `StopFlow`;
  `callbackKey` через счётчик. Первый фейл замечен в первом прогоне после
  этого коммита.

## Гипотезы (не проверены)

1. Тайминг-чувствительный серверный тест (shutdown/drain/timeout), которому
   стало «теснее» из-за фоновой нагрузки на хост — флаки был и мог быть до
   ветки, просто не попадался.
2. Следствие буферизации канала: изменившиеся тайминги доставки (результат
   лежит в буфере, а не в rendezvous) могли вскрыть гонку в каком-то тесте
   вокруг остановки flow. Если где-то «протухший» результат доезжает до PHP,
   это дало бы `FiberStateException: No coroutine for result` — в пойманных
   хвостах вывода такого не видно, но хвосты неполные.
3. Внешний фактор: бэкенд (mysql после рестарта, прогрев пула) отвечает
   ошибкой/медленно в одном тесте.

## AMQP: код закрытия канала (2026-09-04)

Ветка `spike/rust-core`, расширение 0.12.0.

**Наблюдение.** `AmqpFailureTest::testAChannelReportsWhatClosedIt` упал с
`Failed asserting that 0 is identical to 404`
(`tests/feature/Features/Amqp/AmqpFailureTest.php:231`) — один раз в полном
прогоне. Отчёт лежит в `.phpunit-failed/sconcur-phpunit-20260904-065010.xml`.

**Что тест хочет.** Публикация в несуществующий exchange заставляет брокера
закрыть канал с 404; `waitForConfirms` должен вернуть *причину*, а не «канал
закрыт».

**Где на самом деле теряется причина** (первый разбор был неверен — причину есть
кому спросить). `ChannelEntry::close_reason` существует ровно для этого, а
записывает его `collect_confirmation`: когда lapin рушит pending confirm ошибкой,
он сперва зовёт `note_protocol_failure`, и только потом закрывает канал — порядок
намеренный.

Дыра внутри lapin. Закрытие канала брокером идёт там двумя стадиями:
`set_closing(Some(ProtocolError))` — вот эта ошибка несёт 404 — и после
`channel.close-ok` вторая, `set_closed(InvalidChannelState)`, которая не несёт
ничего. Обе рушат pending confirms. Confirm, зарегистрированный до первой стадии,
получает 404; проскочивший между стадиями получает обезличенную вторую,
`protocol_failure()` её не распознаёт, и `close_reason` остаётся пустым.

**Чинить предложено НЕ в ядре.** Убрать гонку полностью можно только слушателем
закрытия на канал — а от него отказались осознанно (см. докблок
`note_protocol_failure`: lapin отдаёт закрытие как ошибку команды, «which is
earlier and needs no listener»). Слушатель — задача на канал, а каналов много:
`PublishChannelPool` растит их до 255 на соединение. Публичного API спросить
причину постфактум у lapin нет — `ChannelStatus` отдаёт только булевы состояния.

Так что размен упирается в один вопрос: насколько 404 важен пользователю
библиотеки. Publish в несуществующий exchange — ошибка конфигурации, и «канал
закрыт» вместо «404 exchange not found» стоит человеку времени. Если это
существенно — слушатель окупается; если нет — поведение верное в большинстве
случаев, а тест требует от него гарантии, которой у него нет, и правится тест.

**Воспроизводимость.** Изолированно 0 фейлов на 12 прогонов. Живёт только в
полном сьюте, где рядом идут остальные AMQP-тесты; повторный полный прогон
зелёный. Ни одна правка этой сессии AMQP-путь публикации не трогала: удаление
`timeout_ms` (7eb5ea8) касается disconnect и usedChannels.

**Развязка (2026-09-04).** Размен решён в пользу теста: ядро не трогали,
слушателя закрытия на канал не появилось. `testAChannelReportsWhatClosedIt`
делает до пяти попыток на свежих каналах и требует 404 от одной из них, а от
каждой — только того, что вызов отбит как закрытый канал. Гарантия, которую тест
держит, стала точной: причина доезжает, но не обязательно в каждой отдельной
гонке.

Почему так, а не слушателем: окно шириной в микросекунды, цена закрытия —
задача на канал при пуле, растущем до 255 каналов на соединение, а цена
проигранной гонки — текст ошибки («No channel available.» вместо «404 ... no
exchange») в редкой ошибке конфигурации. Ни потери данных, ни зависания, ни
утёкшего канала: канал выселяется в обоих случаях.

Проверено: 3 прогона AMQP-директории (159 тестов) подряд зелёные.

## Как ловить (план охоты)

1. Логировать имя упавшего теста персистентно: гонять сьют в цикле с
   `--log-junit /tmp/junit-$i.xml` (или `--log-events-text`), пока не поймается:

   ```bash
   i=0; while :; do i=$((i+1)); \
     docker compose exec -T php php -d extension=./ext/build/sconcur.so \
       vendor/bin/phpunit -d memory_limit=512M --colors=never \
       --log-junit /tmp/junit-$i.xml tests || break; done
   ```

2. Воспроизводить условия появления: прогон сразу после `make ext-build` /
   рестарта бэкенд-контейнера, при фоновой нагрузке на хост.
3. `--order-by=random` (с фиксацией seed при поимке) — расшатать
   меж-тестовые зависимости.
4. При поимке: если это `FiberStateException`/`UnexpectedTaskKeyException` —
   копать связку «буферизованный канал × StopFlow» (гипотеза 2); если таймаут
   серверного теста — гипотеза 1, поднять допуск в тесте.

## Критерий закрытия

Имя теста установлено, причина воспроизведена или опровергнута; либо 50+
полных прогонов подряд без фейла на спокойной машине (тогда закрыть как
внешний шум с пометкой здесь).
