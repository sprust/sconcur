# Фича Std: стандартные функции PHP с выполнением в Go

`Std::*` реализует SConcur-эквиваленты стандартных функций PHP, чьи нативные вызовы
либо блокируют процесс (sleep, файловый I/O), либо являются CPU-bound монолитными
внутренними вызовами, которые не может прервать даже автоматическая преемпция
(`json_decode` огромного блоба, `hash()` большой строки, `password_hash()` — см.
[docs/coroutine-switching.ru.md](../../docs/coroutine-switching.ru.md), «О чём
стоит помнить»). Вызов уезжает в Go-горутину: PHP-поток свободен, соседние
корутины продолжают работать, и — в отличие от `Scheduler::switch()` — работа идёт
на других ядрах CPU параллельно.

Решения владельца (зафиксированы): v1 включает файловые операции; вывод
`jsonEncode` — эквивалентный JSON, не байт-в-байт с `json_encode` (принято);
`Sleeper` удаляется жёстко, без deprecated-фасада; этот план ложится в
`feature/courutine-switcher`, сама фича делается на своей ветке со своим минорным
бампом версии.

## Цель и не-цели

- Цель: ни один вызов стандартной функции не замораживает воркер. Блокирующие вызовы
  (sleep, файловый I/O) подвешивают только свою корутину; CPU-монолиты (json, hash,
  gzip, хеширование паролей) целиком покидают PHP-поток. Единый API для sync и
  async, как у каждой фичи.
- Цель: настоящий параллелизм для CPU-работы. Фан-аут из N хешей использует N
  горутин на разных ядрах, пока PHP-поток обслуживает другие запросы.
- Не-цель: байт-идентичный вывод там, где замешано PHP-специфичное форматирование
  (см. «Семантические допуски»).
- Не-цель: замена быстрых функций. `base64_*`, `str_*` и им подобные дешевле
  границы; они остаются нативными.

## Целесообразность и оговорки

Честный разбор, когда фича оправдана, а когда — нет. Каждый пункт ниже влияет на
состав v1 и формулировки в доке.

### Цена границы PHP↔Go

- Каждый вызов — это msgpack-конверт, cgo-переход и минимум две копии памяти в
  каждую сторону (PHP-строка → C-буфер → Go-строка и обратно). Для мегабайтных
  payload это единицы-десятки миллисекунд чистого копирования и двойной пик памяти
  (данные одновременно живут в PHP и в Go).
- Синхронный путь всегда медленнее нативного вызова — граница прибавляется к той же
  работе. Позиционирование фичи: код в корутинах и серверных обработчиках; вне
  корутин нативные функции остаются правильным выбором (кроме sleep, где семантика
  та же).
- На маленьких payload (порог уточнят бенчмарки, ориентир — меньше десятков КБ)
  граница дороже самой работы: выигрыша нет даже в async. Это не повод резать
  команды, но повод честно писать пороги в доке.

### json: выигрыш частичный по построению

- Для `jsonEncode` PHP-значение сначала пакуется в MessagePack на PHP-потоке —
  это сам по себе монолитный вызов; для `jsonDecode` результат распаковывается из
  msgpack на PHP-потоке. Со структуры данных снимается только часть работы
  (генерация/парсинг текста JSON), а сериализация структуры остаётся на PHP.
  msgpack быстрее json, но это выигрыш в разы, не на порядки.
- Следствие: json-команды — самые спорные в списке и первые кандидаты на вылет по
  бенчмарк-гейту. Они включены из-за узнаваемости сценария («огромный json_decode
  вешает воркер»), но решение о поставке принимают цифры.
- Риск двойного пересечения границы: если результат `jsonEncode` дальше уходит в
  `HttpClient` или пишется в файл, данные пересекают границу дважды. Follow-up
  (не v1): sink-варианты — кодировать сразу в тело запроса или в файл на
  Go-стороне, по образцу `HttpClient::download()`.

### hash / gzip: нативные реализации уже на C

- `hash()` в PHP — это C-реализация со скоростью порядка ГБ/с; sha256 на 100 КБ —
  доли миллисекунды. Go не быстрее; единственный выигрыш — освобождение PHP-потока
  и фан-аут. Значит, целевой кейс — большие payload (сотни КБ и больше) внутри
  корутин, а не «ускорить hash».
- gzip в Go (`compress/gzip`) медленнее C-шного zlib; если бенчмарки покажут
  провал — брать klauspost/compress (drop-in, заметно быстрее). Выход gzip Go не
  байт-в-байт с PHP `gzencode` (метаданные заголовка, разбиение на блоки при том же
  уровне) — корректность проверять только через `gzdecode`-раундтрип, не сравнением
  байтов.

### password_*: самый однозначный кандидат

- `password_hash` намеренно медленный (bcrypt cost 10 — ~50-100 мс, argon2id —
  настраиваемо больше), полностью CPU-bound, строки крошечные — граница бесплатна.
  Один логин-запрос сегодня замораживает весь воркер на это время; со `Std` —
  только свою корутину. Это флагманский кейс фичи.
- Оговорка совместимости: форматы (`$2y$`, `$argon2id$...`) обязаны быть взаимно
  проверяемыми с нативными `password_verify`/`password_hash` — иначе миграция на
  фичу и обратно ломает существующие базы хешей. Тесты interop в обе стороны
  обязательны; дефолтные параметры повторяют PHP (bcrypt cost 10; argon2 —
  memory/time/threads как в PHP_PASSWORD_ARGON2_*).

### Файловые операции: выигрыш зависит от диска

- На локальном SSD с горячим page cache чтение маленького файла — микросекунды:
  поход через границу его только замедлит. Целевые кейсы — большие файлы, холодный
  кэш, медленные/сетевые ФС (NFS, ceph), где нативный вызов блокирует поток на
  миллисекунды и дольше.
- `fileCopy` и `hashFile` — чистый выигрыш при любом размере: байты вообще не
  пересекают границу (паттерн `HttpClient::download`), Go стримит файл сам.
- `fileGetContents` больших файлов тащит весь файл через границу одним куском —
  двойной пик памяти. Стриминговое чтение батчами через `next()` — follow-up, в v1
  задокументировать ограничение.

### Семантический дрейф и поддержка

- Каждая команда — это обещание «ведёт себя как PHP-функция», выполняемое чужим
  рантаймом. Тонкие расхождения (форматирование float в json, заголовок gzip,
  крайние случаи UTF-8) — источник незаметных багов; смягчение — тесты соответствия
  против нативных функций на случайных данных и явный список допусков в доке.
- Каждая команда — поверхность поддержки в двух языках. Список v1 держим коротким,
  расширение — только с бенчмарком и interop-тестами.
- `preg_*` не включать принципиально: RE2 ≠ PCRE не «тонкое расхождение», а другая
  семантика (нет backtracking, lookbehind, рекурсии). Молчаливая подмена движка —
  прямой путь к неотлаживаемым багам у пользователей.

### Память и рантайм Go

- Большие payload надувают Go-хип: рост RSS процесса и давление на GC Go. Обязателен
  mem-leak-стресс с многомегабайтными payload (плоский RSS между раундами).
- Фан-аут CPU-команд грузит те же ядра, на которых крутятся SO_REUSEPORT-соседи
  по per-core пулу: выигрыш одного воркера может стать деградацией пула под полной
  нагрузкой. В доку — оговорка: Std решает латентность и хвосты, throughput
  CPU-bound по-прежнему масштабируется процессным пулом, фичи дополняют друг друга,
  а не заменяют.

### Когда НЕ использовать (резюме для доки)

- Вне корутин (синхронный путь всегда медленнее нативного — кроме sleep).
- Маленькие payload (порог из бенчмарков).
- Когда важен байт-идентичный вывод (`json_encode`-совместимость, побайтовое
  сравнение gzip).
- `preg_*`, `serialize` — эквивалентов не будет сознательно.

## API

Статический фасад (как старый `Sleeper`), `src/Features/Std/Std.php`:

```php
use SConcur\Features\Std\Std;

Std::sleep(seconds: 1);                                  // поглощает Sleeper::sleep
Std::usleep(microseconds: 100);                          // поглощает Sleeper::usleep

$json  = Std::jsonEncode($value);
$value = Std::jsonDecode($json);                         // всегда assoc-массивы

$hex   = Std::hash(algo: 'sha256', data: $bytes);
$hex   = Std::hashFile(algo: 'sha256', path: $path);     // файл читает Go; байты не пересекают границу

$gz    = Std::gzencode($data, level: 6);
$data  = Std::gzdecode($gz);

$hash  = Std::passwordHash($password);                   // bcrypt/argon2id
$valid = Std::passwordVerify($password, $hash);

$data  = Std::fileGetContents($path);                    // чтение на Go-стороне
Std::filePutContents($path, $data, mode: ...);           // запись/дозапись на Go-стороне
Std::fileCopy($sourcePath, $destinationPath);            // целиком на Go-стороне, байты не пересекают границу
Std::fileDelete($path);
```

Внутри корутины вызов подвешивает файбер и выполняется конкурентно; снаружи это
обычный блокирующий вызов (синхронный путь FeatureExecutor).

## Протокол и механика

- Один новый метод `MethodEnum::Std` (`std`) с командным конвертом
  (`StdCommandEnum`, паттерн HttpClient/Sql — поле `cm` выбирает суб-операцию):
  Sleep `slp`, JsonEncode `jen`, JsonDecode `jde`, Hash `hsh`, HashFile `hsf`,
  Gzencode `gzc`, Gzdecode `gzd`, PasswordHash `pwh`, PasswordVerify `pwv`,
  FileRead `fre`, FileWrite `fwr`, FileCopy `fcp`, FileDelete `fdl`. C-ABI не
  тронут — фича это данные.
- PHP: `src/Features/Std/` — `Std.php`, `StdCommandEnum`, `Payloads/*` (каждый
  несёт обязательный дедлайн `timeoutMs`), исключения в `SConcur\Exceptions\Std\*`,
  именованные по случаю (`JsonDecodeException`, `FileOperationException`, ...).
  `src/Features/Sleeper/` удаляется.
- Go: `internal/features/std/` — `feature.go` (диспатч по команде), `sleep.go`,
  `json.go`, `hash.go`, `gzip.go`, `password.go`, `file.go`.
  `internal/features/sleeper/` удаляется; `MethodEnum::Sleep` (`sl`) убирается из
  PHP и Go.
- Оба обязательных требования
  [docs/adding-a-feature.md](../../docs/adding-a-feature.md) соблюдаются: каждый
  обработчик уважает отмену `task.GetContext()`, а дедлайн из payload ограничивает
  операцию через `context.WithTimeout`.

### JSON: прямой транскодер msgpack↔JSON

`encoding/json` в Go сортирует ключи map и по умолчанию HTML-экранирует — и то и
другое здесь неверно. Вместо него `json.go` реализует стриминговый транскодер:

- encode: обход входного MessagePack токен за токеном с прямой записью JSON —
  порядок ключей сохранён, без промежуточных структур, без HTML-экранирования;
- decode: парсинг JSON токен за токеном с прямой записью MessagePack; PHP
  распаковывает его в assoc-массивы.

Невалидный UTF-8 при encode и битый JSON при decode возвращают результат-ошибку →
`JsonEncodeException` / `JsonDecodeException` (обёрнуты по концепции исключений,
оригинал доступен через `getPrevious()`).

### Файловые операции

- `fileGetContents`/`filePutContents` переносят чтение/запись (и блокирующее
  ожидание диска) в Go; содержимое пересекает границу один раз, это неизбежно.
- Режимы записи `filePutContents` переиспользуют семантику `DownloadFileMode`, уже
  живущую в протоколе (Replace `rpl`, Create `crt`, Append `app`).
- `fileCopy` и `hashFile` вообще не двигают байты через границу (паттерн
  HttpClient::download) — Go стримит файл сам.
- v1 — одиночный выстрел (один payload на файл). Стриминговое чтение огромных
  файлов батчами `next()` (машинерия states) — возможное продолжение, не v1.

## Бенчмарк-гейт

Каждая команда до релиза проходит гейт: native vs sync vs async на payload
1 КБ / 100 КБ / 5 МБ (`tests/benchmarks/`, методология
[docs/benchmarks.md](../../docs/benchmarks.md)). Команда, чей async-фан-аут не даёт
реального выигрыша, вырезается из v1. Ожидаемые вердикты: sync-путь всегда
проигрывает нативному (цена границы, как у остальных фич) — фича целится в
корутинный/серверный код; выигрыши — async-фан-аут и «PHP-поток остаётся свободен».

## Сознательно исключено

- `preg_*` — RE2 в Go это не PCRE (другая семантика и возможности); молчаливая
  подмена движков опасна.
- `serialize`/`unserialize` — PHP-специфичный формат.
- `base64_*` и прочие дешёвые преобразования — быстрее границы.
- `openssl_*` шифрование — возможно позже, не v1.

## Семантические допуски (фиксируются в docs/std.md)

- `jsonEncode`: порядок ключей сохранён, вывод — валидный эквивалентный JSON, но не
  байт-в-байт с `json_encode` (детали экранирования, форматирование float). Флаги
  PHP `JSON_*` в v1 не поддерживаются.
- `jsonDecode`: объекты всегда становятся assoc-массивами (режима `stdClass` нет).
- `passwordHash`/`passwordVerify`: кодированные форматы (`$2y$`, `$argon2id$...`)
  взаимно проверяемы с нативными `password_verify`/`password_hash` — interop-тесты
  закрепляют это в обе стороны.
- Отмена: sleep отменяется немедленно; hash/gzip/json проверяют контекст перед
  стартом и не прерываются посреди операции; файловые операции ограничены
  контекстом дедлайна.

## Миграция Sleeper (жёсткое удаление)

- `Sleeper::sleep/usleep` → `Std::sleep/usleep` везде: feature-тесты, бенчмарки,
  stress- и mem-leak-тесты, демо-серверы (`tests/servers/http|ws`), пример
  quick-start в README (оба языка), доки.
- `src/Features/Sleeper/`, `internal/features/sleeper/` и `MethodEnum::Sleep`
  удаляются. Без BC-фасада — проект pre-1.0 и экспериментальный.

## Версионирование

Новый метод + payloads + удалённый метод = изменение протокола PHP↔Go → минорный
бамп версии расширения, один раз на ветке фичи, все три источника вместе
(`ext-go-legacy/main.go`, `Extension.php::REQUIRED_EXTENSION_VERSION`, `composer.json`).

## Тесты

- На команду: корректность против нативной функции (раундтрип для json:
  `jsonDecode(jsonEncode($x)) == $x` и перекрёстные проверки с нативными
  `json_encode`/`json_decode`), синхронный путь, пути ошибок (битый json,
  отсутствующий файл, неизвестный algo → исключение, именованное по случаю, с
  цепочкой `previous`).
- Interop: `Std::passwordHash` проверяется нативным `password_verify` и наоборот.
- Конкурентность: фан-аут из N тяжёлых хешей завершается за ~max, а не ~sum, плюс
  проверка уровня сервера, что огромный `Std::hash` в одном обработчике не
  задерживает лёгкий запрос (E2E-паттерн coroutine-switching).
- Отмена: `WaitGroup::stop()`/shutdown во время sleep и посреди записи файла.
- mem-leak-стресс с многомегабайтными payload (плоский RSS).
