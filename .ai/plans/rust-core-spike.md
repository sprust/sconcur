## Вопрос и гейт

`hot-path-optimization.md` закрыл вопрос смены языка строкой «пол L0 = 14.2 мкс,
а не 150». Но это пол **Go**. Открытым остался вопрос, каков он у другого
рантайма, и сколько из статьи «граница L1 − L0 = 29.8 мкс» держится на цене
именно cgo (`needm`/`dropm` на входе, пробуждение cgo-locked M, копии строк) —
а не на самой идее пересылать msgpack через границу.

Гейт был зафиксирован до кода:

> **L0 ≤ 9 мкс и L1 − L0 ≤ 18 мкс** — тогда есть предметный разговор о поэтапном
> переносе. Не попал — вопрос закрыт окончательно.

Метрика — **мкс CPU на запрос** (`CPU_avg% * 10000 / rps`), не rps: rps мешает
эффективность с насыщением.

## Что построено

`ext/` — ядро расширения на Rust, зеркалящее структуру пакетов Go один в
один. Собирается в `ext/build/sconcur.so`, который **загружается
неизменённым PHP-пакетом**: та же `sconcur.c` (отличается ровно одной строкой —
`#include "sconcur_core.h"` вместо `_cgo_export.h`), тот же набор C-экспортов,
тот же бинарный кадр результата, тот же `version()` = `0.11.0`.

| Go | Rust | Комментарий |
| --- | --- | --- |
| `main.go` | `src/lib.rs` | C-экспорты, кадр результата, тикер преемпшна |
| `internal/dto` | `src/dto` | `Message`, `Result` |
| `internal/types` | `src/types` | `Method` — enum вместо строки с интернированием |
| `internal/tasks` | `src/tasks` | `Task`, `add_result` |
| `internal/flows` | `src/flows` | `Flow`, `Flows` + пул флоу, `run_task_protected` |
| `internal/handler` | `src/handler` | общий канал, `wait_any*`, `pending`, батч-буфер |
| `internal/states` | `src/states` | реестр стримовых состояний |
| `internal/errs`, `helpers` | `src/errs`, `src/helpers` | префиксы ошибок, `calc_execution_ms` |
| `features/factory.go` | `src/features/mod.rs` | единый фасад `detect_message_handler` |
| `features/sleeper` | `src/features/sleeper` | целиком |
| `features/httpserver` | `src/features/httpserver` | подмножество (см. ниже) |
| `features/sql` | `src/features/sql` | целиком: query/exec/begin/commit/rollback, mysql и pgsql |
| `features/mongodb` | `src/features/mongodb` | целиком: 26 команд, курсоры, bulkWrite, сериализатор BSON↔msgpack |

Соответствие механизмов:

| Go | Rust |
| --- | --- |
| горутина на задачу | `tokio::spawn` на задачу |
| `chan *dto.Result` буфер 1024 | `crossbeam_channel::bounded(1024)` |
| спин `runtime.Gosched()` ×8 перед парковкой | спин внутри `crossbeam::recv` (писать нечего) |
| `context.Context` на флоу | `CancellationToken` |
| `recover()` в `RunTaskProtected` | `catch_unwind` вокруг polling'а future |
| `sync.Pool` для `Flow` | `Vec` под тем же замком реестра |
| `net/http` | `hyper` 1.x |
| `vmihailenco/msgpack` | `rmp-serde` (+ ручной энкодер события запроса) |
| `database/sql` + go-sql-driver/pgx | `sqlx` (mysql + postgres) |
| `mongo-driver/v2` + `bsoncore` | `mongodb` + `bson` |

## Что НЕ построено (границы спайка)

Осознанно, чтобы спайк остался спайком:

- Фичи httpclient, socket/ws (сервер и клиент), amqp — их методы отвечают
  «unknown method» через тот же фасад, что и в Go.
- Стримовые ответы HTTP (`head`/`chunk`/`end`) — реализован только одноразовый
  полный ответ (`op=0`), остальные отвечают явной ошибкой, а не тишиной.
- Стриминг тела запроса, телеметрия, `internal/stats`, `internal/logger`.
- `next()` маршрутизируется через реестр состояний, но регистрировать состояния
  в спайке некому — ответ всегда «state not started», как и у Go для неизвестного
  ключа.

## Результаты

Условия: 6 воркеров с пином `taskset -c $i`, wrk 4 треда / 128 соединений / 15 с,
3 раунда, **ступени чередуются ядро за ядром в одной сессии** — машина занята
посторонней нагрузкой (три контейнера RabbitMQ, ~500% CPU постоянно), поэтому
предметом являются дельты, а не абсолютные значения. Медианы трёх раундов, все
ответы 200.

Обе ступени гоняет **один и тот же PHP-скрипт** (`--ladder=l1`), отличаются они
ровно переменной `SCONCUR_HTTP_BENCH_L0` — так что `L1 − L0` это граница и
ничего кроме неё.

| Ступень | Go rps | Go мкс/зпр | Rust rps | Rust мкс/зпр | Дельта |
| --- | ---: | ---: | ---: | ---: | ---: |
| L0 — сервер отвечает сам, PHP не зовётся | 374 996 | 11.85 | 636 002 | **6.31** | **−47%** |
| L1 — каждый запрос ходит в PHP и обратно | 161 644 | 28.24 | 254 204 | **17.64** | **−38%** |
| граница (L1 − L0) | — | 16.39 | — | **11.33** | **−31%** |

Разброс по раундам: Go L0 11.47–12.40, Rust L0 5.26–6.34, Go L1 28.05–36.27,
Rust L1 17.59–18.52. Единственный выброс — Go L1 в третьем раунде (36.27 при
586% CPU), поэтому медиана, а не среднее.

Для сверки с доками: тамошняя лестница (12 воркеров, wrk 4×256) даёт Go
L0 14.2 / L1 38.1. Здесь геометрия другая (6 воркеров, 128 соединений), Go-числа
ниже, но порядок тот же — внутрисессионное сравнение корректно.

### Гейт

| Условие | Порог | Rust | |
| --- | ---: | ---: | :---: |
| Пол L0 | ≤ 9 мкс | 6.31 | ✅ |
| Граница L1 − L0 | ≤ 18 мкс | 11.33 | ✅ |

**Оба условия выполнены.**

### Что это даёт на полном запросе

Экономия ложится ровно на две ступени из четырёх; Fiber (13.9) и обвязка PHP
(33.5) не затрагиваются вообще. Пересчёт на доковскую геометрию `/` (91.2
мкс/запрос, 133.5k rps) двумя способами:

- по измеренной абсолютной экономии (10.6 мкс): 91.2 → **80.6 мкс**, −11.6%;
- по отношению Rust/Go на L1 (0.625), применённому к доковским 38.1: 91.2 →
  **76.9 мкс**, −15.7%.

То есть **−12…16% CPU на пустой запрос**, rps 133.5k → ~151–158k. На `/all` и
на всех БД-бенчмарках — **ноль**: там упор в fsync бэкендов (563% CPU из 1200
доступных), и ядро расширения к этому отношения не имеет.

### Патология `l2f` исчезает

Отдельная пара прогонов (одиночные, та же геометрия). `l2` — свежий Fiber на
запрос, пуш **вне** стека файбера (продовая форма); `l2f` — тот же пуш **на**
стеке файбера.

| Ступень | Go мкс/зпр | Rust мкс/зпр |
| --- | ---: | ---: |
| l2 (пуш вне стека файбера) | 38.92 | 35.67 |
| l2f (пуш на стеке файбера) | **273.24** | **27.55** |
| l2f / l2 | **×7.0** | **×0.77** |

Go на `l2f` деградирует в 7 раз — это ровно механизм из
[hot-path-optimization.md](hot-path-optimization.md), раздел 8: cgo-вызов со
стеком-указателем внутри файберного стека заставляет рантайм пересчитать границы
системного стека (`x_cgo_getstackbound` → `pthread_getattr_np`), а glibc для
главного треда отвечает на это полным чтением и парсингом `/proc/self/maps`.

**У Rust этого механизма нет вовсе.** `l2f` не просто не деградирует — он
*дешевле* `l2`, потому что делает меньше работы (файбер отрабатывает внутри
`start()`, без пары suspend/resume).

Это важнее процентов. `Scheduler::$pendingDispatches` и `pendingStopFlows`,
плюс правило «cgo никогда не вызывается со стека корутины», существуют
исключительно ради обхода этой патологии. На ядре без cgo вся эта машинерия
не нужна, а пуш из корутины становится не запретной, а **предпочтительной**
формой.

## Фаза 2: fork и PHP-FPM

Единственный пункт из вердикта, дававший не проценты, а новый класс применения,
и в первой фазе бывший только предпосылкой. Проверен.

### Что для этого понадобилось

Ленивого старта рантайма мало. Если родитель успел рантаймом воспользоваться, в
потомок переезжает `Runtime` без единого рабочего потока — из `fork` выживает
только форкающий. Поэтому:

- рантайм, хендлер и реестры фич (HTTP и SQL) переехали в `Core`;
- на `pthread_atfork` повешен обработчик, который в потомке взводит атомарный
  флаг — единственное, что там вообще безопасно делать;
- следующее обращение видит флаг и пересобирает `Core` целиком, **бросая старый
  утечкой, а не дропом**: дроп `tokio::Runtime` join'ит рабочие потоки, которых в
  потомке нет, и завис бы навсегда.

Цена на горячем пути — один relaxed-atomic на обращение.

### Результаты

`ext/check/fork-check.php` (три сценария) и `ext/check/fpm-check.sh`
(настоящий пул php-fpm из 4 статических воркеров, запросы через `cgi-fcgi` без
веб-сервера). Проверка засчитывается, только если веер из 12 корутин по 100 мс
реально шёл параллельно: воркер, тихо свалившийся в последовательное исполнение,
её не проходит.

| Сценарий | Go | Rust |
| --- | :---: | :---: |
| `fork` до первого использования расширения | зависание | 108.0 мс |
| `fork` после использования (рантайм уже поднят) | зависание | 102.7 мс, родитель жив |
| 4 потомка параллельно | зависание | все по ~106 мс |
| **PHP-FPM, 4 воркера, 8 запросов** | все запросы висят до таймаута | **все 8, по ~103 мс** |

Go зависает **и в сценарии «до первого использования»** — расширение загружено,
но не тронуто. Это и подтверждает механизм: рантайм Go стартует внутри `dlopen`,
до `MINIT`, поэтому «не трогать до форка» не спасает. Под FPM пул при этом
поднимается, и `ping.php` (страница, не трогающая расширение) отвечает нормально
— висит только то, что действительно ждёт корутину.

**Ограничение README «нельзя `pcntl_fork` после загрузки расширения, только CLI»
— свойство рантайма Go, а не архитектуры библиотеки.**

## Фаза 3: фича SQL (MySQL + PostgreSQL)

Перенесена целиком: `query`/`exec`/`begin`/`commit`/`rollback`, пул на
driver+DSN+размер с рефкаунтом и подметанием, потоковый курсор с заглядыванием
на строку вперёд, транзакции, переживающие задачу, которая их открыла.

Проверка — **штатные тесты проекта**, не свои: они и есть спецификация
совместимости по типам.

| Набор | Результат |
| --- | --- |
| `tests/feature/Features/Mysql` | **23/23, 81 проверка** |
| `tests/feature/Features/Pgsql` | **25/26, 87 проверок** |

Что оказалось непросто и стоит знать заранее:

- **DSN.** PHP шлёт Go-формат (`user:pass@tcp(host:port)/db?parseTime=true`) — это
  часть контракта, его пишут и демо-сервер, и бенчмарки, и тесты. Разбирается в
  `dsn.rs`. Переписать PHP-сторону под URL значило бы отказаться от главного
  свойства спайка: ядро грузится неизменённым пакетом.
- **Типы параметров в Postgres.** sqlx шлёт все параметры бинарно (жёстко, в
  исполнителе), pgx — текстом с невыведенным типом, и поэтому у Go строка
  `'123.4500'` спокойно ложится в `numeric`. Трюк с нетипизированным параметром
  тут не работает: сервер выведет `numeric` и применит к тексту *бинарный*
  парсер. Пришлось спрашивать типы у сервера — `describe` перед выполнением
  (sqlx кэширует его вместе с prepared statement) и приведение каждого
  текстового параметра к типу его позиции (`pg_bindings.rs`).
- **Ширины целых в Postgres точные** — и на чтении (`INT4` не читается как
  `i64`), и на записи (`i64` в колонку `int4` — «incorrect binary data format»).
- **Формы значений — контракт.** `MysqlTypesTest` фиксирует: `DECIMAL` строкой,
  `TINYINT(1)` числом а не булевым, `BLOB` строкой, переживающей `\x00`..`\xff`,
  `DATE` в RFC3339 (у Go включён `parseTime=true`). `PgsqlTypesTest` при этом
  требует для `bool` настоящий булев тип. Каждая такая форма здесь — явное
  решение; у Go она получается сама собой из того, что драйвер отдаёт `[]byte`.

Одно осознанное расхождение, объяснённое в коде:

- **Размер пула по умолчанию.** `database/sql` без `maxOpenConns` не ограничен, а
  sqlx требует максимум и разворачивает по нему таблицу слотов — запрос
  `u32::MAX` это попытка выделить ~200 ГиБ (поймано на первом же прогоне тестов).
  Поставлено 32; все бенчмарк-ручки и демо-сервер размер задают явно.

Второе — `bytea` с невалидным UTF-8 — какое-то время стояло тут же как
непроходящий тест, и оказалось починимым. pgx шлёт строку текстом, поэтому её
разбирает серверный `byteain`: `'plainbytes'` проходит, `"\x00\x01binary"`
отвергается из-за NUL. sqlx шлёт только бинарно, и `bytea` брал байты как есть —
то есть молча принимал то, что сервер бы отверг. Решение оказалось тем же, что уже
применялось к `numeric` и датам: **выполнить на клиенте то преобразование, которое
сервер сделал бы с текстовым параметром.** `byteain` эмулируется в
`pg_bindings.rs` (hex-форма, escape-форма, отказ на NUL), и обе стороны сходятся.
Отличие от Go осталось одно и названо в комментарии: ошибка поднимается на
клиенте, а не приходит от сервера.

### Метрики `/db` и `/db-rw`

Доковские числа сняты на другой машине и с этими несопоставимы — поэтому оба
ядра меряются здесь заново, встык, в одной сессии. 6 воркеров с пином, пул 9 на
процесс, wrk 4×128, 15 с, 3 раунда, медианы. Порядок ядер чередуется по раундам.

| Ручка | Ядро | rps | CPU avg | мкс CPU/зпр | p50 | p99 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `/db` | Go | 23 874 | 448.2% | 190.4 | 5.01 мс | **15.16 мс** |
| `/db` | Rust | **34 175** | 443.4% | **128.0** | 1.35 мс* | 410.76 мс* |
| `/db-rw` | Go | 2 126 | 126.6% | 579.6 | 54.53 мс | 213.40 мс |
| `/db-rw` | Rust | **2 291** | **96.6%** | **413.8** | **51.60 мс** | **167.05 мс** |

- **`/db`** (точечные SELECT, упор в CPU): +43% rps, −33% CPU на запрос.
- \* Колонки латентности для Rust помечены звёздочкой: они получены из
  wrk-харнесса и **недостоверны** — разбор ниже. Перезамер независимым клиентом
  даёт у Rust латентность лучше, чем у Go, включая хвост.
- **`/db-rw`** (INSERT + COUNT + SELECT, упор в бэкенд): +8% rps при −29% CPU на
  запрос. Выигрыш по пропускной способности мал именно потому, что упор не в
  ядро, — ровно то, что показывал анализ до спайка. Хвост при этом лучше на 22%.

#### Две ошибки методики, найденные по дороге

Обе искажали результат в разные стороны, обе исправлены в `bench/db.sh`:

1. **`/db-rw` копит строки.** Каждый запрос вставляет строку, а `COUNT(*)`
   дорожает с ростом `bench_rw`. В первом прогоне ядра шли в фиксированном
   порядке, и Rust всегда мерился по большей таблице: получилось 1563 против
   2344 rps у Go — «Rust медленнее на 33%». После `TRUNCATE` перед каждым
   прогоном картина перевернулась: 2291 против 2126. Порядок ядер теперь ещё и
   чередуется по раундам, чтобы остаток дрейфа не доставался одному и тому же.
2. **Сводка молча падала** (`asort` — расширение gawk, на хосте mawk), так что
   первый прогон дал только построчные числа.

#### Хвост p99 на `/db` — оказался артефактом замера

В таблице выше у Rust на `/db` стоит p99 = 410 мс при медиане 1.35 мс. Цифра
воспроизводилась во всех трёх раундах, и я разобрал её до конца. **Ядро тут ни
при чём: врал замер.**

Проверенные и **не подтвердившиеся** гипотезы, по порядку:

1. `block_in_place` в отдаче результата на переполненном канале. Путь переписан
   на асинхронный (`Task::add_result` ждёт через `yield_now`/таймер, не блокируя
   рабочий поток) — хвост не сдвинулся. Правку оставил: она верна сама по себе,
   на однопоточном рантайме блокировать воркер нельзя, — но причина была не в ней.
2. Разгон пула соединений. Прогон вчетверо длиннее (60 с) даёт тот же хвост.
3. Упирается генератор нагрузки. 4, 8 и 12 потоков wrk — одинаковый результат.
4. Сервер отдаёт лишние ответы, из-за чего wrk завышает счётчик. Проверено
   двумя способами: (а) `/db-rw` вставляет ровно строку на запрос, и
   `строк − 10 000` (посев таблицы) совпало со счётчиком wrk плюс 128 запросов в
   полёте — у обоих ядер; (б) прямой клиент на одном keep-alive соединении, 300
   последовательных запросов: ноль лишних байт в сокете.

Что вывело на ответ — проверка замера на внутреннюю непротиворечивость.
`rps × средняя латентность` это среднее число запросов, одновременно
находящихся в системе. Клиент держит N соединений и по одному запросу в полёте
на каждом, значит **величина физически не может превысить N** — это потолок, а
не ориентир:

| соединений | Go, по wrk | Rust, по wrk |
| ---: | ---: | ---: |
| 4 | 4.0 | **5.2** |
| 16 | 16.0 | **415.0** |
| 64 | 71.2 | **2782.7** |

У Go попадание в потолок на всех точках. У Rust потолок пробит **уже на
четырёх соединениях** — 5.2 при максимуме 4, то есть замер неверен с самой
первой точки, просто там это ещё похоже на правду. Дальше расхождение растёт
лавинообразно: ×1.3, ×26, ×43.

Сверка с независимым клиентом на той же точке (4 соединения) показывает, где
именно ошибка: пропускная способность совпадает (10 084 против 10 874 rps), а
средняя латентность у wrk завышена в 1.4 раза (519 против 370 мкс) — ровно на
столько же пробит потолок. Пропускная способность честная (проверено ещё и по
вставленным строкам), латентность — нет.

Перезамер вторым, независимым клиентом (`bench/loadclient.py`: поток на
соединение, строго последовательные запросы, так что конкуренция равна числу
соединений точно), один воркер с пином, `/db`:

| соединений | Go rps | Go mean | Go p99 | Rust rps | Rust mean | Rust p99 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 9 180 | 0.44 мс | 1.12 мс | **10 874** | **0.37 мс** | **1.01 мс** |
| 16 | 8 654 | 1.85 мс | 4.56 мс | **11 981** | **1.33 мс** | **1.74 мс** |
| 64 | 8 152 | 7.84 мс | 33.14 мс | **11 706** | **5.46 мс** | **7.85 мс** |

Закон Литтла сходится у обоих на всех точках (4.0 / 16.0 / 63.9),
переподключений и ошибок ноль. **Хвост у Rust не хуже, а вчетверо лучше:** 7.85
против 33.14 мс на 64 соединениях.

Механизм искажения внутри wrk остался недоказанным. Правдоподобная версия — что
ответы приходят пачками и wrk штампует время завершения после разбора всей
пачки; но на четырёх соединениях пачек почти нет, а завышение уже
сорокапроцентное, так что версия слабая, и выдавать её за объяснение нельзя.
Твёрдо установлено другое: замер нарушает физическую границу, а независимый
инструмент даёт непротиворечивые числа. Практический вывод для проекта важнее: **колонки p50/p99 из wrk-харнесса для этого сервера
недостоверны, а rps и CPU — достоверны.** Если латентность будет предметом
решения, её надо снимать вторым инструментом и проверять законом Литтла; это
дешёвая проверка, которая здесь поймала бы ошибку сразу.

## Фаза 4: фича MongoDB

Вторая по сложности после AMQP, и взята именно поэтому: SQL был из простых, а
цена «тонкой» фичи — это то, чего не даёт оценка со стороны.

Перенесено целиком: все 26 команд, курсоры find/aggregate с заглядыванием на
документ вперёд, bulkWrite, пул клиентов и — главное — сериализатор
BSON↔MessagePack с конвертом объектов `SConcur\Bson\*`.

| Набор | Результат |
| --- | --- |
| `tests/feature/Features/Mongodb` | **109/109, 21 521 проверка, 1 incomplete** |

Это **в точности совпадает с Go**: то же число тестов, то же число проверок, тот
же единственный incomplete.

### Объём

| | Go | Rust |
| --- | ---: | ---: |
| строк в фиче | 4 073 | **2 247** |
| строк во всём ядре | ~3 215 + фичи | 7 096 |

Меньше строк — не заслуга языка: `bsoncore` в Go собирает BSON побайтово, а
здесь driver'ский `Document` делает это сам. Обратная сторона в разделе про
производительность ниже.

### Пять ошибок, каждая из которых молча портила данные

Все пять — не про Rust, а про то, что контракт ext-msgpack нигде не выписан
целиком и восстанавливается только чтением обеих сторон:

1. **Параметры команд — не вложенные блобы.** Go объявляет `Filter []byte` и
   заполняет его сырыми байтами поля, но на проводе `'f' => $this->filter` —
   обычный вложенный массив. Я читал его как строку байтов, и **все фильтры
   уходили пустыми**: `deleteOne` удалял не то, `distinct` возвращал 5 значений
   вместо 2, `find` — 11 документов вместо 1. 23 ошибки и 21 провал из одной
   строки.
2. **Счётчик контейнеров.** ext-msgpack нумерует каждый контейнер, а повтор
   одного и того же объекта кодирует ссылкой на номер. Я не считал map у
   `scope` в Javascript — сдвиг на единицу, и `reference to an unknown object 6`.
3. **Хинт завёрнут.** `$data['hn'] = ['v' => $this->hint]`. Без разворачивания
   сервер получал просьбу использовать индекс с именем `v` — «hint provided does
   not correspond to an existing index» на трёх тестах.
4. **Пустой документ уходит массивом, а не map.** ext-msgpack декодирует пустую
   map (`80`) в `stdClass`, а пустой массив (`90`) в `[]`. В Go это прямо
   прокомментировано в `encodeBSONDocument`; воспроизвёл бы я это по здравому
   смыслу — нет.
5. **Состояние не снималось при остановке флоу.** В Go `states.Start` вешает
   `context.AfterFunc`; я это пропустил. Когда PHP бросает курсор на полпути,
   `next()` больше не зовут — и снять состояние может только конец флоу. Без
   хука реестр держал состояние вечно, а MongoDB — ещё и серверный курсор.
   **Та же утечка была и в SQL-курсорах**, где её ничто не ловило.

Пункт 5 стоит отдельного слова: его поймал `MongodbAbandonedCursorTest`, который
опрашивает счётчик открытых курсоров на сервере до пяти секунд. Без него утечка
уехала бы в продакшен незамеченной — на стороне Rust всё выглядело исправным.

### Что это говорит про цену переноса

Тесты проекта отработали как приёмка идеально: каждая из пяти ошибок портила
данные тихо, и все пять были пойманы. Но обратная сторона — **ни одну из них не
предотвратила бы аккуратность**. Это не ошибки трансляции кода, это места, где
контракт живёт в комментарии на другой стороне границы, и узнать о них можно
только уперевшись.

Для оценки AMQP это и есть главный вывод: 4.5 тысячи строк там тоньше этих 4
тысяч (подтверждения публикации, возвраты, пул каналов, супервизия консьюмеров),
а тестовая приёмка слабее — брокер надо ещё и ронять, чтобы проверить половину
поведения.

отчёте был результатом Go, а не Rust.

Путь сделан переопределяемым (`SCONCUR_EXT`, по умолчанию без изменений), и
честная цифра оказалась другой — **49/57**. Все восемь провалов лежат ровно на

| Провал | Пробел |

проверено, какое расширение загрузил тот процесс, который делает работу. Здесь
это стоило одного неверного утверждения в отчёте.

## Побочные наблюдения

| | Go | Rust | |
| --- | ---: | ---: | --- |
| размер `sconcur.so` | 18.46 МБ | **3.24 МБ** | −82% |
| RSS воркеров (сумма по 6, пик, L1) | 298.3 МиБ | **185.5 МиБ** | −38% (49.7 → 30.9 МиБ на воркер) |
| строк кода в зеркалимом наборе файлов | ~3 215 | 2 467 | не выигрыш: Rust реализует строгое подмножество |

- **Рантайм стартует лениво.** Go-рантайм поднимается внутри `dlopen`, из чего и
  следует запрет `pcntl_fork` после загрузки расширения. Здесь до первого
  реального пуша не создаётся ни одного потока. Это структурная предпосылка для
  FPM и `fork`, но **в спайке она не проверена** — утверждать можно только то,
  что препятствие в виде «рантайм уже поднят» отсутствует.
- **Число потоков совпадает по построению.** `available_parallelism` на Linux
  читает маску аффинности, поэтому воркер под `taskset -c N` получает ровно один
  рабочий поток tokio — так же, как Go выводит `GOMAXPROCS` из аффинности.
  `SCONCUR_RUNTIME_THREADS` переопределяет, зеркаля `GOMAXPROCS`.
- **Спин перед парковкой писать не пришлось.** `waitSpinIterations` с восемью
  `runtime.Gosched()` — обход дорогого пробуждения cgo-locked M. `crossbeam::recv`
  спинит сам, а PHP-тред здесь обычный поток без прицепленного рантайма.
- **Content-Type пришлось досылать вручную.** `net/http` сниффит его, когда
  обработчик не задал, — это 39 байт на ответ, которые попадают прямо в цифры
  трафика. Без выравнивания сравнение было бы нечестным в пользу Rust.
- **Найдено и исправлено по ходу:** утечка регистрации запроса при обрыве
  соединения клиентом (в Go её закрывает `defer` conn-горутины, здесь
  потребовался Drop-гвард), и насос запросов, не реагировавший на остановку
  флоу при живых keep-alive соединениях.

## Ворота

Гейт пройден по обоим условиям, и сверх того спайк снял вопрос, которого в гейте
не было: **патология пуша со стека корутины — свойство cgo, а не архитектуры.**

Что это НЕ означает:

- Не означает, что переезд оправдан. −12…16% на пустой ручке и ноль на реальных
  нагрузках — это то же самое, что показывал анализ до спайка. Ступени, где
  лежит основная стоимость (Fiber 13.9 и обвязка PHP 33.5 мкс), ядром
  расширения не затрагиваются, и ленивый PSR-7 из
  [hot-path-optimization.md](hot-path-optimization.md) (потолок ~30 мкс) по-прежнему
  даёт больше, чем весь переезд.
- Не означает, что 18 тысяч строк переносимы за те же деньги. Спайк — 2.5 тысячи
  строк без единого драйвера. AMQP (4.5 тыс. строк: подтверждения публикации,
  возвраты, пул каналов, супервизия консьюмеров) и MongoDB (4 тыс., включая
  BSON↔msgpack) остаются главным риском, и `lapin` слабее `amqp091-go` ровно там,
  где у нас тонко.

Что стало предметным:

1. Пол ядра действительно вдвое дешевле (6.31 против 11.85 мкс), и граница
   действительно на треть дешевле — это измерено, а не оценено.
2. Ограничение «cgo только с главного стека», ради которого построена очередь
   отложенного диспатча, на другом ядре не существует.
3. Ленивый старт рантайма снимает структурное препятствие для `fork`/FPM.

**Следующий шаг, если тема продолжается** — не порт, а вторая проверка: поднять
на спайке `fork`/FPM-сценарий и убедиться, что предпосылка из пункта 3
действительно реализуема. Это опять несколько дней, и оно проверяет
единственное, что даёт не проценты, а новый класс применения.
