# ТЗ: диспетчеризация запросов через мастер

> **Статус: замеры проведены, рекомендуется закрыть.** Альтернатива
> `SO_REUSEPORT` для разнородной нагрузки. Разбор в разделе 9 показал, что
> посылки раздела 1 не проверены; `dispatch-experiment.md` их проверил и
> опроверг — итог в 9.7.

## 1. Постановка задачи

### Что не так с `SO_REUSEPORT`

Ядро балансирует **соединения**, а не запросы, и хеширует по кортежу без учёта
загрузки. При keep-alive соединение прибито к воркеру на всё время жизни:

- один медленный запрос задерживает все последующие на этой же connection, даже
  когда соседний воркер простаивает;
- воркер, умерший с запросами в работе, роняет соединения — накопленное в его
  accept-очереди получает RST;
- у ядра нет сигнала о занятости воркера.

### Что даёт диспетчеризация

Мастер терминирует HTTP и раздаёт **каждый запрос отдельно**, выбирая воркера по
загрузке. Соединение клиента живёт в мастере и переживает смерть воркера.

### Чего это стоит

HTTP-парсинг переезжает из воркера в мастер (там он и остаётся, а не
дублируется), но добавляются кадрирование, две записи в сокет и два разбора.
**Суммарный CPU системы вырастет.** Выигрыш только в p99 на разнородной
нагрузке. На однородной пустой ручке режим обязан проигрывать — это ожидаемый
результат, а не регрессия.

### Границы

- Режим **опциональный**, `SO_REUSEPORT` остаётся дефолтом
- Реализация воркера не меняется: те же `HttpServer` и `serve()`, новый
  параметр вместо `host`/`port`

---

## 2. Архитектура

```
клиент ──HTTP──▶ Мастер (Go)
                   ├── HTTP-сервер, терминирует соединения
                   ├── диспетчер: выбор воркера, in-flight, backpressure
                   └── unix-сокет на воркера ──▶ Воркер N (PHP + ext)
                                                   └── Scheduler, файбер на запрос
```

Мастер держит по одному unix-сокету на воркера. **Запросы мультиплексируются:**
несколько запросов в одном сокете одновременно, ответы приходят вперемешку.
Роутинг по `requestId`.

Путь сокета передаётся воркеру аргументом при `proc_open`; воркер подключается
на старте и слушает через расширение.

---

## 3. Протокол

Формат кадра — существующий `FrameCodec`: 4 байта BE длины + тело. Добавляется
байт типа перед телом.

| Тип | Направление | Назначение |
| ---: | --- | --- |
| `0x01` | M → W | `REQUEST` |
| `0x02` | W → M | `RESPONSE` |
| `0x03` | W → M | `ERROR` (паника обработчика) |
| `0x04` | M → W | `CANCEL` (клиент отвалился) |
| `0x10` | W → M | `HELLO` (готовность, версия, `maxConcurrency`) |
| `0x11` | M ↔ W | `PING` / `PONG` |
| `0x12` | M → W | `DRAIN` (готовиться к остановке) |

`REQUEST`: `requestId` (uint64 LE) + метод, путь, query, заголовки, тело, remote
addr. `RESPONSE`: тот же `requestId` + статус, заголовки, тело.

**Кодирование тела:** msgpack на первой итерации — он уже есть с обеих сторон.
Ручное кодирование как в `hand-encode the request event` — оптимизация второго
этапа, после замеров.

**Тело запроса и ответа передаётся копией.** На больших POST это доминирующая
статья, заметнее всего оверхеда на пустой ручке. Стриминг тела — вне области
этого ТЗ, зафиксировать как ограничение.

## 4. Диспетчер

### 4.1. Выбор воркера

Least-in-flight: мастер сам ведёт счётчик (`+1` при отправке, `−1` при
`RESPONSE`/`ERROR`/таймауте). Телеметрия для этого не нужна — счёт точный и
бесплатный.

Оговорка на будущее: in-flight считает запросы, а не потребление. Десять
запросов по 50 мс и сто по 0.5 мс дают противоположные показания при одинаковой
нагрузке. Если на смешанном профиле это проявится, второй итерацией — EWMA
времени ответа как вес. **Не делать сразу**, сначала измерить.

### 4.2. Backpressure

**Это отдельный механизм, не часть выбора воркера.** Least-in-flight отвечает на
вопрос «кому отдать», но когда все заняты, он всё равно кого-то выберет:
минимум из двенадцати больших чисел — тоже число.

Конкурентный воркер делает вопрос острее, а не мягче: он примет и тысячу
запросов, потому что каждый — просто ещё один файбер. Встроенной точки, где
система перестаёт брать работу, нет.

Обязательный минимум:

| Параметр | Смысл | Дефолт |
| --- | --- | --- |
| `workerMaxInFlight` | потолок запросов на воркера | `maxConcurrency` воркера, иначе 256 |
| `queueSize` | глобальная очередь ожидания | 1024 |
| `queueTimeoutMs` | сколько запрос ждёт свободного воркера | 1000 |

Алгоритм:

1. Есть воркер ниже потолка → отправить
2. Все на потолке, очередь не полна → в очередь
3. Очередь полна → **`503` немедленно**, заголовок `Retry-After`
4. Ожидание в очереди превысило `queueTimeoutMs` → `503`

Без шага 3 очередь и есть утечка памяти под пиком.

### 4.3. Отказы

- **Воркер умер с запросами в работе.** Мастер знает `requestId` всех
  незавершённых. Идемпотентные (GET/HEAD) — переотправить другому; остальные —
  `502`. Переотправку сделать выключаемой (`retryIdempotent`, дефолт `true`)
- **Таймаут запроса.** `requestTimeoutMs`, по истечении — `504` клиенту,
  `CANCEL` воркеру, in-flight декрементируется
- **Клиент отвалился.** `CANCEL` воркеру, чтобы он не дожёвывал мёртвую работу
- **Сокет разорвался.** Все in-flight этого воркера считаются потерянными,
  воркер помечается недоступным, `RestartPolicy` поднимает новый

### 4.4. Graceful reload

Преимущество перед `SO_REUSEPORT`, ради которого стоит делать: соединения живут
в мастере. Rolling restart без единого сброшенного соединения — `DRAIN`, ждать
завершения in-flight, `SIGTERM`, поднять новый, повторить для следующего.

## 5. Изменения в компонентах

### Мастер (Go)

Новый режим рядом с супервизией. Мастеру теперь **нужен** Go-рантайм с HTTP —
это отход от текущего «мастер не требует расширения». Зафиксировать явно.

Отдельный `GOMAXPROCS` и отдельный профиль: при 63k rps мастер один делает
accept, парсинг, две сериализации и две записи, и становится кандидатом в
узкое место раньше воркеров.

### Воркер (PHP + ext)

- `HttpServer` принимает `dispatchSocket: string` взамен `host`/`port`
- Слушает сокет на Go-стороне (не PHP-стримом): кадр приезжает в горутину
  независимо от того, чем занят PHP, и забирается на ближайшем витке `tick()`
- На `REQUEST` — `Scheduler::spawn` с обработчиком, как сейчас на HTTP-запрос
- `maxConcurrency` продолжает действовать и сообщается мастеру в `HELLO`
- `CANCEL` → отмена соответствующей корутины

### CLI

`bin/sconcur-server --dispatch` плюс параметры из 4.2. Без флага поведение
не меняется.

## 6. Этапы

1. Протокол и кадрирование, `HELLO`/`PING`, без HTTP — эхо-стенд
2. Мастер: HTTP + диспетчер + least-in-flight, без backpressure
3. Воркер: `dispatchSocket`, приём `REQUEST`, отправка `RESPONSE`
4. Backpressure (4.2) — **до любых замеров под нагрузкой**
5. Отказы (4.3), `CANCEL`, переотправка идемпотентных
6. Замеры (раздел 7)
7. Graceful reload (4.4)
8. По результатам 6: ручной кодек вместо msgpack, EWMA

---

## 7. Критерии приёмки

Мерить **мкс CPU/запрос по всем процессам сразу** (мастер + воркеры), а не по
одному воркеру.

### 7.1. Однородная нагрузка (`/`)

Здесь режим обязан проигрывать. Задача — измерить цену, а не победить.

- Зафиксировать дельту мкс CPU/запрос против `SO_REUSEPORT`
- **Порог:** дельта не хуже +40 мкс. Больше — протокол требует пересмотра
  до этапа 7

### 7.2. Разнородная нагрузка — главный тест

Профиль: 90% запросов ~0.5 мс, 10% ~50 мс, keep-alive включён.

- **p99 должен улучшиться минимум в 2 раза** против `SO_REUSEPORT`
- p50 не хуже +20%
- Если p99 не улучшился, режим не нужен — закрыть работу, оставить
  `SO_REUSEPORT`

### 7.3. Насыщение

- При нагрузке выше ёмкости — `503` вместо роста латентности
- RSS мастера при полной очереди ограничен и предсказуем
- Ни одного зависшего `requestId` после снятия нагрузки

### 7.4. Отказы

- `kill -9` воркера под нагрузкой: GET переотправлены, POST → `502`, ни одного
  оборванного клиентского соединения
- Rolling restart всех воркеров: ноль сброшенных соединений

---

## 8. Открытые вопросы

- **Thundering herd не при чём** — у каждого воркера свой сокет, мастер шлёт
  адресно. В отличие от общего слушателя, здесь этой проблемы нет
- **Стриминг тел** (chunked, SSE, WebSocket upgrade) — вне области ТЗ.
  Решить, что делать с апгрейдом: отклонять или отдавать в обход диспетчера
- **`Expect: 100-continue`** — кто отвечает, мастер или воркер
- Нужен ли `dispatch` для не-HTTP воркеров (сокет-сервер) или только HTTP

## 9. Оценка (2026-08-15)

Вывод: в текущем виде делать не стоит. Цена почти наверняка превышает
собственный порог из 7.1, а главный заявленный выигрыш держится на посылке,
которая для конкурентного воркера неверна. Ниже — по статьям.

### 9.1. Цена: порог +40 мкс недостижим

База из `cpu-per-request-attribution.md` после hot-path-работы: `/` стоит
138.7 мкс CPU/запрос при 86.7k rps на 12 воркерах. Разложение оттуда же:

| Статья | мкс |
| --- | ---: |
| Go-сервер (пол L0) | ~19 |
| Граница PHP↔Go (L1−L0) | ~69 |
| Fiber | ~27 |
| Обвязка PHP | ~76 |

Ключевое — что такое эти 69 мкс: передача запроса и ответа между горутинами
внутри одного процесса (msgpack в обе стороны, `chansend`, park/wake двух
потоков). Диспетчеризация добавляет обмен той же природы, но межпроцессный:
те же две сериализации, плюс системные вызовы, плюс пробуждения через
futex/epoll между процессами. Это дороже внутрипроцессного хендоффа, а не
дешевле.

Эмпирическое подтверждение уже измерено в проекте: RoadRunner — это и есть
архитектура настоящего ТЗ (Go-прокси терминирует HTTP и гонит запрос воркеру
через сокет со своим кадрированием). Его цена на пустой ручке — ~225
мкс/запрос, при том что воркер там не держит ни шедулера, ни файберов, а пол
его Go-прокси тот же ~19 мкс.

Оценка добавки: +80…150 мкс, то есть 220–290 мкс/запрос и ~41–55k rps вместо
86.7k (−35…−52%). Порог 7.1 (+40 мкс) — это уже −22%, и он выглядит
оптимистичным в два-три раза. Отдельно: мастер при 87k rps съедает около
четырёх ядер из двенадцати — у тех же воркеров.

### 9.2. Выигрыш: посылка про HOL-блокировку не работает

Раздел 1 утверждает, что один медленный запрос задерживает последующие на той
же connection. Это верно, но это свойство HTTP/1.1, а не `SO_REUSEPORT`: без
пайплайнинга клиент не отправит запрос N+1, пока не получит ответ на N. HTTP/2
сервер не поддерживает (`net/http` без TLS — только 1.1). Диспетчеризация
здесь не меняет ничего; она меняет только то, какой воркер выполнит следующий
запрос.

Профиль 90/10 из 7.2 распадается на два разных случая, и ТЗ их смешивает:

- Тяжёлые 50 мс — это ожидание (БД, сеть). Файбер паркуется, воркер продолжает
  обслуживать дешёвые запросы; блокировки нет, выигрывать нечему. Хуже того,
  least-in-flight здесь вредит: счётчик считает запросы, а не потребление
  (оговорка в 4.1), и припаркованные файберы делают простаивающий воркер
  «загруженным».
- Тяжёлые 50 мс — это CPU в PHP. Здесь выигрыш реальный: соединения, прибитые
  к занятому воркеру, ждут его единственный тред. Преемпция
  (`preemptionQuantumMs`) ограничивает задержку соседей квантом, но суммарный
  CPU не меняет.

То есть из главного теста ТЗ работает половина.

### 9.3. Этот выигрыш доступен без своего кода

Архитектура из ТЗ — прокси терминирует соединения и раздаёт запросы по
загрузке — это nginx/HAProxy с `least_conn` перед пулом воркеров на разных
портах. Решающее обстоятельство: TLS проект не терминирует и сам отсылает к
nginx/HAProxy, значит обратный прокси в проде почти всегда уже стоит. Свой
диспетчер дублирует его с нуля и навсегда в поддержку.

### 9.4. Что ТЗ недооценивает

- Мастер перестаёт быть чистым супервизором. Сейчас это документированное
  свойство: `pcntl`/`posix`, расширение не грузится. Раздел 5 требует
  Go-рантайм с HTTP — это уже не режим, а второй сервер со своим протоколом,
  backpressure, таймаутами, ретраями и точкой отказа.
- Стриминг вынесен «вне области ТЗ», но это несущая балка, а не ограничение
  объёма (подробно в 9.5).
- Память. Копия тела в мастере плюс msgpack-копия плюс копия в воркере, при
  `maxRequestBody` 10 МиБ и очереди на 1024 — принципиально другой профиль RSS,
  чем сегодняшний.

### 9.5. Стриминг ответа — отдельная трудность

Сейчас ответ передаётся командами `full` либо `head` → `chunk`* → `end`, и
чанк подтверждается только после того, как Go записал и сфлашил его клиенту;
это и есть write backpressure. Под диспетчеризацией соединение живёт в мастере,
а обработчик — в воркере, поэтому подтверждение каждого чанка становится
межпроцессным round trip.

- Протокол перестаёт быть плоским: к таблице раздела 3 добавляются
  `RESPONSE_HEAD`/`RESPONSE_CHUNK`/`RESPONSE_END`/`CHUNK_ACK`,
  мультиплексированные по `requestId`, и мастер превращается в набор конечных
  автоматов на запрос.
- Переотправка идемпотентных (4.3) умирает: после `RESPONSE_HEAD` статус уже на
  проводе — ни переотправить, ни отдать `502`, только оборвать соединение.
  Стриминг и главное преимущество режима несовместимы в пределах запроса.
- Мультиплексирование по одному сокету на воркера создаёт настоящую
  HOL-блокировку — ту самую, ради устранения которой всё затевается: крупный
  чанк держит за собой `RESPONSE` быстрого запроса, `CANCEL` и `PING` того же
  воркера. Простой вариант (положиться на TCP-backpressure, перестав читать
  сокет) останавливает весь мультиплекс, то есть один медленный клиент вешает
  все запросы воркера. Починка — лимит размера кадра и честное чередование по
  `requestId`, то есть ручная реализация flow control из HTTP/2.
- Тело запроса — та же задача в зеркале: least-in-flight выбирает воркера в
  момент запроса, значит мастер обязан вычитать тело целиком до выбора. Сегодня
  тело не буферизуется — первый чанк едет с запросом, остальное тянется по
  64 КиБ.
- `abandoned` становится консенсусом трёх сторон: клиент отвалился → мастер шлёт
  `CANCEL` → воркер разматывает корутину, но в сокете уже летят чанки для
  `requestId`, который мастер забыл. Критерий «ни одного зависшего `requestId`»
  из 7.3 — ровно про это.

Без стриминга режим не умеет SSE, chunked, отдачу файлов, большие загрузки и
WS-upgrade — всё это сегодня работает и задокументировано. То есть флаг
`--dispatch` молча выключал бы заметную часть функциональности сервера.

### 9.6. Что делать вместо

Порядок в разделе 6 инвертирован: замеры стоят этапом 6, после того как
написаны этапы 1–5. Развернуть — сначала фальсифицирующий эксперимент, он же
самый дешёвый: `dispatch-experiment.md`. Если nginx с `least_conn` не улучшает
p99 на разнородном профиле, свой диспетчер не улучшит тем более, и работу можно
закрывать за один прогон вместо месяцев.

По CPU-bound хвостам честный вектор — уже стоящие в роадмапе `Std`-фича
(json/hash/gzip в Go, снимает непреемптируемые монолиты) и watchdog зависших
воркеров, а не маршрутизация.

### 9.7. Измерено (2026-08-15)

`dispatch-experiment.md` исполнен целиком; полные числа там, в разделе 10.
Кратко по воротам самого ТЗ:

| Посылка ТЗ | Измерено |
| --- | --- |
| Ядро раскладывает неравномерно (раздел 1) | Неверно: разброс `1.13x`, CV 4.9% при 256 соединениях и `1.16x` при 32; тяжёлые запросы легли 266–283 на воркера |
| Раздача по запросу лечит p99 (7.2) | Провалено: 3.15 с → 2.46 с, то есть −22% вместо требуемых −50%, и это зрелым nginx с `least_conn` |
| Цена укладывается в +40 мкс (7.1) | Планка оказалась другой: nginx стоит 0 на пустой ручке (90.3 → 86.1 мкс) и +27 мкс на I/O-профиле |

Три вещи, которых ТЗ не предполагало:

- На CPU-профиле система стоит в потолке (756–806% из 800%). Маршрутизация не
  создаёт ёмкости, а при насыщении хвост — это общая очередь.
- Хвост создаёт преемпция, а не привязка соединений. С
  `--preemptionQuantumMs=0` тот же профиль даёт p99 604 мс против 3.15 с
  (в 5.2 раза лучше) и на 17% меньше CPU, ценой p50 229 мс против 28 мс. Это
  внутрипроцессная политика планировщика и существующая ручка.
- Наивная раздача по запросу — то есть round-robin, механизм из раздела 2 ТЗ
  без учёта загрузки, — хуже ядра: p99 70.5 мс против 38.8 мс на пустой ручке.
  Работает не пораздельность, а выбор по загрузке.

Планка для своего мастера после этого — не «+40 мкс», а «дешевле, чем
бесплатно»: nginx уже даёт выигрыш там, где он есть, за нулевой CPU. Мастер из
ТЗ получил бы ту же экономию на соединениях, но добавил бы msgpack в обе
стороны и копию тела — статей, которых у nginx нет.
