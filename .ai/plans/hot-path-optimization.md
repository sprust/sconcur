# 1. Пул файберов (~20 мкс)

Лучшее соотношение выигрыша к риску во всём списке.

Лестница: L2 − L1 = 27.3 мкс, а чистый цикл `new Fiber` + start + suspend +
resume = 5.37 мкс. **Разница 22 мкс это не файберы, это жизненный цикл их
стеков:** 3.1 minor fault на запрос при первом касании страниц плюс munmap с
TLB-shootdown IPI по ~15 потокам Go-рантайма в процессе.

Ни одна оптимизация внутри файбера этого не уберёт, потому что стоимость лежит в
создании и уничтожении, а не в переключении.

## Идея в одну строку

Файбер завершается, когда его колбэк возвращает управление, и перезапустить его
нельзя. Значит колбэк не должен возвращаться никогда: это вечный цикл, который
паркуется на `Fiber::suspend()`, получает работу через значение `resume()`,
выполняет её и снова паркуется.

## 1.1. Носитель

```php
<?php

declare(strict_types=1);

namespace SConcur\Scheduler;

use Fiber;

final class PooledFiber
{
    /**
     * Sentinel suspend value: the worker loop parked itself, i.e. the previous
     * job finished. Distinguished from a task push by identity, so it must not
     * be a value a payload could ever take.
     */
    public const IDLE = "\0sconcur_idle";

    /**
     * Bumped on every acquire. A result frame carries the generation it was
     * created under; a frame whose generation no longer matches is stale and
     * must not resume the fiber. Replaces the old "spl_object_id was reused"
     * guard, which no longer works when the id is stable by construction.
     */
    public int $generation = 0;

    public function __construct(
        public readonly Fiber $fiber,
        public readonly int $id,
    ) {
    }
}
```

## 1.2. Пул

```php
<?php

declare(strict_types=1);

namespace SConcur\Scheduler;

use Fiber;
use Throwable;

final class FiberPool
{
    /** @var list<PooledFiber> */
    private array $idle = [];

    private int $live = 0;

    public function __construct(
        private readonly int $maxIdle = 256,
    ) {
    }

    public function acquire(): PooledFiber
    {
        $pooled = array_pop($this->idle);

        if ($pooled === null) {
            $pooled = $this->create();
        }

        ++$pooled->generation;

        return $pooled;
    }

    public function release(PooledFiber $pooled): void
    {
        if (count($this->idle) >= $this->maxIdle) {
            // Over the cap: let the loop return so the fiber and its stack die.
            $pooled->fiber->resume(null);
            --$this->live;

            return;
        }

        $this->idle[] = $pooled;
    }

    public function stats(): array
    {
        return ['idle' => count($this->idle), 'live' => $this->live];
    }

    private function create(): PooledFiber
    {
        $fiber = new Fiber(static function (): void {
            while (true) {
                /** @var \Closure|null $job */
                $job = Fiber::suspend(PooledFiber::IDLE);

                if ($job === null) {
                    return; // eviction
                }

                try {
                    $job();
                } catch (Throwable $e) {
                    // Must not escape: a throw here terminates the fiber and
                    // silently drains the pool. Report and keep looping.
                    ErrorReporter::report($e);
                }
            }
        });

        // Runs to the first suspend. This is where the stack is mapped and its
        // pages are first touched, once per fiber instead of once per request.
        $fiber->start();

        ++$this->live;

        return new PooledFiber(fiber: $fiber, id: spl_object_id($fiber));
    }
}
```

## 1.3. `Scheduler::spawn`

```php
public function spawn(Closure $callback): void
{
    $pooled  = $this->pool->acquire();
    $fiber   = $pooled->fiber;
    $fiberId = $pooled->id;
    $flowKey = 'sp_' . (++$this->spawnCounter);

    State::registerFiberFlow(
        fiberId: $fiberId,
        flow: new CurrentFlow(isAsync: true, key: $flowKey),
    );

    State::registerCoroutineContext(
        fiberId: $fiberId,
        parentFiberId: State::currentContextFiberId(),
    );

    $coroutine             = new Coroutine(
        id: $fiberId,
        fiber: $fiber,
        group: null,
        callbackKey: '',
        flowKey: $flowKey,
    );
    $coroutine->pooled     = $pooled;
    $coroutine->generation = $pooled->generation;

    $this->register($coroutine);

    ++$this->spawnedCount;

    // Hand the job over. No try/catch here any more: the worker loop swallows
    // throws, so this can only fail on scheduler bugs.
    $suspendValue = $fiber->resume($callback);

    if ($suspendValue === PooledFiber::IDLE) {
        $this->finishPooled($coroutine); // fully synchronous handler

        return;
    }

    $this->dispatchPendingTask(
        fiber: $fiber,
        fiberId: $fiberId,
        suspendValue: $suspendValue,
    );
}
```

## 1.4. Завершение вместо `isTerminated()`

Пулированный файбер не терминируется никогда, так что все проверки
`$fiber->isTerminated()` в горячем пути заменяются на сравнение с сентинелом.
В месте возобновления (сейчас около `Scheduler.php:949`):

```php
$suspendValue = $coroutine->fiber->resume($resumeValue);

if ($suspendValue === PooledFiber::IDLE) {
    $this->finishPooled($coroutine);

    return;
}

$this->dispatchPendingTask(
    fiber: $coroutine->fiber,
    fiberId: $coroutine->id,
    suspendValue: $suspendValue,
);
```

```php
private function finishPooled(Coroutine $coroutine): void
{
    $this->forget($coroutine); // existing: stopFlow when flowUsed, registry purge

    State::purgeCoroutineContext($coroutine->id);

    $coroutine->awaitedFlowKey = '';
    $coroutine->awaitedTaskKey = '';
    $coroutine->flowUsed       = false;

    $this->pool->release($coroutine->pooled);
}
```

## 1.5. Что сломается, если сделать неаккуратно

### Главное: `spl_object_id` перестаёт быть поколением

В `Coroutine` записано: `spl_object_id` переиспользуется после освобождения
файбера, поэтому устаревший результат с чужим `ownerFiberId` не должен
возобновить корутину не в свою очередь. Сейчас это редкий случай. **С пулом id
стабилен по построению, то есть коллизия становится не редкой, а гарантированной
на каждом запросе.**

Коммит `route results by a frame-carried owner id` маршрутизирует именно по id,
и этого больше недостаточно. Нужно одно из двух:

- нести в кадре пару `(ownerFiberId, generation)` и сверять оба
- либо маршрутизировать по `flowKey`, который и так уникален на задание

Без этого поздний результат запроса N разбудит запрос N+1 на том же файбере, и
проверка пройдёт. Это самый дорогой из возможных багов здесь: воспроизводится
только под нагрузкой и выглядит как перепутанные ответы. **Закладывать до первой
строки пула.**

### Остальное

- **Утечка состояния между запросами.** `State::registerFiberFlow` и
  `registerCoroutineContext` ключуются по `fiberId`. Регистрировать заново на
  каждое задание и обязательно чистить в `finishPooled`, иначе контекст запроса
  N виден запросу N+1
- **Исключения.** Ловятся внутри цикла. Любой throw, вышедший наружу, убивает
  файбер, и пул тихо пустеет под нагрузкой, деградируя в текущее поведение
- **Вложенный `spawn`.** Задание может само вызвать `spawn`; пул обязан отдать
  другой файбер, а при исчерпании создать новый, а не блокироваться
- **RSS.** `maxIdle` стеков живут постоянно. Сейчас 217 MiB на 12 воркеров;
  начинать с `maxIdle` = `maxConcurrency` и следить за пиком в телеметрии
- **`fiber.stack_size`.** Если пул почему-то не взлетит, меньший стек снижает
  число страниц на первое касание

## 1.6. Как померить

```bash
# до и после, ступень L2 лестницы
SERVER_ARGS='--ladder=l2' tests/benchmarks/http/load-stats.sh

# прямое подтверждение, что ушла именно mm-статья

```

Ожидание: minor faults на запрос падают с ~3.1 почти до нуля, L2 − L1 сжимается
с 27.3 до ~5–7 мкс. **Если minor faults остались, чёрн идёт не от стеков
файберов, а от чанков Zend MM, и пул не поможет** — тогда возвращаться к
разделению этих двух статей.

# 2. Аллокации на запрос в Go (~15–20 мкс)

Профиль `allocs` из фазы 3 уже назвал все точки. Статья «GC + аллокатор
~23 мкс» из фазы 2 состоит из них.

| Точка | Действие |
| --- | --- |
| `time.NewTimer` в `consumeCommands` на запрос | таймер из `sync.Pool` с `Reset`, либо один грубый sweeper на воркер вместо таймера на запрос |
| `context.WithCancel` ×2 (`flows.HandleMessage`/`tasks.NewTask` + http-слой) | в горячем пути не создавать context: структура с переиспользуемым done-каналом, либо один context на соединение |
| `formatAccessLine` (Sprintf) | проверять уровень логирования **до** форматирования; при выключенном access-логе не вызывать вовсе |
| `readMIMEHeader` | переиспользуемый `textproto.Reader`, буфер заголовков из пула |

Первые три это правки на десятки строк каждая. `time.NewTimer` на 63k rps это
63 000 таймеров в секунду на воркер, каждый со своей записью в куче таймеров
рантайма, и это же объясняет часть статьи «Go: runtime прочее».

**Замер:** ступень L1 до и после, плюс `alloc_objects` на запрос через pprof.

# 3. Ленивый PSR-7 (~25–35 мкс)

Самая крупная статья (обвязка L3 − L2 = 76 мкс), но и наименее изученная.

**Сначала измерение, потом код.** В профиле фазы 2 записано: PHP-бинарь в образе
стрипнут и собран без frame pointers, поэтому колл-графы PHP-стороны не
читаются. Пока это не исправлено, 76 мкс это чёрный ящик и любая оптимизация в
нём угадывание.

```dockerfile
# отдельный образ только для профилирования
CFLAGS="-fno-omit-frame-pointer -g" ./configure --enable-debug-assertions ...
```

Гипотеза, которую проверять первой: на каждый запрос строится полный
`ServerRequest` (декод заголовков, парс query, объекты nyholm), тогда как
типовой обработчик трогает путь и метод. Ленивый объект, декодирующий заголовки
и query при первом обращении, срезает это для большинства ручек.

Вторая гипотеза: бухгалтерия `Scheduler` (spawn, `State`,
`dispatchPendingTask`). После профиля с символами будет видно распределение.

# 4. Копии строк на границе (~3–5 мкс)

> **Сделано 2026-08-12** в безопасном объёме: view-ключи для lookup-only
> вызовов (`wait`, `stopFlow`), интернирование метода из фиксированного набора
> енумов (`types.InternMethod`) — сообщение хранит каноническую константу, а не
> копию на пуш. Ступень L1 на одном воркере +4.6% (37.9k → 39.7k rps); полный
> `/` в пределах шума — на проде один пуш на запрос, и ~0.5 мкс не видны на
> фоне 91. Остальные копии (`payload`, `taskKey`, `flowKey` в сообщении)
> уезжают в горутину задачи — им копия обязательна, пункт закрыт.

`GoString`/`GoStringN` в профиле аллокаций: копия на каждом cgo-переходе.
PHP-поток заблокирован на время вызова, значит буфер жив и его можно читать без
копии:

```go
b := unsafe.Slice((*byte)(unsafe.Pointer(p)), n)
```

**Строго при условии**, что результат не переживает вызов и не уезжает в
горутину. Если уезжает, копия обязательна, и тогда это не оптимизируется.

# 5. Ручной кодек вместо msgpack (~4 мкс)

Делать после 1–3, и только для фич с объёмными результатами (`RowsResult`,
`WsServer`), где msgpack стоит O(n). На пустом запросе потолок 5–8 мкс.

Первым шагом замер, а не код: стоимость pack/unpack как функция размера payload
(1 / 100 / 10 000 строк) и split между разбором и построением массива. Если
доминирует построение, правильный ход другой: ленивая построчная выдача вместо
материализации массива.

## 5.1. Ручной кодек ответного события (симметрия abb2c56)

Коммит `abb2c56` кодирует событие запроса (Go → PHP) вручную, но обратный путь
остался на msgpack: `RespondPayload` пакуется `MessagePackTransport::pack` на
каждый запрос (плюс распаковка в Go). После пула это часть главной статьи
L1 − L0 ≈ 85 мкс. Сделать зеркально: фиксированный бинарный конверт для
respond-события, PHP собирает его конкатенацией/`pack()`, Go разбирает без
msgpack. Замерять на ступени L1 (она содержит оба кодека и ничего лишнего).

# 8. Путь B: maps-чёрн cgo-вызовов со стеков файберов (найден и срезан 2026-08-12)

Гипотеза park/wake для `/all` **закрыта — не подтвердилась**. CPU-профиль
воркера под `/all` (tmpfs-бэкенды, база 4 024 rps при ~1 017% CPU ≈ 2 527
мкс/запрос): futex-слой (`Syscall6`) всего 4.3%, зато **65% CPU — внутри libc**,
из них 35.6% всего CPU в `__read_nocancel` + паттерн
`open/getdelim/vfscanf/strtoull`. strace показал источник: главный PHP-тред
читает `/proc/self/maps` (~45 КиБ на чтение) **четыре раза на каждый запрос**
(~78 тыс. read()/с на воркер).

Механизм: cgo-вызов, входящий в Go со стеком-указателем внутри файберного
стека, заставляет рантайм пересчитать границы системного стека
(`callbackUpdateSystemStack` → `x_cgo_getstackbound` → `pthread_getattr_np`), а
для главного треда процесса glibc отвечает на это полным чтением и парсингом
`/proc/self/maps`. Четыре вызова на `/all`-запрос: три пуша членов `WaitGroup`
(`launch` диспатчит на стеке корутины-родителя — тоже файбер) и один `stopFlow`
при сносе группы (`iterate()` finally). Это же объясняет патологию `l2f`
(432 мкс): пуш со стека файбера = maps-чтение на каждый, и maps растёт с числом
живых файберов — квадратичная деградация фан-аута получает механизм.

Срез: `dispatchPendingTask` при `Fiber::getCurrent() !== null` не делает cgo, а
ставит диспатч в очередь `pendingDispatches`; `State::deleteFlow` изнутри
файбера откладывает stopFlow в `pendingStopFlows`. Обе очереди дренируются в
`takeReadyResult` на главном C-стеке до любого блокирующего wait. Семантика не
меняется (результат не может прийти раньше пуша), меняется только стек
cgo-перехода. Пробник: 401 maps-чтение на 100 спаун+WaitGroup итераций → 1.

Замер `/all` после среза (tmpfs-бэкенды, 12 воркеров, wrk 4×256, 20 с,
медианы трёх прогонов, одна сессия):

| Метрика | До | После | Дельта |
| --- | ---: | ---: | ---: |
| rps | 4 024 | 6 407 | **+59%** |
| CPU `php` avg | ~1 017% | ~721% | −29% |
| мкс CPU/запрос | 2 527 | 1 125 | **−55%** |
| maps-чтений на запрос | 4 (~180 КиБ) | 0 | — |

`/` (пустая ручка) без регрессии: 132.4k rps при ~1 217% (её пуши и так шли с
главного стека). Узкое место `/all` сместилось к бэкендам (mysql ~289%, mongodb
~214% CPU при php ~721% из 1 200 доступных).

Перезамер на дисковых бэкендах (методология доков, `make bench-reset`,
2026-08-12): 2 667 → ≈3 010 rps (**+13%**), CPU ~730% → ~563%, p50 87 → 76 мс —
упор в fsync съедает большую часть CPU-выигрыша, но и rps, и цена запроса
улучшились. Свежие дисковые тома прогреваются: первые 2 прогона после
bench-reset занижены (2.2–2.5k), медиана берётся по стабильному окну. Доки
(benchmarks, positioning, load-testing) обновлены.
