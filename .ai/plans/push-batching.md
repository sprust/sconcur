# Батчинг пушей (pushBatch) — проверено, отклонено

Статус: закрыто по результатам замеров (2026-08-02). Код отброшен, в ветку не
вошёл. Заметка — чтобы к идее не возвращаться вслепую.

## Гипотеза

Зеркало `waitAnyBatch` для обратной стороны: планировщик не пушит pending-задачу
сразу в `dispatchPendingTask`, а копит очередь (по fiberId) и перед каждым
cgo-ожиданием (`takeReadyResult`, вход в `run()`) сбрасывает её одним переходом
`pushBatch`. Ожидание: веер из N `add()` и responds разобранного батча
результатов стоят один переход вместо N.

## Что было реализовано (и работало)

- Мультифрейм PHP → Go: `[count u16]`, на задачу заголовок 10 байт
  (`flags u8 (bit0 isNext)` + `methodLen u8` + `payloadLen u32` +
  `flowKeyLen u16` + `taskKeyLen u16`) + method, flowKey, taskKey, payload —
  зеркало формата результата `buildResultFrame`.
- Go `Handler.PushBatch`: валидация всех методов до регистрации — ошибка батча
  атомарна (ничего не запушено), PHP мог безопасно передиспатчить поштучно.
- Scheduler: очередь pending-задач, сброс перед ожиданиями, очередь размером 1 —
  старым одиночным `push`, чистка записей в `detach`/`forget` (переиспользование
  spl_object_id), поштучный фолбэк при ошибке батча.
- Всё зелёное: сборка, Go-тесты, 442 PHPUnit, PHPStan, cs-fixer.

## Почему не работает

- Сам переход дёшев (~1–3 мкс: cgo + копии аргументов + бухгалтерия под
  фактически неконтендящимися мьютексами — их берёт только PHP-поток). Это <2%
  цены запроса даже на самой дешёвой ручке, экономия N−1 переходов не видна.
- Отложенный пуш ломает конвейер. При немедленном пуше выполнение задачи в Go
  перекрывается с добавлением остальных корутин и с разбором результатов: старты
  в разбежку → результаты в разбежку. С батчем фазы выстраиваются
  последовательно («добавили все → выполнились все → разобрали все»), и ровный
  веер платит сверху до одной длительности операции — на 64 × 1 мс это ровно
  лишняя миллисекунда (+40%). Async-колонки `make bench-*` (веера одинаковых
  операций) просели бы так же.
- Это фундаментально, а не вопрос донастройки: батчинг требует отложки, отложка
  и есть цена. Гибрид «батчить только resume-сторону» не оправдан — серверные
  ручки выигрыша не показали вовсе.

Вывод тот же, что и в [park-wake-coordination.ru.md](park-wake-coordination.ru.md)
с другой стороны: дорогая часть координации — park/wake ожиданий, а не переходы.
Батчить стоит ожидание результатов (`waitAnyBatch` — уже сделано), пуши — нет.

## Что оставлено

Единственная микрооптимизация из этой работы: успешные `push`/`next` возвращают
из Go `NULL` вместо `C.CString("")` — минус malloc/free на каждый пуш (C-глю
трактует `NULL` как пустую строку через интернированный `RETURN_EMPTY_STRING`).
Семантика для PHP не изменилась.
