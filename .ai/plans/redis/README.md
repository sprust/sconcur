## Цель

`Redis` — фича верхнего уровня со своим `MethodEnum`, по образцу `Sql` и `Amqp`.
Команда уезжает в расширение, вызывающая корутина подвешивается, PHP-поток
свободен. Тридцать `GET` из тридцати корутин уходят в один сокет пайплайном и
возвращаются за время одного round trip, а не тридцати — это и есть то, чего
нельзя получить от phpredis, где каждый вызов блокирует процесс.

Вне `WaitGroup` тот же API работает синхронно (общее правило фич).

## Не-цели

- Не эмулировать phpredis. Нет `OPT_PREFIX`, нет `OPT_SERIALIZER`, нет
  автосжатия — всё это молчаливая магия над ключами и значениями, которая
  ломается ровно тогда, когда данные читает кто-то другой. Значения — байты,
  сериализует их вызывающий.
- Не покрывать все ~250 команд типизированными методами. Типизированный метод
  есть там, где он формирует ответ (`HGETALL` → ассоциативный массив) или где
  порядок аргументов легко перепутать; остальное — через `command()`.
- Не делать кластер и sentinel в v1 (см. «Отложено»).

## Зафиксированные решения

1. Драйвер — `redis-rs`. Обоснование и альтернатива (`fred`) — в
   [rust-core.md](rust-core.md#драйвер).
2. Соединение адресуется DSN в каждом сообщении, как в `Sql`, а не хендлом, как
   в `Amqp`. Цена и условие пересмотра — [protocol.md](protocol.md#dsn-в-каждом-сообщении).
3. Обычные команды идут по мультиплексированному соединению (много команд в
   одном сокете, пайплайном). Блокирующие (`BLPOP`, `XREAD BLOCK`, `WAIT`, …) —
   по отдельному соединению, иначе одна `BLPOP` останавливает обслуживание всех
   соседних команд: Redis обрабатывает команды одного соединения строго
   последовательно.
4. Команды, меняющие состояние соединения (`SUBSCRIBE`, `MULTI`, `WATCH`,
   `SELECT`, `AUTH`, `RESET`, `MONITOR`), на общем соединении отклоняются с
   исключением, называющим замену. Это повторяет решение AMQP: отказать вслух
   лучше, чем тихо испортить соседей по сокету.
5. Аргументы команд — только `string|int|float`. `bool` и `null` отклоняются:
   phpredis превращает `false` в пустую строку, и это источник багов, которые
   видно только в данных.
6. Протокол по умолчанию RESP2. RESP3 включается параметром DSN и меняет форму
   ответов части команд — это задокументировано, а не сглажено.
7. v1 без кластера, sentinel, consumer-групп Streams и телеметрии.

## Состав v1

| Возможность | Механика |
| --- | --- |
| Одиночная команда | `Command`, мультиплексированное соединение |
| Пайплайн | `Pipeline`, один round trip на пачку |
| Транзакция `MULTI`/`EXEC` | тот же `Pipeline` с флагом атомарности |
| Блокирующие команды | `Command` с флагом, выделенное соединение |
| `SCAN`/`HSCAN`/`SSCAN`/`ZSCAN` | стриминговый state, батчи через `next()` |
| Pub/Sub | стриминговый state на выделенном соединении |
| Типизированный фасад | ~50 команд поверх `command()` |

## Отложено

Кластер и sentinel; consumer-группы Streams и супервизируемый воркер-потребитель
(«сервер без сокета», как `Amqp\Consumer\QueueConsumer`); секция телеметрии
(`WorkloadProvider`) для redis; повтор идемпотентных команд после обрыва;
клиентское кеширование (RESP3 invalidation push). Конверт команд спроектирован
так, чтобы ничто из этого не потребовало менять его форму.
