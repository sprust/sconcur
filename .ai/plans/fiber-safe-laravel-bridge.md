# Fiber-safe мост к Laravel: пакет `sconcur-laravel`

Адресат: разработчик интеграции `sconcur-laravel` — отдельного composer-пакета,
которого в этом репозитории нет и быть не должно. Парный документ со стороны
библиотеки — [sconcur-coroutine-context.ru.md](sconcur-coroutine-context.ru.md):
он реализует примитив контекста и явно откладывает сюда всё, что касается
контейнера, фасадов и per-request состояния фреймворка.

Статус: **план**, кода нет.

## 1. Цель

Дать возможность запускать код Laravel внутри корутин SConcur так, чтобы две
корутины, работающие конкурентно в одном процессе, не видели состояния друг друга.

Ведущий сценарий, из которого вырос этот план, — консьюмер очереди на фиче
[amqp](../../docs/amqp.md): один процесс тянет несколько очередей сразу, вместо
`queue:work`, который занят одной джобой за раз (§8).

Не-цель: сделать конкурентным произвольное приложение. Мост даёт безопасность,
а не ускорение; что именно ускорится — §7.

## 2. Что ломается: статика процесса

Laravel держит корневые ссылки в статических свойствах, то есть на уровне процесса:

| Что | Где |
| --- | --- |
| контейнер приложения | `Illuminate\Container\Container::$instance` (`protected static`), читается через `Container::getInstance()` и `app()` |
| приложение для фасадов | `Illuminate\Support\Facades\Facade::$app` (`protected static`) |
| кеш разрешённых фасадов | `Illuminate\Support\Facades\Facade::$resolvedInstance` (`protected static`) |

Пока запрос в процессе один, это работает. В модели SConcur каждый запрос (или
джоба) исполняется в своей корутине, и планировщик переключает их на каждом
async-вызове — значит любое per-request значение, положенное в контейнер как
синглтон, будет перетёрто соседней корутиной ровно в тот момент, когда та проснётся.

Ошибка при этом тихая: не падение, а джоба, отработавшая от имени чужого
пользователя.

## 3. Что библиотека уже даёт

Строить заново не нужно ничего из перечисленного — всё реализовано и
задокументировано в [docs/coroutine-context.md](../../docs/coroutine-context.md).

- `SConcur\Context\Context::current()` — key-value хранилище, привязанное к текущей
  корутине по `Fiber::getCurrent()`. Вне фибера возвращает корневой контекст
  процесса, поэтому bootstrap-код работает как обычно.
- Наследование: чтение идёт вверх по цепочке родителей (свой map → родитель → корень),
  запись всегда локальная. Родитель фиксируется при создании корутины —
  `Scheduler::spawn` или `WaitGroup::add`.
- Освобождение: `State::unRegisterFiber` снимает map вместе с корутиной.

Отдельно проверено, потому что от этого зависит, нужен ли мосту свой сброс:
**переиспользование фибера из `Scheduler/FiberPool` контекст не протекает.**
Завершение пулового spawn-а идёт `Scheduler::forget()` → `State::deleteFlow()` →
`unRegisterFiber()`, и только потом `FiberPool::release()`. Идентификатор корутины —
`spl_object_id` фибера, то есть после переиспользования тот же, но map к этому
моменту уже снят, а `State::registerCoroutineContext` заново проставляет родителя.
Своего сброса между джобами мосту заводить не надо.

## 4. Отвергнутый путь: Octane-своп

Напрашивается перенести подход Octane: держать `clone $app` на запрос и свопать
`Container::setInstance()` / `Facade::setFacadeApplication()` при входе в запрос.

В фиберной модели это означало бы своп на каждый resume корутины, то есть хуки
вокруг возобновления. [sconcur-coroutine-context.ru.md](sconcur-coroutine-context.ru.md) (§3)
такие хуки отвергает по существу: в модели с контекстом они не нужны, потому что код
читает контекст по текущему фиберу в момент обращения, а не в момент переключения.

Своп на resume к тому же хрупок: любой путь, который резюмит корутину мимо хука
(а планировщик — единственное место, где это происходит, и оно в библиотеке, не в
мосте), оставляет процесс с чужим контейнером. Клонирование `Application` на джобу —
ещё и дорого, а в модели «одна корутина на консьюмера, живущая часами» бессмысленно.

## 5. Архитектура: один Application, per-coroutine значения

Контейнер остаётся **один на процесс**, поднимается один раз при старте воркера и
разделяется всеми корутинами. Меняется не он, а то, как разрешаются те немногие
сервисы, которые действительно относятся к одному запросу.

Правило: **сервис, у которого есть per-request состояние, не биндится как синглтон
со значением — он биндится как резолвер, читающий значение из контекста корутины.**

```php
// вместо $app->instance('request', $request)

$app->bind('request', static function () {
    return Context::current()->find('sconcur.request');
});
```

Значение кладёт тот, кто открывает корутину:

```php
Scheduler::get()->spawn(static function () use ($request) {
    Context::current()->set('sconcur.request', $request);

    // отсюда и глубже app('request') и Request::user() видят своё
});
```

Так `Container::$instance` и `Facade::$app` остаются неизменными на всё время жизни
процесса — их вообще не надо трогать, — а расходится только то, что обязано.

Ключи контекста мост объявляет своими константами с префиксом `sconcur.`, чтобы
не столкнуться с ключами приложения.

## 6. Что надо сделать coroutine-aware

Список закрытый и короткий; всё, чего в нём нет, разделяется между корутинами как есть.

| Что | Почему | Как |
| --- | --- | --- |
| текущий HTTP-запрос | своё у каждого запроса | резолвер `request` поверх контекста (§5); для консьюмера очереди не нужен |
| аутентифицированный пользователь | `AuthManager` кеширует пользователя на guard-е, guard живёт в контейнере | guard, читающий пользователя из контекста |
| локаль | `Application::setLocale()` пишет в конфиг процесса | ставить и снимать вокруг джобы, значение — в контексте |
| соединение с БД | §7, отдельный разговор | §7 |
| контекст логов | иначе строки джоб перемешаются без признака | биндить `Log`-контекст из контекста корутины |

Явно **не** трогаем: конфиг, роутер, скомпилированные вью, кеши вроде
`Str`-мемоизации, сам `Container::$instance`, `Facade::$app`.

## 7. База данных — главный вопрос, и он не решается мостом

`Illuminate\Database\DatabaseManager::connection()` отдаёт разделяемый объект
`Connection` с живым PDO-хендлом и счётчиком уровня транзакции. Две корутины,
чередующиеся на одном PDO, ломают транзакции: `BEGIN` одной попадёт внутрь
транзакции другой.

Здесь надо честно понимать вот что: **PDO блокирующий, и переключение корутин на нём
не происходит.** Пока джоба ждёт ответа от MySQL через Eloquent, весь PHP-поток стоит —
никакая другая корутина в это время не работает. Фичи `Features/Sql/Connection`
(и `Features/Mysql`, `Features/Pgsql`) — собственные классы, а не PDO-драйверы, так
что Eloquent поверх них не поедет без отдельной работы.

Отсюда два следствия:

- **Безопасность.** Раз на PDO переключений нет, запрос Eloquent атомарен
  относительно других корутин: они не могут вклиниться в середину. Опасны только
  транзакции, охватывающие async-вызов между запросами. Минимальное правило v1 —
  запретить `await` внутри транзакции Eloquent (проверять в мосте и падать явно),
  а не выдавать соединение на корутину.
- **Выигрыш.** Джоба, которая почти всё время ждёт БД через Eloquent, от корутин
  не ускорится вообще. Ускоряются джобы, ждущие на SConcur-фичах: HTTP-клиент,
  AMQP, Mongo, `Features/Sql`. Это надо сказать в README пакета первым абзацем,
  иначе интеграцию попробуют на типичной БД-очереди и справедливо разочаруются.

Перевод Eloquent на `Features/Sql` — отдельный план, не этот.

## 8. Ведущий сценарий: консьюмер очереди

Модель очереди Laravel делится надвое, и половины ведут себя по-разному.

### 8.1. Продюсер: обычный драйвер, работает целиком

`push`, `pushRaw`, `later` и `bulk` из `Illuminate\Contracts\Queue\Queue` ложатся на
`basic.publish` один в один. Никакой специфики корутин на этой стороне нет: публикация
не ждёт ответа брокера, ждать нечего и параллелить нечего. Пакет отдаёт обычную пару
`ConnectorInterface` + `Queue`, и `dispatch(new SomeJob())` из CLI-процесса, где
расширение загружено, работает штатно.

Важное следствие, снимающее главное ограничение: **продюсеру SConcur не нужен вообще.**
В очереди лежит обычное AMQP-сообщение с payload-ом Laravel. Веб-часть под php-fpm,
куда расширение не поставить, публикует чем угодно — `vladimir-yuldashev/laravel-queue-rabbitmq`,
`php-amqplib`, `ext-amqp`, — а консьюмер на SConcur читает ту же очередь. Транспорт
общий, формат общий. Драйвер в пакете нужен не для совместимости, а для удобства тех
процессов, где расширение и так загружено.

Что решить на этой стороне: `later()` (отложенные джобы) в AMQP штатно не выражается —
нужен либо плагин `rabbitmq_delayed_message_exchange`, либо per-message TTL плюс DLX.
Выбор влияет на требования к брокеру, поэтому он в §10.

`pop()` реализуем честным `basic.get`: он нужен для `queue:size` и делает `queue:work`
рабочим в разработке, просто без выигрыша по конкурентности.

### 8.2. Консьюмер: заменяется цикл воркера

А вот `Illuminate\Queue\Worker::daemon()` не подходит: это строго последовательный
цикл (`getNextJob()` → `pop()` → `runJob()` → `sleep()`), одна джоба за раз, причём
`sleep()` блокирует процесс. Через него SConcur не даёт ничего — консьюмер,
приостанавливающий свою корутину, оказался бы не при делах.

Вместо него — своя команда:

```
php artisan sconcur:queue-work orders invoices emails --coroutines=10
```

По корутине на консьюмера, у каждой свой `AMQPChannel` с `setPrefetchCount(1)`,
`$queue->consume()` читается в той же корутине, что его открыла. Внутри колбэка —
разбор payload-а Laravel и прогон через публичный `Illuminate\Queue\Worker::process()`,
который уже умеет события, `failed_jobs` и release; ack на успехе, nack с requeue на
падении.

Потолки берём из [docs/amqp.md](../../docs/amqp.md) как есть: 256 каналов на
соединение, один сокет на соединение, один PHP-поток на процесс. Масштабирование
процессами — [мастер воркеров](../../docs/worker-master.md), консьюмеру для
супервизии слушающий сокет не нужен.

Совместимость по рантайму проверена и препятствий не даёт:

- `artisan` — это CLI SAPI, чего требует README;
- `Illuminate\Queue\Worker` использует `pcntl_signal`, `pcntl_alarm` и
  `pcntl_async_signals`, но не `pcntl_fork`; `Illuminate\Queue\Listener` порождает
  процессы через Symfony `Process`. Запрещён библиотекой только форк;
- расширение цепляет `zend_interrupt_function`, вызывая предыдущий обработчик
  ([docs/coroutine-switching.md](../../docs/coroutine-switching.md)), поэтому
  pcntl-диспетчеризация сигналов продолжает работать — `SIGALRM`-таймаут джобы и
  `SIGTERM` на остановку выживают.

Чего сценарий **не** даёт: публиковать в очередь из веб-части приложения через
SConcur нельзя — php-fpm исключён по природе расширения. Это не мешает связке
работать, см. §8.1: веб-часть публикует своим драйвером, консьюмер читает ту же
очередь.

## 9. Этапы

1. **Каркас пакета.** По образцу `sparallel-laravel`: composer-пакет, ServiceProvider
   через `extra.laravel.providers`, orchestra/testbench, свой docker и makefile.
2. **Драйвер очереди** (§8.1) — push-сторона плюс `pop()` через `basic.get`. Самая
   простая часть, полезна сама по себе и не зависит от моста.
3. **Мост без HTTP.** Ключи контекста, резолверы §6 кроме `request`, правило §7 про
   транзакции. Этого достаточно для консьюмера.
4. **Команда `sconcur:queue-work`** (§8.2) и тесты на ней: две очереди, медленный
   обработчик на SConcur-фиче, проверка что вторая очередь не ждёт первую.
5. **HTTP-сервер.** Резолвер `request`, guard пользователя, сессия. Самая большая
   часть, и она не нужна для очереди — отсюда порядок.
6. **Eloquent на `Features/Sql`** — если вообще, то отдельным планом.

## 10. Решения, которые нужны от владельца

- Имя и репозиторий пакета: `sconcur/laravel` по аналогии с `sparallel/laravel`?
- Диапазон версий Laravel. `sparallel-laravel` держит `^9 | ^10 | ^11 | ^12`;
  здесь можно взять уже, если не тянуть старые контейнеры.
- Правило §7 про транзакции: падать явно или ограничиться записью в лог?
- Чем реализовать `later()` (§8.1): плагином `rabbitmq_delayed_message_exchange`,
  который надо ставить на брокер, или per-message TTL плюс DLX, который работает на
  голом RabbitMQ, но требует служебной очереди и хуже переживает изменение задержки.
