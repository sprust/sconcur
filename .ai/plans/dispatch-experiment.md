# Замер: нужна ли диспетчеризация запросов

> **Статус: выполнено (2026-08-15), см. раздел 10.** Фальсифицирующий
> эксперимент перед `dispatch-master.ru.md`. Цель — проверить посылки того ТЗ
> чужими руками, не написав ни строки диспетчера. Итог: перекоса нет, ворота
> p99 провалены, а настоящая причина хвоста оказалась другой.

## 1. Что проверяем

ТЗ `dispatch-master.ru.md` стоит на трёх непроверенных посылках:

1. ядро раскладывает соединения по воркерам неравномерно, и это видно на p99;
2. пораздельная раздача запросов этот перекос лечит;
3. цена такой раздачи укладывается в +40 мкс CPU на запрос.

Все три проверяются существующими инструментами. Первая — access-логом
воркеров, вторая и третья — nginx перед пулом: это ровно архитектура из ТЗ
(прокси терминирует соединения и раздаёт запросы по загрузке), только уже
написанная.

Отдельно проверяем разделение, которого в ТЗ нет: разнородность бывает по
ожиданию и по счёту, и для конкурентного воркера это два разных мира.

## 2. Ворота решения

| Исход | Вывод |
| --- | --- |
| Перекоса по воркерам нет | Закрыть `dispatch-master.ru.md`, посылка 1 неверна |
| `least_conn` не улучшил p99 | Закрыть: если не помогает готовый диспетчер, свой не поможет |
| Цена nginx-хопа > +40 мкс | Ворота 7.1 ТЗ недостижимы: nginx — нижняя граница цены |
| p99 лучше вдвое при приемлемой цене | Оформить схему в `docs/http-server.md`; своё писать только если цена nginx неприемлема |

Цена nginx-хопа — именно нижняя граница цены своего мастера, а не оценка:
nginx на C, без msgpack, без копирования тела в PHP-структуры, без park/wake
PHP-треда. Мастер из ТЗ делает всё то же плюс две сериализации и межпроцессные
пробуждения.

## 3. Эксперимент 0 — есть ли перекос

Без nginx, один прогон. `http-load-stats.sh` отправляет stdout воркеров в
`/dev/null`, а там лежит access-лог по строке на запрос с временем обработки.
Направить каждый воркер в свой файл и после прогона посчитать:

- число запросов на воркера — равномерность раздачи ядром;
- распределение времён внутри каждого воркера — где именно живёт хвост.

Если под разнородным профилем и запросы, и хвосты разложены ровно, посылка 1
неверна и остальные фазы не нужны.

## 4. Стенд

Машина 16 тредов. Геометрия одинакова во всех руках — иначе сравнивается
число воркеров, а не способ раздачи.

| Ядра | Плечо A (`SO_REUSEPORT`) | Плечо B (nginx) |
| --- | --- | --- |
| 0–7 | 8 воркеров, один порт, `reusePort=1` | 8 воркеров, порты 18081..18088, `reusePort=0` |
| 8–11 | простаивают | nginx, 4 `worker_processes` |
| 12–15 | wrk | wrk |

У плеча A четыре ядра отбираются намеренно, чтобы у обоих было ровно восемь
воркеров.

nginx поднимается в сетевом неймспейсе контейнера `php`
(`network_mode: "service:php"`), чтобы до воркеров был loopback, а не
docker-bridge: это ближе к unix-сокету из ТЗ и не завышает цену хопа.
`docker stats` при этом считает его отдельным контейнером, и суммарный CPU
обеих частей остаётся измеримым.

## 5. Профиль нагрузки

Профиль из ТЗ: 90% запросов дешёвых, 10% тяжёлых, keep-alive включён.
Смешивание должно идти внутри одних и тех же соединений, поэтому это Lua-скрипт
для wrk (`request()` выбирает путь), а не два параллельных wrk.

Тяжёлая ручка берётся в двух вариантах — это главное разделение эксперимента:

| Ручка | Природа | Предсказание |
| --- | --- | --- |
| `/msleep/50` | 50 мс асинхронного ожидания | Выигрыша нет; `least_conn` вероятно вредит — припаркованные файберы считаются загрузкой, простаивающий воркер обходится |
| `/cpu/{n}` | sha256-цикл, занимает единственный PHP-тред | Выигрыш по p99 реален: соединения, прибитые к занятому воркеру, ждут его тред |

`n` подбирается разово до ~50 мс на запрос (`curl -w '%{time_total}'` по одному
воркеру).

Дополнительные руки на CPU-профиле, чтобы отделить эффект маршрутизации от уже
существующих механизмов:

- `--preemptionQuantumMs=0` — сколько хвоста съедает автоматическая преемпция
  сама по себе;
- `/cpu-switch/{n}` — верхняя граница идеально кооперативного обработчика.

## 6. Руки сравнения

В upstream обязателен keepalive: без него nginx открывает воркеру новое
TCP-соединение на каждый запрос, и замер перестаёт быть про диспетчеризацию.

```nginx
upstream workers {
    least_conn;                  # переменная эксперимента
    server 127.0.0.1:18081;
    # ... 18082..18088
    keepalive 64;
}

server {
    listen 18080;

    location / {
        proxy_pass http://workers;
        proxy_http_version 1.1;  # по умолчанию 1.0 — upstream keepalive не работает
        proxy_set_header Connection "";
    }
}
```

| Стратегия | Что показывает |
| --- | --- |
| round-robin (дефолт) | Базовая гранулярность ТЗ достигается без least-in-flight: nginx и так раздаёт по запросу, а не по соединению |
| `least_conn` | Прямой аналог least-in-flight из раздела 4.1 ТЗ |
| `random two least_conn` | Power-of-two-choices; под многими воркерами часто ровнее чистого `least_conn` |

`least_time` не берётся — он только в NGINX Plus.

## 7. Метрики

Основная — мкс CPU на запрос по всей системе, как требует раздел 7 ТЗ:

```
мкс/запрос = (CPU_avg_percent * 10000) / rps
```

CPU суммируется по контейнерам `php` и nginx. Рядом — rps, p50/p90/p99, RSS
обоих.

| Фаза | Аналог в ТЗ | Что меряем |
| --- | --- | --- |
| Однородная `/` | 7.1 | Дельта мкс/запрос A→B — цена раздачи по запросу |
| Разнородная, оба варианта тяжёлой ручки | 7.2 | p50/p90/p99 A против B |
| Выше ёмкости | 7.3 | Поведение при насыщении, RSS nginx под очередью |

## 8. Оговорки честности

- Все руки — в одной сессии: межсессионный дрейф по методологии
  `docs/benchmarks.md` доходит до ±20%.
- Проверять `Non-2xx or 3xx responses` в выводе wrk перед тем, как верить
  числу.
- 256 соединений на 8 воркеров — это ~32 на воркера. Эффект хеша резче при
  малом числе соединений, поэтому нужен дополнительный прогон на
  `CONNECTIONS=32`, где перекос максимален.
- На пустой ручке wrk с 4 тредами близок к потолку генератора (фаза 6
  `cpu-per-request-attribution.md`). Если упрётся — поднять `WRK_THREADS`,
  отдав ядра генератору одинаково у обоих плеч.
- nginx считает соединения, а не запросы. При upstream keepalive это близко к
  числу запросов в работе, но не тождественно — расхождение относить на счёт
  инструмента, а не стратегии.

## 9. Что менять в коде

  (`DISTINCT_PORTS=1`: `--address` со сдвигом на индекс, `--reusePort=0`) и

Демо-сервер менять не нужно: `/`, `/msleep/{ms}`, `/cpu/{n}`, `/cpu-switch/{n}`

## 10. Результаты (2026-08-15)

Сессия одна, машина idle, расширение от 2026-08-14. Геометрия во всех руках
одинакова: 8 воркеров на ядрах 0–7, nginx на 8–11 (в плече `SO_REUSEPORT` эти
ядра простаивают), wrk 4 треда на 12–15, 256 соединений, 20 с, `--timeout 10s`.
Тяжёлая ручка откалибрована до ~49 мс: `/cpu/270000` (медиана 49.05 мс на
прогретом одиночном воркере). Все ответы `200`.

Инструменты: `WORKER_LOGS=1`/`DISTINCT_PORTS=1`/`WRK_SCRIPT` в
`tests/benchmarks/http-load-stats.sh`, профиль
`tests/benchmarks/http-mixed-profile.lua`, прокси
`tests/benchmarks/nginx-proxy.sh`.

| Прогон | rps | CPU итого | мкс/запрос | p50 | p90 | p99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `/` `SO_REUSEPORT` | 90 014 | 812.6% | 90.3 | 2.71 мс | 5.97 мс | 38.84 мс |
| `/` nginx round-robin | 90 518 | 804.6% | 88.9 | 2.27 мс | 19.65 мс | 70.48 мс |
| `/` nginx `least_conn` | 94 076 | 809.7% | 86.1 | 2.40 мс | 10.45 мс | 29.28 мс |
| `/` nginx `random two` | 93 614 | 808.3% | 86.3 | 2.03 мс | 9.60 мс | 17.96 мс |
| 90/10 CPU `SO_REUSEPORT` | 1 079 | 806.2% | 7 471 | 28.46 мс | 2.16 с | 3.15 с |
| 90/10 CPU nginx `least_conn` | 1 126 | 758.4% | 6 733 | 31.95 мс | 2.04 с | 2.46 с |
| 90/10 CPU nginx `random two` | 1 101 | 783.7% | 7 120 | 29.05 мс | 2.03 с | 2.54 с |
| 90/10 CPU `SO_REUSEPORT`, преемпция off | 1 052 | 671.0% | 6 381 | 229.04 мс | 383.05 мс | 604.33 мс |
| 90/10 I/O `SO_REUSEPORT` | 48 633 | 384.5% | 79.1 | 7.99 мс | 44.89 мс | 50.96 мс |
| 90/10 I/O nginx `least_conn` | 49 048 | 521.6% | 106.3 | 2.13 мс | 44.96 мс | 50.73 мс |

`CPU_avg% * 10000 / rps`.

### 10.1. Перекоса нет — посылка 1 неверна

Раздача ядром оказалась практически идеальной. На 90/10 CPU при 256
соединениях тяжёлые запросы легли по воркерам как 279 / 269 / 266 / 270 / 269 /
270 / 269 / 283, общий разброс `max/min = 1.13x` (CV 4.9%). Хвосты дешёвых
запросов по воркерам тоже неразличимы: p99 от 31.9 до 35.7 мс.

При 32 соединениях — режиме, где хеш по кортежу максимально грубый, — разброс
не вырос: `1.16x`, CV 5.3%.

nginx ровнее не раскладывает: `least_conn` дал `1.16x`, `random two` — `1.24x`
против `1.13x` у ядра.

### 10.2. Ворота p99 провалены

Главный тест ТЗ (7.2, «p99 должен улучшиться минимум в 2 раза»): 3.15 с →
2.46 с, то есть −22% вместо требуемых −50%. Порог был бы 1.58 с.

Причём это результат зрелого диспетчера: nginx с `least_conn` — ровно та
стратегия, что описана в 4.1 ТЗ, только уже написанная и отлаженная. Свой
мастер лучше не сделает.

Причина видна в CPU: на этом профиле система стоит в потолке (756–806% из
800%). Маршрутизация не создаёт ёмкости — при насыщении хвост это очередь, и
очередь общая независимо от того, кто её раздаёт.

### 10.3. Настоящая причина хвоста — преемпция, а не привязка соединений

Самый содержательный результат сессии. Один и тот же профиль с
`--preemptionQuantumMs=0`:

| | p50 | p90 | p99 | CPU |
| --- | ---: | ---: | ---: | ---: |
| преемпция 5 мс (дефолт) | 28.46 мс | 2.16 с | 3.15 с | 806% |
| преемпция выключена | 229.04 мс | 383.05 мс | 604.33 мс | 671% |

p99 лучше в 5.2 раза, p90 — в 5.6 раза, CPU на 17% меньше. Ценой p50, который
вырос в 8 раз.

Механика: под потоком дешёвых запросов преемпция паркует тяжёлый каждые 5 мс,
и 49 мс работы размазываются на секунды. Дешёвые запросы от этого выигрывают
(p50 28 мс), тяжёлые — платят весь хвост. Без преемпции всё обслуживается
почти FIFO: медиана хуже, хвост ограничен.

То есть хвост, ради которого затевалась диспетчеризация, создаётся политикой
планировщика внутри процесса, а не тем, к какому воркеру прибито соединение.
Это регулируется существующей ручкой `preemptionQuantumMs` и никакой смены
архитектуры не требует. Разумный следующий шаг — снять кривую по кванту
(5 / 20 / 50 / 100 мс) и посмотреть, есть ли точка с приемлемым p50 и
ограниченным хвостом.

### 10.4. Цена раздачи по запросу ≈ 0, но не там, где ожидалось

На пустой ручке nginx не подорожал, а слегка удешевил запрос: 90.3 → 86.1
мкс. Причина не в магии прокси, а в том, что при upstream keepalive воркеры
обслуживают меньше TCP-соединений (пул nginx вместо 256 клиентских), и
экономия на стороне Go покрывает стоимость самого прокси: `php` падает с
812.6% до 686.4%, nginx берёт 123.3%.

На I/O-профиле, где воркеры не насыщены и этой экономии нет, цена проявляется
в чистом виде: 79.1 → 106.3 мкс, то есть **+27 мкс/запрос**.

Для ТЗ отсюда следует главное: планка не «+40 мкс», а «дешевле, чем
бесплатно». Свой мастер получил бы ту же экономию на соединениях, но добавил
бы msgpack в обе стороны и копию тела — статьи, которых у nginx нет вовсе.
Обойти ноль он не может.

### 10.5. Наивная раздача по запросу хуже ядра

На пустой ручке round-robin — то есть буквально «каждый запрос отдельно», без
учёта загрузки, — дал p99 70.48 мс против 38.84 мс у `SO_REUSEPORT`. Помогает
не сама пораздельная раздача, а выбор по загрузке: `least_conn` 29.28 мс,
`random two least_conn` 17.96 мс (в 2.2 раза лучше ядра).

Это единственное место, где ворота 7.2 были бы взяты, — но на однородной
нагрузке, где ТЗ никакого выигрыша и не обещало.

### 10.6. I/O-профиль: улучшать нечего

p99 50.96 → 50.73 мс при длительности самого ожидания 50 мс. Оптимум уже
достигнут, запас равен нулю. Предсказание раздела 5 подтвердилось: для
конкурентного воркера разнородность по ожиданию не создаёт блокировки.

Побочно nginx выровнял очередь: p50 7.99 → 2.13 мс. Это честный плюс, но он
стоит +27 мкс/запрос и к диспетчеризации отношения не имеет — тот же эффект
даёт любой прокси с upstream keepalive.

### 10.7. Оговорки

- wrk — генератор с закрытой петлёй: он держит фиксированное число соединений
  и не моделирует поток с заданной интенсивностью. Под насыщением (90/10 CPU)
  задержка вырождается в «концентрация / пропускная способность», и абсолютные
  p90/p99 там надо читать как меру очереди, а не как задержку в проде.
  Сравнение между руками при одинаковой концентрации остаётся корректным.
- Плечо `SO_REUSEPORT` оставляет 4 ядра простаивать, чтобы число воркеров
  совпадало с плечом nginx. Это делает сравнение честным по воркерам, но
  занижает потолок плеча без прокси по железу.
- Разброс по воркерам считается по access-логу, который асинхронный и роняет
  строки при переполнении буфера. При наблюдавшихся объёмах (тысячи строк на
  воркера) потери не заметны, но метрика не претендует на точный счёт.

### 10.8. Вывод

Все три ворота раздела 2 сработали против ТЗ: перекоса нет, `least_conn` не
дал требуемого p99, а цена оказалась не тем рычагом, каким её считали. При
этом эксперимент нашёл настоящую причину хвоста — политику преемпции — и она
лежит целиком внутри процесса.

Рекомендация: `dispatch-master.ru.md` закрыть. Вместо него:

1. снять кривую `preemptionQuantumMs` на профиле 90/10 CPU и выбрать дефолт
   или задокументировать размен p50 ↔ p99;
2. задокументировать в `docs/http-server.md`, что перед пулом имеет смысл
   ставить прокси с выбором по загрузке (`least_conn`, лучше
   `random two least_conn`), с измеренными числами по пустой ручке;
3. по CPU-bound монолитам — `Std`-фича из роадмапа.
