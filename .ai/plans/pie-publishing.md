# Публикация расширения в PIE

PIE (PHP Installer for Extensions, <https://php.github.io/pie/>) — замена PECL: пакет
расширения лежит на Packagist и ставится командой `pie install vendor/name`. Сам PIE
требует PHP 8.1+, ставить умеет и под более старые.

Цель — установка в две команды вместо «скачай `sconcur.so` из GitHub Releases и
пропиши `extension=` руками»:

```
pie install sconcur/sconcur-ext
composer require sconcur/sconcur
```

Сейчас расширение распространяется одним бинарником: `.github/workflows/release.yml`
прикладывает `ext/build/sconcur.so` к релизу. Установки как таковой нет — ни в
`README.md`, ни в `docs/`.

Всё, что ниже про внутренности PIE, сверено с исходниками ветки `1.4.x`; при
расхождении с поведением на живой установке верить установке, а не этому файлу.

## Решения владельца (зафиксированы)

- Репозиторий: вариант A — `ext/` остаётся в монорепе, зеркало делается сплитом.
- Имя пакета: `sconcur/sconcur-ext`.
- Теги зеркала — без `v`: `0.13.1`.
- Первая поставка — только бинарники, без `config.m4` и без сборки из исходников.
- `ext/build.sh` остаётся быстрым путём разработки.
- `ext-sconcur` в `require` библиотеки не добавляется.
- Локальная ячейка musl — после первой поставки.
- Стартовая матрица — одна ячейка 8.4 / x86_64 / linux / glibc / nts на текущей
  релизной базе; сборочную базу не понижаем, порог GLIBC 2.34 становится обещанием и
  гейтом релиза; `require.php` пакета сужается до `~8.4.0`.

## Что уже сделано

- `68e78e0` — версия модуля больше не захардкожена: `get_module()` берёт её у ядра,
  `php --ri sconcur` показывает настоящую версию. Это предусловие: PIE ставит пакет
  версии X, а расширение отчитывалось «0.2.0».

## Главное: отдаём готовый бинарник, а не сборку

PIE умеет ставить заранее собранные бинарники не только под Windows. При
`download-url-method: pre-packaged-binary` он:

1. берёт релиз по тегу пакета — `GET /repos/{org}/{repo}/releases/tags/{version}`
   (`src/Downloading/GithubPackageReleaseAssets.php`);
2. ищет среди ассетов релиза имя из списка, который строит
   `src/Platform/PrePackagedBinaryAssetName.php`;
3. распаковывает архив и ждёт в его корне файл `{extension-name}.so` — для нас
   `sconcur.so` (`src/Building/UnixBuild.php`, `prePackagedBinary()`);
4. копирует его в `extension_dir`, при необходимости через sudo
   (`src/Installing/UnixInstall.php`).

`phpize`, `./configure` и `make` на этом пути не вызываются вообще. То есть у
пользователя не нужен ни Rust, ни компилятор — ровно то, что уже кладёт в релиз наш
CI, только переименованное и упакованное в zip.

Предупреждение PIE «не используйте `pre-packaged-binary`, если расширение тянет
динамические библиотеки» нас не касается: `ldd ext/build/sconcur.so` показывает только
`libm`, `libgcc_s` и `libc` — rustls, hyper, sqlx, lapin и остальное линкуются
статически внутрь `libsconcur_core.a`.

### Имена ассетов

PIE не парсит имя, а собирает список ожидаемых имён под текущую платформу и сравнивает
строкой, в нижнем регистре. Схема:

```
php_{extension-name}-{version}_php{php-major-minor}-{arch}-{os}-{libc}[-debug][-nts|-zts].{zip|tgz}
```

`{arch}` — `x86`, `x86_64`, `arm64`; `{os}` — `linux`, `darwin`, `windows`, `bsd`,
`solaris`, `unknown`; `{libc}` — `glibc`, `musl`, `bsdlibc`. Для NTS подходят оба
варианта: и с суффиксом `-nts`, и вовсе без суффикса. На Linux дополнительно
проверяется `anylibc` — для бинарника, годного и под glibc, и под musl; нам он не
подходит, `.so` линкуется с конкретной libc.

Для PHP 8.4 / x86_64 / glibc / NTS PIE будет искать, среди прочего:

```
php_sconcur-0.13.1_php8.4-x86_64-linux-glibc-nts.zip
php_sconcur-0.13.1_php8.4-x86_64-linux-glibc.zip
```

Архив содержит один файл — `sconcur.so` в корне. Никаких вложенных каталогов.

### Fallback на сборку — в первой поставке выключен

`download-url-method` — список, и общая рекомендация PIE —
`["pre-packaged-binary", "composer-default"]`: сначала ищется ассет под платформу
пользователя, а если подходящего нет, скачиваются исходники и собираются обычным путём.

Решено начать без второго элемента: первая поставка — `["pre-packaged-binary"]`, без
`config.m4`. Это заметно короче путь до первого релиза, но у него есть прямое
следствие: **платформа вне матрицы не ставится вообще**, PIE отвечает «не нашёл
подходящий ассет». Поэтому матрица и `require.php` пакета обязаны описывать одно и то
же множество — иначе пользователь упрётся в невнятную ошибку там, где Composer мог бы
сказать «ваш PHP не подходит».

`composer-default` и `config.m4` добавляются потом, отдельным шагом.

## Отдельный пакет

`composer.json` несёт ровно один `type`, а корневой уже занят библиотекой
`sconcur/sconcur` (`type: library`). Значит расширение — второй пакет на Packagist со
своим репозиторием.

Выбран вариант A: `ext/` остаётся каноническим местом кода, а на релизе
`git subtree split --prefix=ext` выкладывает его в отдельный read-only репозиторий
`sprust/sconcur-ext` с тем же тегом. Монорепа не рвётся, релиз остаётся одним
действием.

Отвергнутый вариант B — вынести ядро в собственный репозиторий насовсем: честнее для
сборки, но разносит PHP-пакет и ядро по двум историям, и `make check`, который гоняет
тесты против свежесобранного ядра, пришлось бы чинить сабмодулем или локальным путём.

**Релизы с бинарниками должны жить в том репозитории, на который смотрит Packagist.**
PIE спрашивает ассеты у репозитория пакета — то есть у зеркала, а не у основного репо.
Сплит-шаг обязан не только пушить код и тег, но и создавать релиз с ассетами там.

`build-path` из спецификации PIE здесь не помогает: он указывает подкаталог внутри
пакета, но `composer.json` всё равно должен лежать в корне репозитория.

## composer.json расширения

Файл `ext/composer.json` (после сплита — корень зеркала):

```json
{
    "name": "sconcur/sconcur-ext",
    "type": "php-ext",
    "description": "PHP concurrency extension core, written in Rust",
    "license": "MIT",
    "require": { "php": "~8.4.0" },
    "php-ext": {
        "extension-name": "sconcur",
        "priority": 80,
        "support-zts": false,
        "support-nts": true,
        "os-families": ["linux"],
        "download-url-method": ["pre-packaged-binary"]
    }
}
```

- `extension-name` задаётся явно. По умолчанию PIE выводит имя из имени пакета без
  вендора — получилось бы `sconcur-ext`, а дефис в имени расширения недопустим. Это же
  имя попадает и в имя ассета, и в имя искомого `.so` внутри архива.
- `support-zts: false` — ядро рассчитано на единственный PHP-поток: преемпция пишет
  `EG(vm_interrupt)` одного потока, `sconcur_preemption_callback` — глобальный zval
  (`ext/sconcur.c`). ZTS потребует отдельной работы и здесь не обещается.
- `os-families` ограничивает установку. Windows требует своих DLL и отдельного
  пайплайна (`php/php-windows-builder`), macOS — проверенной сборки под darwin. Ни то,
  ни другое пока не заявляется.
- `require.php` сужен до `~8.4.0` (`>=8.4.0 <8.5.0`) — ровно то, на что есть бинарник.
  Библиотека `sconcur/sconcur` свой `^8.4` сохраняет. Подробнее в «Матрица бинарников».
- Поля `"version"` нет: версию даёт git-тег. Пятый источник версии заводить нельзя
  (см. «Extension versioning» в [.ai/README.md](../README.md)).

## Матрица бинарников

`.so` привязана к мажорно-минорной версии PHP (у нас сейчас API 20240924, PHP 8.4),
арке, libc и TS-режиму. Патч-версии PHP ABI не меняют, так что одна сборка покрывает
все 8.4.x. При NTS-only матрица — PHP × арка × libc:

| PHP | arch   | libc  | статус                                      |
|-----|--------|-------|---------------------------------------------|
| 8.4 | x86_64 | glibc | первая поставка, собирается уже сейчас      |
| 8.4 | x86_64 | musl  | после локальной ячейки musl; нужен Alpine   |
| 8.4 | arm64  | glibc | когда появится ARM-раннер                   |
| 8.4 | arm64  | musl  | то же + Alpine                              |
| 8.5 | x86_64 | glibc | вторая ячейка наравне с musl; нужен образ 8.5 |
| 8.5 | …      | …     | остальные комбинации — по мере расширения    |

**Решено: в первую поставку идёт ровно одна ячейка — 8.4 / x86_64 / linux / glibc /
nts**, на текущей релизной базе.

Причина одна и та же для всех остальных ячеек: не выкладывать то, что ни разу не
запускали. musl отложен решением о локальной ячейке, arm64 негде гонять (см. «Проверка
матрицы локально»), 8.5 не проверялся ни одним прогоном — образ проекта прибит к
8.4.15.

Отсюда же решение сузить `require.php` до `~8.4.0`. Без fallback на сборку пользователь на
PHP 8.5 иначе получит «не нашёл подходящий ассет» — при том, что `^8.4` формально
позволяет ему поставить пакет. Узкий констрейнт превращает это в понятное сообщение
Composer о несовместимости платформы и расширяется обратно тем же коммитом, что добавит
8.5-бинарник.

Порядок расширения: musl и 8.5 — вторыми, в любом порядке, затем arm64/glibc.

8.5 поднят с третьего места на второе намеренно. Образы `php:8.4-alpine` популярны, и
musl — самый вероятный первый запрос; но 8.5 вышла давно и успела стать текущей
версией, а поставка без fallback на сборку и с `require.php: ~8.4.0` означает, что
человек на текущей PHP пакет поставить не может вообще. Отставание на минорную версию
PHP — это не отложенная ячейка матрицы, а отсечённая аудитория, и оно растёт само
собой с каждым релизом PHP.

Стоимость ячейки при этом низкая: 8.5 — это другой образ и другой `PHP_API`, но та же
арка, та же libc и тот же способ сборки. Дорогие ячейки — musl (другой аллокатор и
128 КБ стека потока) и arm64 (модель памяти), а не следующая минорная PHP.

### Порог glibc

В имени ассета есть только `glibc`, без версии, так что нижнюю границу надо знать и
писать в доке самим. Считается она не по glibc сборочного образа, а по самой высокой
версии символа, на который бинарник ссылается:

```
$ objdump -T ext/build/sconcur.so | grep -o "GLIBC_[0-9.]*" | sort -uV | tail -1
GLIBC_2.34
```

То есть текущая `.so`, собранная на trixie с glibc 2.41, требует 2.34 и идёт на
Debian 12 (2.36), Ubuntu 22.04 (2.35) и RHEL 9 (2.34). Менять сборочную базу ради них
не нужно.

Не пойдёт она на Debian 11 и Ubuntu 20.04 (обе 2.31). Если такие системы попадают в
обещания, нужна отдельная сборочная база постарше (`php:8.4-cli-bookworm` и ниже) —
основная часть 2.34 приходит на `pthread_*` и `dlopen`, переехавшие в libc именно в
2.34, и на старой базе они отдадут версии ниже.

Решено базу не менять: Debian 11 и Ubuntu 20.04 уже вне обычной поддержки, а понизить
порог позже можно без ломки совместимости — это расширение множества, а не сужение.

Зато проверку потолка нужно сделать гейтом релиза: она детерминированная, занимает
миллисекунды и ловит молчаливое повышение границы после обновления базы или крейтов.
Обещанные 2.34 должны падать в CI, а не у пользователя.

### musl и arm64

- musl: Alpine-образ, Rust-таргет `x86_64-unknown-linux-musl`, PHP-заголовки из
  Alpine. Отдельная сборка, не флажок к текущей.
- arm64: ARM-раннер GitHub или кросс-компиляция Rust плюс кросс-gcc для `sconcur.c`.

Обе ячейки — самостоятельная работа; в первую поставку их можно не брать.

### Имя тега

И тег релиза, и версия внутри имени ассета берутся PIE из одной строки —
`Package::version()`, то есть Composer-овского prettyVersion, а это имя тега как оно
есть. Основной репозиторий тегает `v0.13.1`, и ассет тогда обязан был бы называться
`php_sconcur-v0.13.1_php8.4-...`.

Решено тегать зеркало без `v` — `0.13.1`, — чтобы это соответствие не приходилось
держать в голове. Сплит-шаг, соответственно, перетегивает. Проверить на первом же
релизе.

## Проверка матрицы локально

Гонять ячейки на машине разработчика можно, но полезность у них разная, и городить
полную матрицу локально незачем — стоит делать то, что ловит настоящие различия.

**glibc / x86_64** — это текущий `make check`, отдельная ячейка ему не нужна. Оверлей с
базой `php:8.4-cli-bookworm` по образцу `docker-compose.release.yml` понадобится только
если решим опустить порог ниже 2.34.

**musl / x86_64** — ячейка с самым высоким ожидаемым выхлопом, решено делать её после
первой поставки. Нужен образ на Alpine:
apk-зависимости вместо apt, `pie install` для msgpack/mongodb/amqp/redis (собираются из
исходников), Rust-таргет `x86_64-unknown-linux-musl`. Бэкенды (mysql, postgres, mongo,
rabbit, redis) переиспользуются из `docker-compose.yml` как есть — они по сети.

Делать её стоит не ради галочки: у musl дефолтный стек потока 128 КБ против 8 МБ у
glibc, а ядро поднимает tokio-рантайм и ставит `pthread_atfork`-хендлер, который
пересобирает рантайм после `fork` (`ext/src/core.rs`). Это ровно тот класс различий,
который не виден в коде и ловится только запуском.

**arm64** — локально сейчас недоступен: на машине не зарегистрирован qemu-binfmt и нет
buildx (`docker run --platform linux/arm64 …` падает с `exec format error`). Поднимается
это привилегированной командой и пакетом, но под эмуляцией всё идёт в разы медленнее, а
суита завязана на время — преемпция, таймауты телеметрии, бенчмарки, soak-тесты. Такой
прогон будет флакать не по делу.

При этом arm64 — единственная ячейка с содержательным риском на уровне модели памяти:
`zend_atomic_bool_store` в `ext/sconcur.c`, атомики флагов преемпции, каналы crossbeam.
Отсюда разделение: локально — smoke под эмуляцией (`make ext-build` плюс
`ext/check/core-smoke.php`), полный прогон — на живом ARM-раннере в CI.

### Прогон суиты против самого артефакта

Самая ценная проверка перед релизом не требует матрицы вообще. Харнессы читают
`SCONCUR_EXT` (`makefile:13`), поэтому весь набор тестов можно прогнать против той
`.so`, которая поедет в релиз:

```
make test SCONCUR_EXT=/path/to/unzipped/sconcur.so
```

Разворачивать архив при этом стоит тем же способом, каким это сделает PIE: распаковать и
скопировать `.so` в `extension_dir`. Ничего сверх `cp` он не делает
(`src/Installing/UnixInstall.php`), так что расхождения между «проверили» и «поставилось»
взяться неоткуда.

Рядом — две дешёвые проверки артефакта: потолок GLIBC (см. «Порог glibc») и `ldd`, что не
появилось новых динамических зависимостей помимо `libm`, `libgcc_s`, `libc`.

### Оформление

По оверлею на ячейку, как `docker-compose.release.yml`, и `make check-matrix`, гоняющий
их последовательно. Именно последовательно: контейнеры делят фиксированные имена
(`sc-php`, `sc-mysql`) и опубликованные порты, две ячейки одновременно не поднять без
своего `COMPOSE_PROJECT_NAME` и своих портов.

## config.m4 — отложен

В первую поставку не входит: на бинарном пути он не вызывается вообще. Понадобится
вместе с `composer-default`, то есть когда комбинации вне матрицы должны собираться у
пользователя. Черновик ниже — заготовка на тот момент, а не работа «на сейчас».

Сейчас сборки в смысле phpize нет вообще: `ext/build.sh` делает два шага руками —
`cargo build --release` в статический архив и `gcc`, который компилирует `ext/sconcur.c`
и линкует его с этим архивом.

Черновик `ext/config.m4` (проверять на живой сборке, не переносить вслепую):

```m4
PHP_ARG_ENABLE([sconcur], [whether to enable sconcur],
  [AS_HELP_STRING([--enable-sconcur], [Enable sconcur])], [no], [yes])

if test "$PHP_SCONCUR" != "no"; then
  AC_PATH_PROG(CARGO, cargo, no)

  if test "$CARGO" = "no"; then
    AC_MSG_ERROR([sconcur is built from Rust sources and needs cargo in PATH])
  fi

  PHP_ADD_INCLUDE([$ext_srcdir/include])

  SCONCUR_SHARED_LIBADD="\$(builddir)/target/release/libsconcur_core.a -lpthread -ldl -lm"
  PHP_SUBST(SCONCUR_SHARED_LIBADD)

  PHP_NEW_EXTENSION([sconcur], [sconcur.c], [$ext_shared], , [-std=gnu11])
  PHP_ADD_MAKEFILE_FRAGMENT([$ext_srcdir/Makefile.frag])
fi
```

Плюс `ext/Makefile.frag`, собирающий архив до линковки и держащий цель cargo вне дерева
исходников:

```make
$(builddir)/target/release/libsconcur_core.a:
	cd $(srcdir) && CARGO_TARGET_DIR=$(builddir)/target cargo build --release

all: $(builddir)/target/release/libsconcur_core.a
```

Что проверить на месте:

- out-of-tree сборка (`./configure` из отдельного каталога): `$(builddir)` и `$(srcdir)`
  должны разъезжаться правильно;
- порядок линковки — архив последним, символы PHP остаются неразрешёнными и резолвятся
  при `dlopen`; это уже так в `build.sh`, autoconf не должен сломать;
- `make install` кладёт `sconcur.so` в `extension_dir`;
- сообщение об отсутствии cargo должно называть требуемую версию Rust и ссылку на
  rustup — это дешевле любой документации;
- `ext/build.sh` остаётся быстрым путём разработки (решено). Значит с появлением
  `config.m4` в проекте станет два способа собрать одно и то же, и они будут
  разъезжаться — за этим нужно следить руками: любая правка сборки должна попадать в
  оба, а `make ext-check` гоняться против того, что собрал phpize.

`config.w32` не нужен, пока Windows не заявлена в `os-families`.

## Состав архива исходников — вместе с config.m4

Тоже не входит в первую поставку: без `composer-default` исходники пользователю не
едут. Packagist отдаёт git-архив зеркала. В `ext/`
уже не попадает собранное (`/target/`, `/build/*.so`, `/build/*.o` в `ext/.gitignore`),
но попадёт лишнее: `ext/bench/` (`ladder.sh`, `loadclient.py`), `ext/check/` (smoke и
конфиг FPM), `ext/.env`.

Нужен `ext/.gitattributes` с `export-ignore` на них. Обязаны попасть: `sconcur.c`,
`include/sconcur_core.h`, `src/**`, `Cargo.toml`, `Cargo.lock`, `config.m4`,
`Makefile.frag`, `composer.json`, `LICENSE` (копия из корня — у зеркала своей нет).

## Релиз и CI

`.github/workflows/release.yml` после создания тега получает шаги:

1. `git subtree split --prefix=ext` и push ветки и тега в зеркало, перетегивая без `v`;
2. проверка потолка GLIBC на собранной `.so` — гейт, а не отчёт;
3. упаковка `.so` в zip с ассетным именем (сам файл — в корне архива);
4. создание релиза в зеркале с этим ассетом.

Отдельной сборочной базы не нужно: ячейка одна и собирается тем же образом, что и всё
остальное.

Условия те же, что у текущего релиза: тег иммутабелен, повторный push пропускается.

Официальный экшен `php/pie-ext-binary-builder` собирает через phpize/configure и потому
требует `config.m4`; нам он не нужен — `.so` CI уже производит, остаётся переименовать и
заархивировать. Вернуться к нему имеет смысл, если матрица разрастётся.

Отдельная проверочная job: в чистом контейнере (без тулчейнов проекта, без Rust)
выполнить `pie install` и убедиться, что `php -m | grep sconcur` и `php --ri sconcur`
отвечают ожидаемой версией. Без этого о поломке имён ассетов первым узнает пользователь:
основной `make check` собирает ядро через `build.sh` и путь PIE не трогает вообще.

## Packagist и документация

- Зарегистрировать `sconcur/sconcur-ext` на Packagist, включить webhook зеркала.
- Раздел установки в `README.md` и `README.ru.md` (обе версии, синхронно): `pie install`
  + `composer require`, на каких платформах это работает (PHP 8.4, x86_64, glibc ≥ 2.34),
  и бинарник из релизов как запасной путь для всех остальных. Пока fallback на сборку
  выключен, честнее написать «на других платформах — вручную», чем умолчать.
- `"require": {"ext-sconcur": ...}` в корневой `composer.json` не добавляется (решено):
  composer начал бы жёстко требовать загруженное расширение, включая окружения, где
  библиотеку ставят только чтобы почитать код.
