# Атрибуция CPU на запрос: план измерений до любых переписываний

> **Статус: фазы 0–4 выполнены** (см. «Результаты» внизу), включая лестницу
> отсечений и pprof. Цель плана: разложить ~189 мкс CPU на пустой запрос до
> статей, каждая из которых подтверждена измерением. Вопрос смены языка закрыт:
> пол L0 — ~19 мкс, а не ~150.

## Исходные числа

Из `docs/benchmarks.ru.md` (сессия 2026-08-09), пересчёт CPU на запрос:

| Ручка | Стек | rps | CPU avg | мкс CPU/запрос | p50 |
| --- | --- | ---: | ---: | ---: | ---: |
| `/` | SConcur | 64 100 | 1210% | **~189** | 3.9 мс |
| `/` | RoadRunner | 46 600 | 1050% | ~225 | 5.4 мс |
| `/` | Swoole | 353 000 | 257% | **~7** | 0.4 мс |
| `/all` | SConcur | 2 681 | 735% | ~2741 | 86 мс |
| `/all` | Swoole | 2 671 | 237% | ~887 | 80 мс |

Известная сумма примитивов: cgo-переход 0.082 мкс, msgpack pack/unpack
0.1–0.2 мкс, unmarshal 0.19 мкс. Итого < 1 мкс. **Неатрибутировано ~188 мкс.**

## Ключевое разделение, которое нельзя смешивать

Это **две разные статьи**, и они требуют разных экспериментов:

- **A. Путь запроса (`/`).** Нет веера, нет БД, нет парковки на `waitAny`.
  План `park-wake-coordination.ru.md` эту статью **не объясняет**: там речь про
  приостанавливающиеся корутины, которых на пустой ручке нет. 189 мкс тратятся
  на accept, доставку в PHP, создание Fiber, сборку ответа.
- **B. Координация веера (`/all`).** Здесь гипотеза уже есть: ~128 мкс на
  корутину не атрибутировано, подозрение на park/wake cgo-нити через futex.

Начинать надо с **A**: меньше переменных, и это пол под всем остальным. Пока пустой
запрос стоит 189 мкс, оптимизация веера бессмысленна.

## Основная метрика

**мкс CPU на запрос**, а не rps. RPS смешивает эффективность с насыщением: вы
обогнали RoadRunner на 38% по rps, но всего на 16% по стоимости запроса, потому
что просто дожали CPU выше. Формула:

```
мкс/запрос = (CPU_avg_percent * 10000) / rps
```

## Фаза 0. Проверить, что измеряется то, что кажется

Без этого все последующие цифры недостоверны.

### 0.1. Не упирается ли генератор нагрузки

Для Swoole вы это уже поймали. Проверьте для себя:

```bash
for T in 4 8 16; do
  WRK_THREADS=$T CONNECTIONS=256 DURATION=20 ROUTE=/ \
    tests/benchmarks/http-load-stats.sh
done
```

Если rps растёт с числом тредов wrk, все числа на `/` надо пересчитать.

### 0.2. Насыщение или лимит конкуренции

Little's law на ваших числах: 256 соединений / 3.9 мс = ~65 600 rps, а измерено
64 100. Совпадение почти точное, то есть система работает ровно на пределе
конкуренции. Нужно понять, упирается она в CPU или в глубину очереди:

```bash
for C in 64 128 256 512 1024; do
  CONNECTIONS=$C DURATION=20 ROUTE=/ tests/benchmarks/http-load-stats.sh
done
```

- rps плоский, p50 растёт линейно → насыщение по CPU, идём дальше
- rps растёт с соединениями → вы мерили не потолок, все выводы пересобрать

### 0.3. Холостой CPU

```bash
# сервер поднят, нагрузки нет
docker stats --no-stream
```

Ожидание: ~0%. Любое заметное значение означает спиннинг или слишком частый
тикер, и это сразу объясняет часть 1210%.

## Фаза 1. Гипотеза номер один: оверсабскрипция Go-рантаймов

**Проверять первой, потому что она дешёвая и объясняет и CPU, и латентность.**

У вас 12 воркеров, каждый со своим Go-рантаймом, и в каждом `GOMAXPROCS` по
умолчанию равен числу ядер машины. То есть 12 × N потоков Go-планировщика на N
ядер, плюс `sysmon` на процесс, плюс GC-воркеры на процесс. У Swoole для
сравнения один процесс и reactor-потоков всего N на всю систему.

Это даёт ровно ту картину, которую вы видите: высокий CPU, скромная пропускная
способность, десятикратная латентность на пустой ручке. Время уходит в
переключения контекста и миграции между ядрами, а не в полезную работу.

### 1.1. Замер

```bash
nproc  # зафиксировать N
# на воркере, до старта рантайма
GOMAXPROCS=1 tests/benchmarks/http-load-stats.sh
GOMAXPROCS=2 ...
GOMAXPROCS=4 ...
```

Прогнать на `/` и на `/all` отдельно.

### 1.2. Подтверждающий счётчик

```bash
perf stat -e context-switches,cpu-migrations,task-clock \
  -p $(pgrep -d, -f 'sconcur') -- sleep 20
```

Разделить на число обслуженных за эти 20 секунд запросов.

**Интерпретация:**

| context-switches на запрос | Вывод |
| --- | --- |
| < 1 | Стоимость вычислительная, идти в фазу 2 |
| 2–5 | Park/wake round-trip, ожидаемо для B, подозрительно для A |
| > 10 | Оверсабскрипция или спиннинг, лечится настройкой |

Если `GOMAXPROCS=1` даёт заметное падение мкс/запрос, дальше можно не копать:
это конфигурация, а не архитектура, и Rust тут ни при чём.

## Фаза 2. Top-down профиль всего процесса

### 2.1. Где вообще время

```bash
perf record -F 999 -g --call-graph fp \
  -p $(pgrep -d, -f 'sconcur') -- sleep 30
perf report --sort=dso        # libphp / расширение / ядро / libc
perf report --sort=sym --percent-limit=1
```

Go на amd64 собирается с frame pointers, так что `fp` работает и намного дешевле
`dwarf`.

**Что искать:** доля в ядре. Если в `entry_SYSCALL_64`, `futex_wait`,
`schedule` лежит больше 30%, это park/wake, и фаза 3 обязательна.

### 2.2. Off-CPU время

CPU-профиль не покажет ожидание. Отдельно:

```bash
perf record -e sched:sched_switch -e sched:sched_stat_sleep \
  -g -p $(pgrep -d, -f 'sconcur') -- sleep 20
```

Или через `offcputime-bpfcc`, если доступен bcc.

## Фаза 3. Профиль Go-стороны

Добавить в расширение включаемый по env pprof-эндпоинт (`net/http/pprof` на
отдельном порту, только при `SCONCUR_PPROF=1`).

```bash
go tool pprof -http=: 'http://localhost:6060/debug/pprof/profile?seconds=30'
go tool pprof -http=: 'http://localhost:6060/debug/pprof/block'
go tool pprof -http=: 'http://localhost:6060/debug/pprof/mutex'
go tool pprof -http=: 'http://localhost:6060/debug/pprof/allocs'
```

Включить сбор:

```go
runtime.SetBlockProfileRate(1)     // на время профилирования
runtime.SetMutexProfileFraction(1)
```

**Block и mutex профили здесь важнее CPU-профиля:** именно они покажут
park/wake и контенцию на каналах, которых CPU-профиль не видит.

Плюс трассировка планировщика:

```bash
curl -o trace.out 'http://localhost:6060/debug/pprof/trace?seconds=5'
go tool trace trace.out
```

В `go tool trace` смотреть **Scheduler latency profile** и **Syscall blocking
profile**. Первое покажет, сколько горутина ждёт исполнения, второе, сколько
времени cgo-нити проводят в syscall.

## Фаза 4. Лестница отсечений

Самая ценная часть плана: локализует статью без профилировщика, через дельты.
Каждая ступень это отдельная ручка в демо-сервере.

| Ступень | Что делает | Что измеряет |
| --- | --- | ---: |
| L0 | Go отвечает `200 ok` сам, PHP не вызывается | сеть + Go-рантайм |
| L1 | + cgo-переход, PHP-обработчик возвращает константу | цена границы |
| L2 | + создание Fiber на запрос, тело пустое | цена Fiber |
| L3 | + текущая обвязка целиком (`/`) | остаток |

Считать мкс CPU/запрос на каждой ступени. Дельта L(n) − L(n−1) и есть цена
ступени.

**Ожидание по вашим же микробенчам:** L1 − L0 должно быть меньше 1 мкс. Если оно
существенно больше, микробенчи мерили не то, что происходит в проде, и это само
по себе главный результат.

L0 отдельно ценен как абсолютный пол: он показывает, что даёт ваш Go-сервер
вообще без PHP, и с чем честно сравнивать 7 мкс Swoole.

## Фаза 5. Точечные подозреваемые

Проверять только те, на которые указали фазы 1–4.

- **GC.** `GODEBUG=gctrace=1`, посмотреть частоту и паузы. При 12 рантаймах GC
  идёт независимо в каждом. Попробовать `GOGC=400` и `GOMEMLIMIT`.
- **Аллокации на запрос.** `allocs` профиль, метрика `alloc_objects` на запрос.
  Каждая аллокация в горячем пути умножается на rps.
- **Спиннинг.** `perf top` под нагрузкой: если в топе видно активный цикл
  ожидания, это прямая находка.
- **Создание горутины на запрос.** Если на каждый запрос создаётся горутина плюс
  каналы, при 64k rps это заметно. Проверяется по `allocs` и по счётчику
  горутин в трассировке.
- **Стоимость Fiber.** Отдельный микробенч: `Fiber` create + start + suspend +
  resume в цикле, без всякого Go. Даёт пол, ниже которого PHP-сторона не
  опустится.

## Результаты фаз 0–2 (сессия 2026-08-10)

Условия: коммит `7adbcba`, `nproc` 16 (hybrid P/E), 12 воркеров с пином
`taskset -c $i`, wrk 4 треда / 256 соединений / 20 с, ручка `/`, суммарный RSS
воркеров ~571 MiB. Все числа — внутрисессионные. `GOMAXPROCS` пробрасывается в
`tests/benchmarks/http-load-stats.sh` через окружение (добавлено в этой сессии).

### Фаза 0: замеры достоверны

| Прогон | rps | p50 | CPU avg | мкс CPU/запрос |
| --- | ---: | ---: | ---: | ---: |
| база (t4) | 63 758 | 3.92 мс | 1210% | 189.9 |
| wrk 8 / 16 тредов | 63 417 / 63 508 | ~3.9 мс | ~1200% | 190.4 / 188.5 |
| 8 серверов | 42 648 | 5.90 мс | 807% | 189.3 |
| 64 → 1024 соединений | 61 006 → 59 912 | 0.94 → 16.9 мс | ~1210% | 197.8 → 202.3 |

Генератор не упирается (rps не растёт с тредами wrk); rps плоский по
соединениям при линейном росте p50 — насыщение по CPU; стоимость запроса
инвариантна к геометрии (при 8 серверах — те же 189 мкс). Холостой CPU
~13–15% на 12 воркеров (~1.2%/процесс) — периодический тикер, не спиннинг.

### Фаза 1: оверсабскрипции нет, гипотеза закрыта

| Прогон | rps | CPU avg | мкс CPU/запрос |
| --- | ---: | ---: | ---: |
| `/` default | 63 758 | 1210% | 189.9 |
| `/` G=1 | 63 403 | 1208% | 190.5 |
| `/` G=2 | 58 606 | 1204% | 205.5 |
| `/` G=4 | 25 962 | 1210% | 466.1 |
| `/all` default | 4 006 | 1024% | 2556 |
| `/all` G=1 | 3 994 | 1007% | 2520 |

Go выводит дефолтный `GOMAXPROCS` из CPU-аффинности, а воркеры пинятся на одно
ядро — эффективный `GOMAXPROCS` уже равен 1 (поэтому default ≡ G=1).
Принудительные G=2/4 при пине на одно ядро только добавляют потоков
планировщика и роняют пропускную способность. Настройкой рантайма здесь ничего
не выиграть.

Счётчики (под нагрузкой на `/`, `perf stat` и `/proc` сходятся):

- context switches: **4.7 на запрос** (3.1 добровольных + 1.6 вытесняющих) —
  по таблице интерпретации это зона park/wake, подозрительная для пути A;
- cpu-migrations: 0.01 на запрос — пиннинг работает;
- minor page faults: **3.1 на запрос** — см. `kernel: mm` ниже.

### Фаза 2: top-down профиль (999 Гц, 20 с, cpu_core, ~273k сэмплов)

Разбивка по DSO: `sconcur.so` 38.6%, `php` 31.6%, ядро 26.5%, libc+vdso ~2%.
Одного доминирующего пожирателя нет — стоимость размазана. По категориям
(агрегация символов; ~190 мкс CPU/запрос за 100%):

| Категория | % CPU | ~мкс/запрос |
| --- | ---: | ---: |
| Go: GC + аллокатор | 12.2% | ~23 |
| PHP: VM-цикл (`execute_ex`) | 9.9% | ~19 |
| Go: runtime прочее (spanSet, pcvalue, unwinder) | 8.8% | ~17 |
| ядро: mm (page faults, munmap, TLB, maple tree) | 6.6% | ~13 |
| Go: stdlib `net/http` + poller | 6.9% | ~13 |
| Go: планировщик/каналы/cgo (selectgo, lock2, futex) | 5.3% | ~10 |
| ядро: сеть (tcp/ip/softirq) | 3.8% | ~7 |
| PHP: hash/array/string | 3.4% | ~6 |
| ядро: sched/futex | 2.9% | ~6 |
| PHP: аллокатор | 2.0% | ~4 |
| PHP: прочее (мелкие zend_*) | 11.6% | ~22 |
| ядро: прочее (rcu, spinlocks, load_avg) | 8.3% | ~16 |
| Go: msgpack + код расширения | 2.8% | ~5 |
| PHP: ext-msgpack, dtor/GC; libc; vdso | ~3% | ~6 |

Наблюдения:

- Доля ядра 26.5% — ниже порога 30% из фазы 2.1; futex/sched-статья видна
  (~5–8% суммарно по ядру и Go-стороне), но не доминирует.
- `kernel: mm` — это mmap/munmap-чёрн PHP-стороны: в стеках `zap_pte_range`,
  `do_vmi_align_munmap`, `mas_*` (maple tree), munmap приходит из libc (не из
  Go), в профиле виден `make_fcontext` (Boost.Context — механизм Fiber), и на
  запрос приходится 3.1 minor fault. Кандидат — жизненный цикл стека Fiber
  (mmap при создании, первое касание страниц, munmap при уничтожении); точное
  разделение с чёрном чанков Zend MM даст лестница фазы 4 (ступень L2).
- Крупнейшая одиночная статья Go-стороны — GC + аллокатор (~23 мкс/запрос):
  на запрос создаются горутина, каналы (`makechan` в профиле) и msgpack-буферы.
  Профиль `allocs` из фазы 3 покажет точки аллокаций.
- PHP-сторона суммарно ~54 мкс: VM-цикл + рассыпанные zend_* без единого
  горячего пятна. PHP-бинарь в образе стрипнут и собран без frame pointers —
  для символов и колл-графов PHP-стороны нужен пересобранный образ.

### Ворота (по фазе 6)

Оверсабскрипция — закрыта (не подтвердилась). GC — кандидат, идти в фазу 3
(`allocs`/`block`/`mutex` профили). Спиннинга нет. Стоимость Fiber — кандидат,
проверяется ступенью L2 лестницы (фаза 4) и микробенчем Fiber (фаза 5). Park/wake —
вторична для пути A (4.7 переключений на запрос при futex-доле ~5–8%), для
пути B остаётся основной гипотезой. Пол L0 не измерен — лестница фазы 4 нужна,
чтобы закрыть вопрос про смену языка. Ни одна из подтверждённых статей к смене
языка не ведёт.

## Результаты фаз 3–5 (та же сессия 2026-08-10)

### Фаза 3: pprof

В расширение добавлен опциональный pprof-эндпоинт (`ext/pprof.go`): включается
`SCONCUR_PPROF_ADDR=127.0.0.1:6060`; `SCONCUR_PPROF_BLOCK=1` /
`SCONCUR_PPROF_MUTEX=1` дополнительно включают block/mutex-профили. При
reuse-port-пуле переменную ставят одному воркеру. Профили под нагрузкой на `/`:

- `allocs` (alloc_objects, горячий путь на запрос): `time.NewTimer` — таймер
  `handlerTimeout` создаётся в `consumeCommands` на каждый запрос;
  `context.WithCancel` дважды (задача в `flows.HandleMessage`/`tasks.NewTask` и
  http-слой); `formatAccessLine` (Sprintf); `GoString`/`GoStringN` (копии строк
  на каждом cgo-переходе); `readMIMEHeader`. Это и есть источник статьи «GC +
  аллокатор ~23 мкс» из фазы 2 — всё точечно устранимо (ленивый/переиспользуемый
  таймер, задача без context в горячем пути, лог без Sprintf).
- `block`: почти всё в `selectgo` conn-горутины (`net/http.(*conn).serve` ждёт
  ответ PHP через канал `pendingRequest.commands`) — рандеву park/wake на
  запрос; mutex-профиль пуст, контенции нет.
- Трассировка (scheduler latency): ожидание исполнения в `chansend`/
  `selectnbsend` — очередь готовых горутин при эффективном GOMAXPROCS=1; влияет
  на латентность, не на CPU.

### Фаза 4: лестница отсечений

Демо-сервер получил bench-режимы: `SCONCUR_HTTP_BENCH_L0=1` (Go отвечает сам,

`tests/servers/http/http-server.php`; `l2` — Fiber suspend'ится, push вне стека
файбера, как в проде; `l2f` — push на стеке файбера, патологический эталон).
`http-load-stats.sh` пробрасывает `SERVER_ENV`/`SERVER_ARGS`. Та же геометрия
(12 воркеров, wrk 4×256, 20 с):

| --- | ---: | ---: | ---: | ---: | ---: |
| L0: Go без PHP | 352 482 | 0.35 мс | 676% | 19.2 | 19.2 |
| L1: +cgo, ответ без Fiber | 137 959 | 1.85 мс | 1212% | 87.8 | +68.6 |
| L2: +Fiber (suspend/resume) | 104 603 | 2.40 мс | 1205% | 115.1 | +27.3 |
| L3: полный сервер (`/`) | 63 142 | 3.92 мс | 1206% | 191.0 | +75.9 |
| l2f: push на стеке файбера | 28 301 | 8.94 мс | 1223% | 432.2 | — |

На L0 wrk с 4 тредами близок к потолку генератора (те же ~352k, что и у Swoole
в сессии 2026-08-09), CPU сервера не насыщен (676%); мкс/запрос как CPU/rps
остаётся корректной оценкой стоимости.

Выводы лестницы:

- **Главный результат: L1 − L0 = 68.6 мкс, а не «меньше 1 мкс».** Микробенчи
  границы мерили голый cgo-переход; продовый путь доставки запроса — это
  msgpack-marshal события в Go, канал в `Next()`, кадрирование результата,
  `waitAnyBatch`-переход, unpack в PHP, сборка `RespondPayload`, обратный push,
  `chansend` в conn-горутину и park/wake обоих потоков — ~69 мкс на запрос.
- Fiber (L2 − L1) — 27.3 мкс. Отдельный микробенч чистого цикла
  `new Fiber` + start + suspend + resume даёт 5.37 мкс: разница — та самая
  mm-статья (3.1 minor fault на первое касание стека и munmap с TLB-shootdown
  IPI по ~15 потокам Go-рантайма в том же процессе).
- Обвязка (L3 − L2) — 75.9 мкс, крупнейшая статья: `Scheduler` (spawn, State,
  dispatchPendingTask), декод запроса в PSR-7 (`decodeRequest`, заголовки,
  query), `HttpServer::handle`/`resolveResponse`, сборка ответа nyholm.
- l2f (push со стека файбера) — 432 мкс на запрос: воспроизводимое
  подтверждение патологии, ради которой пуши вынесены из корутин
  (`.ai/plans/async-fan-out-optimization.ru.md`).

### Ворота (итог по фазе 6)

Пол L0 — 19 мкс, не ~150: **смена языка не обсуждается**. Статьи, по убыванию:

| Статья | мкс | Кандидаты действий |
| --- | ---: | --- |
| Обвязка PHP (L3−L2) | ~76 | профилировать хвост: PSR-7-декод по запросу, spawn/State-бухгалтерия |
| Граница (L1−L0) | ~69 | аллокации на запрос в Go (таймер, context, Sprintf, cgo-копии), park/wake |
| Fiber (L2−L1) | ~27 | page-fault/munmap-чёрн стеков; сам Fiber стоит ~5 |
| Go-сервер (L0) | ~19 | пол; сравнивать с ~7 мкс Swoole честно именно здесь |

### Побочные находки

- После нагрузки на `/all` часть воркеров переживает SIGTERM: в двух прогонах
  свипа graceful shutdown завис у 2 и 4 воркеров из 12 — они продолжали слушать
  порт и обслуживать следующий прогон. Требует отдельного разбирательства
  (подозрение на зависание в останове при живых keepalive-соединениях или
  недобранных задачах).
- Для профилирования нужна сборка расширения без `-ldflags="-s -w"`
  (`ext-build.sh` стрипует символы) — отладочная копия собирается тем же
  рецептом в `build/sconcur-debug.so`.
- Хостовые sysctl для perf: `kernel.perf_event_paranoid=1`,
  `kernel.kptr_restrict=0` (значения по умолчанию 4/1 блокируют и сэмплинг, и
  символы ядра).
