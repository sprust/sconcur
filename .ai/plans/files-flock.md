# Files: замок на файле (`flock`)

Межпроцессный замок без внешнего сервиса: воркеры одного сервера исключают друг друга
через `flock(2)` на общем файле. Нативный `flock()` из PHP в корутине не годится:
`LOCK_EX` без `LOCK_NB` ставит весь PHP-поток в syscall, пока замок держит другой
процесс, а ни планировщик, ни преемпция в этот момент ничего не могут. Со `Files::lock()`
ждёт только своя корутина.

Продолжение [files-feature.md](files-feature.md): там `flock` стоял в «Сознательно
исключено» с формулировкой «нужен fd, живущий в расширении, и модель владения им». Эта
модель уже есть — сессия `FileWriter` (`ext/src/features/files/writer.rs`), и замок
строится по ней.

## Решения владельца (зафиксированы)

- Реализуется только файловый замок. Мьютекс для корутин внутри процесса, advisory-замки
  СУБД и Redis в эту работу не входят.
- Замок живёт в фиче Files: новые команды в `FilesCommandEnum`, без новой `MethodEnum`.
- Библиотека низкоуровневая: один `Files::lock()`, никаких `tryLock()`/`withLock()`.
  Обёртки делают пользователи.
- Не дождались замка — `lock()` возвращает `null`, а не бросает.
- `timeoutMs: null` — одна попытка без ожидания. `0` сохраняет смысл, общий для проекта:
  без дедлайна, ждать, пока не дадут или не остановят флоу.
- Только эксклюзивный замок (`LOCK_EX`). Разделяемого (`LOCK_SH`) и параметра режима нет.
- `pcntl_fork` с взятым замком — не лечится кодом, описывается в доке (см. «Ограничения»).
- Бамп версии минорный.

## Цель и не-цели

- Цель: взаимоисключение между процессами одного сервера (воркеры одного пула, CLI-скрипты,
  cron), и между корутинами одного процесса тем же вызовом.
- Цель: ожидание замка не держит PHP-поток, поток рантайма и поток blocking-пула.
- Цель: замок не теряется навсегда. Процесс умер — ядро сняло замок. Корутина умерла —
  замок снимает конец её флоу или деструктор.
- Не-цель: несколько серверов. `flock` локален для ядра; на NFS он либо не работает, либо
  работает по-разному в зависимости от версии и опций монтирования. Об этом прямо сказать
  в доке.
- Не-цель: честная очередь. `flock` не обещает порядок, опрос тоже. Кто первым попал в
  окно — тот и взял.
- Не-цель: разделяемый замок (`LOCK_SH`) в v1.

## API

```php
use SConcur\Features\Files\Files;
use SConcur\Features\Files\FileLock;

// Ждёт до timeoutMs; не дождался — null.
$lock = Files::lock(path: '/var/lock/app/report.lock', timeoutMs: 5_000);

if ($lock === null) {
    return;
}

try {
    buildReport();
} finally {
    $lock->release();
}

// Одна попытка без ожидания.
$lock = Files::lock(path: $path, timeoutMs: null);

// Ждать без ограничения — до замка или до остановки флоу.
$lock = Files::lock(path: $path, timeoutMs: 0);
```

- `Files::lock(string $path, int $permissions = 0644, ?int $timeoutMs = DEFAULT_TIMEOUT_MS): ?FileLock`
- `FileLock::release(): void` — идемпотентен; `FileLock::path()`, `FileLock::isHeld()`.

`timeoutMs` — срок ожидания замка, а не срок владения. Сколько держать, решает вызывающий;
верхнюю границу даёт `Deadline::run()` вокруг кода, как для любой корутины.

| `timeoutMs` | Ожидание | Не дождались |
| --- | --- | --- |
| `null` | одна попытка | `null` |
| `0` | без ограничения, до замка или остановки флоу | — |
| `> 0` | до истечения срока; открытие файла входит в срок | `null` |

## Протокол

Две команды в `FilesCommandEnum`, C-ABI не меняется:

| Команда | Код | Параметры | Ответ |
| --- | --- | --- | --- |
| LockAcquire | `lk` | `i` id, `p` path, `pm` права, `w` ждать ли | `a` взят ли |
| LockRelease | `ulk` | `i` id | пустой успех; неизвестный id — тоже успех |

`null` в `timeoutMs` на провод не идёт: конверт `FilesPayload` несёт `timeoutMs` как `int`
у всех команд. PHP отправляет `w: false` и `timeoutMs` = `DEFAULT_TIMEOUT_MS` — последний
тогда ограничивает только открытие файла. Для `0` и `> 0` — `w: true` и значение как есть.

Id рисует PHP (`uniqid('fl_', more_entropy: true)`), как у писателя. Ключ состояния в
реестре — с префиксом `files-lock:`, по той же причине, что `files-writer:`: id выбирает
вызывающий, и он не должен совпасть с чужим ключом задачи.

`LockRelease` без ошибки на неизвестный id: его отправляет деструктор, которому некому
сообщить об ошибке, и повторное снятие — нормальный исход (снял `release()`, потом
деструктор; или флоу закончился раньше).

## Механика в ядре

Новый модуль `ext/src/features/files/lock.rs`, реестр — рядом с `writer::Registries` в
`Core` (`ext/src/core.rs`), чтобы после `fork` потомок начинал без чужих замков в реестре.

### Открытие файла

`OpenOptions`: read + write + create, без truncate, права из `pm` (по умолчанию `0644`).
Через `open_bounded`, как у писателя: файл, который blocking-пул создал уже после дедлайна,
не должен повиснуть открытым дескриптором.

Файл замка никогда не удаляется — ни при снятии, ни при брошенном замке. Удаление ломает
сам замок: процесс A держит замок на inode 1, B ждёт на нём же, A снимает и удаляет файл,
C создаёт новый файл (inode 2) и берёт замок на нём, B просыпается с замком на inode 1.
Два владельца. Это правило идёт в доку отдельной строкой, а `Files::delete()` на файле
замка — забота вызывающего.

### Ожидание: опрос с `LOCK_NB`, а не блокирующий `flock`

Взятие — цикл: `spawn_blocking(flock(fd, LOCK_EX | LOCK_NB))`; `EWOULDBLOCK` → пауза
`tokio::time::sleep` → следующая попытка. Пауза растёт от 1 мс вдвое до потолка 50 мс.
Цикл слушает `task.context().cancelled()`, поэтому `stopFlow` прерывает его между
попытками.

Срок конверта здесь значит то же, что во всей фиче (`0` — без дедлайна), но его истечение
во время ожидания — не `Kind::Timeout`, а ответ «не взят». Поэтому обработчик не отдаёт
цикл в `bounded()`, а ведёт срок сам через `Budget`:

- `w: false` — открытие файла под сроком конверта, потом ровно одна попытка;
- `w: true` — попытки, пока не истечёт срок (при `0` — без конца); открытие входит в срок;
- не дождались — успешный ответ с `a: false`, без ошибки. Этот ответ последний
  (`success`, не `success_with_next`): сессии нет, и на синхронном пути флоу должен
  закончиться сразу. Файл при этом закрывается, сессия не регистрируется.

Почему не `spawn_blocking(flock(fd, LOCK_EX))` без `LOCK_NB`:

- Поток blocking-пула стоит в syscall всё время ожидания. Сто ждущих корутин — сто потоков
  из общего пула процесса, а в нём же резолвятся имена для HTTP-клиента.
- Такой syscall не отменить. Срок вышел, PHP получил `null`, а поток
  продолжает ждать и потом берёт замок, которым никто не владеет. Чистить это пришлось бы
  отложенной задачей, как в `open_bounded`, и всё это время замок держит никто.

Цена опроса — задержка до потолка паузы после освобождения и одна переправа в blocking-пул
на попытку (десятки микросекунд). Для замка, который держат миллисекунды и дольше, это
незаметно. Потолок 50 мс — стартовое значение; окончательное — по бенчмарку конкуренции
(см. «Тесты»).

Гонка «замок взят в момент отмены»: замыкание `spawn_blocking` владеет `File`
(перемещён внутрь, не `dup` и не сырой fd). Если цикл уже бросил future, успешная
попытка возвращает `File` в брошенный `JoinHandle`, он дропается, fd закрывается — последний
дескриптор на open file description, ядро снимает замок. Держателя-призрака не остаётся.
Это отдельный Rust-тест.

### Сессия и владение

- `Session { file: tokio::sync::Mutex<Option<File>>, path }`; реестр
  `HashMap<id, Arc<Session>>` плюс резервирование id на время открытия — тот же `Claim`,
  что у писателя.
- Состояние регистрируется через `states::get().register_with_flow(...)` под
  `files-lock:<id>`. Конец флоу вызывает `close()` состояния, и тот снимает замок.
- Ответ на `LockAcquire` — `success_with_next`, как у `WriteOpen`: на синхронном пути
  `FeatureExecutor` останавливает флоу на последнем результате, а конец флоу снимает замок
  раньше, чем PHP получит `FileLock`.
- Снятие: `flock(fd, LOCK_UN)` явно, потом `close`. Просто `close` недостаточно, если
  дескриптор был унаследован потомком после `fork` (см. «Ограничения»): у open file
  description тогда два держателя, и замок живёт, пока жив потомок. `LOCK_UN` снимает замок
  с description целиком.
- Оба syscall — в `spawn_blocking`: правило фичи «ни одного синхронного файлового вызова на
  потоке рантайма» (`ext/src/features/files/mod.rs`) не делает исключений для быстрых
  вызовов.

### Снятие из деструктора: detached push

`FileLock::__destruct()` снимает незакрытый замок. Ждать ответа в деструкторе нельзя: он
может выполниться посреди размотки корутины или вне файбера. Поэтому `LockRelease` из
деструктора уходит detached-пушем (пустой ключ флоу), как закрытие канала AMQP в
`Channel::pushDetached`.

Для этого `Method::Files` добавляется в `detachable()` (`ext/src/handler/mod.rs`). Detached
обработчик выполняется синхронно на PHP-потоке и не имеет права блокироваться, поэтому:

- в detached-режиме Files принимает только `LockRelease`, любая другая команда — отказ
  `files[arg]`. Иначе список разрешённых методов стал бы разрешением на всю фичу;
- обработчик только достаёт сессию из реестра и отдаёт снятие в `tokio::spawn` +
  `spawn_blocking`, сам ничего не ждёт.

Явный `release()` — обычный ожидающий `exec`: вызывающий узнаёт об ошибке, и после возврата
замок гарантированно снят. Обёртка пользователя вызывает его в `finally`.

Зачем деструктор, если есть конец флоу: флоу корутины в `WaitGroup` принадлежит группе. Член
группы, упавший с замком, иначе держал бы его до конца всей группы. У корутины из
`Scheduler::spawn()` флоу свой, и там оба механизма срабатывают почти одновременно, что
безопасно благодаря идемпотентности.

## Семантика, которую надо записать в доку

- Замок рекомендательный (advisory): он исключает только тех, кто тоже берёт `flock` на том
  же файле. Обычный `Files::write()` в файл замка он не останавливает.
- Нативный `flock()` из PHP и `Files::lock()` видят друг друга: это один и тот же `flock(2)`.
  Скрипт без SConcur исключается корректно.
- Внутри одного процесса две корутины тоже исключают друг друга: каждая открывает свой
  дескриптор, а `flock` привязан к open file description, а не к процессу (в отличие от
  `fcntl`-замков).
- Повторный вход: та же корутина, дважды взявшая `Exclusive` на одном пути, ждёт сама себя
  до `timeoutMs` и получает `null`. Не обнаруживается — ядро не знает про корутины. В доку.
- `null` вместо исключения: «занято» — ожидаемый исход, а не сбой.
- Ожидание прерывается дедлайном и `WaitGroup::stop()` между попытками; ничего не остаётся
  взятым.

## Ограничения

- Только один сервер, только локальная ФС (в Docker — общий том на одном хосте).
- `pcntl_fork` при взятом замке. Состояние ядра в потомке сбрасывается (`core.rs`), и
  замок по-прежнему держит родитель: его `release()`, конец флоу или деструктор делают
  `LOCK_UN`, а это снимает замок для всех, кто разделяет дескриптор. Но старый `Core` в
  потомке утекает, а не дропается, поэтому fd замка в потомке остаётся открытым. Отсюда
  один случай: родитель завершился, не сделав `LOCK_UN` (`SIGKILL`, падение, `exit()`
  раньше, чем дошёл detached-release), а потомок жив — ядро ОС не снимет замок, пока
  потомок не закроет свою копию fd, то есть до его выхода. Воркеров мастера это не
  касается: `proc_open` делает `exec`, а Rust открывает файлы с `O_CLOEXEC`. Для v1 —
  описывается в доке.
- Время владения не ограничено самим замком. Зависший держатель держит замок, пока жив его
  процесс. В отличие от замка с арендой в Redis, это не таймаут, а владение до конца процесса.

## Исключения

Новых видов ошибок в `errors.rs` не нужно:

- срок ожидания вышел → не ошибка, `null`;
- остановка флоу → `Kind::Stopped` → `FileStoppedException`;
- нет каталога, нет прав, путь — каталог → существующие `nf`/`pd`/`ft`;
- `release()` после снятия → не ошибка (идемпотентно, проверка на стороне PHP до переправы).

## Тесты

Rust (`#[cfg(test)] mod tests` в `lock.rs`), каждый проверен откатом фикса:
- второй замок на том же пути не берётся, пока первый не снят;
- отмена во время ожидания: после неё замок свободен, реестр пуст;
- попытка, успевшая после отмены future, не оставляет замок взятым (гонка из «Ожидания»);
- снятие через `LOCK_UN` освобождает замок при живом `dup` дескриптора — модель
  унаследованного после `fork` fd;
- файл замка после снятия и после брошенной сессии на месте;
- detached-режим принимает только `LockRelease`.

PHP (`tests/feature/Features/Files/FilesLockTest.php`):
- две корутины: критические секции не пересекаются (журнал входов и выходов);
- `timeoutMs: null` → `null` при занятом, объект при свободном;
- `timeoutMs: 0` ждёт, пока держатель не снимет замок, и прерывается `stop()` группы;
- срок ожидания вышел → `null`, после этого замок можно взять; флоу синхронного пути
  отпущен (нет висящей сессии);
- корутина упала с замком в `WaitGroup` с живыми соседями — замок свободен до конца группы
  (деструктор);
- `stop()` группы во время ожидания;
- синхронный путь: `lock` → `release` → повторный `lock` без ожидания;
- между процессами: дочерний `php` через `proc_open` держит нативный `flock()`,
  `Files::lock()` ждёт и получает замок после его выхода; и наоборот — `Files::lock()` держит,
  нативный `flock(LOCK_NB)` в дочернем процессе получает отказ;
- убитый (`SIGKILL`) держатель в дочернем процессе — замок свободен сразу.

Soak: сценарий `lock` в `make mem-leak-files` — циклы взятия и снятия, брошенные без
`release()` замки, ожидания, прерванные дедлайном; RSS и число открытых fd
(`/proc/self/fd`) должны стоять на месте.

Бенчмарк `tests/benchmarks/files/lock-contention.php` (`make bench-files-lock-contention`):
N корутин и M процессов берут один замок на короткую секцию; задержка от снятия до взятия
следующим и пропускная способность. По нему выбирается потолок паузы опроса.
