# SConcur

> ⚠️ Экспериментальный проект, не для продакшена. Очередная попытка
> сделать PHP асинхронным, но без расширения, написанного на C, — с расширением
> на Rust.

Библиотека конкурентности для PHP поверх собственного расширения на Rust.
PHP-сторона (Fiber) приостанавливается, пока расширение выполняет задачу
(операции MongoDB, sleep и т.п.) конкурентно на асинхронном рантайме. Обмен между
сторонами идёт через
MessagePack.

## Цифры против RoadRunner и Swoole

Одно и то же демо-приложение на одной машине: `wrk` 4 треда / 256 соединений /
20 c, данные БД на диске. Число воркеров у каждого сервера указано в строке:
пустой ответ замерен на 12, а `/db` и `/db-rw` — на лесенке по числу воркеров,
откуда взята ступень в 8 (на ней SConcur выходит на пик, и генератор нагрузки
ещё не делит ядра с серверами):

| Запрос | SConcur | RoadRunner | Swoole |
| --- | ---: | ---: | ---: |
| пустой ответ (12 воркеров) | ≈194 300 rps, p50 0.9 мс | ≈45 100 rps, p50 5.4 мс | ≈365 600 rps, p50 0.35 мс |
| точечный SELECT по id, `/db` (8 воркеров) | 44 200 rps, p50 5.4 мс | 22 887 rps, p50 10.7 мс | 117 693 rps, p50 2.0 мс |
| INSERT + COUNT(*) + SELECT, `/db-rw` (8 воркеров) | 2 366 rps, p50 95.8 мс | 289 rps, p50 877 мс | 2 467 rps, p50 89.8 мс |

Строки для эндпоинта с MongoDB здесь нет. `ext-mongodb` находится вне
рантайм-хуков Swoole, поэтому тот же обработчик блокирует Swoole-воркер целиком,
и такая строка показывала бы состояние драйвера так, будто это свойство модели
исполнения.

Swoole на дешёвых путях быстрее, но его конкурентность держится на хуках в
существующие PHP-драйверы: то, что хуками не покрыто, блокирует воркер целиком
(так с `ext-mongodb`). В SConcur фича — обычный асинхронный Rust поверх зрелого
Rust-драйвера, поэтому новые фичи добавлять и поддерживать проще.

Где SConcur не выигрывает — одиночные дешёвые запросы, мегабайтные данные,
CPU-bound обработчики — так же прямо перечислено в таблице
[«Нужен ли вам SConcur»](docs/positioning.ru.md#нужен-ли-вам-sconcur), рядом с
[бенчмарками по фичам](docs/benchmarks.ru.md) и
[поведением под нагрузкой](docs/load-testing.ru.md).

## Идея

Обычный PHP синхронен: `sleep()`, запрос через PDO, HTTP-вызов — каждая операция
блокирует процесс, и выполняются они строго по очереди. Две операции по секунде
занимают две секунды.

SConcur выполняет такие операции одновременно. Блокирующие вызовы заменяются на
аналоги из SConcur (см. [Что заменяет](#что-заменяет)), оборачиваются в корутины,
и сама работа уходит в расширение и исполняется там параллельно. Общее время
ограничено самой медленной операцией, а не их суммой. PHP остаётся тонким
слоем-оркестратором, вся конкурентность живёт ниже него.

## Пример

Две корутины работают одновременно, каждая — операция на секунду.
Последовательно это заняло бы около двух секунд, конкурентно — около одной.

```php
use SConcur\WaitGroup;
use SConcur\Features\Sleeper\Sleeper;

$start = microtime(true);

$waitGroup = WaitGroup::create();

// корутина 1: операция на секунду (вместо блокирующего sleep())
$waitGroup->add(function () {
    Sleeper::sleep(seconds: 1);

    return 1;
});

// корутина 2: ещё одна такая же операция
$waitGroup->add(function () {
    Sleeper::sleep(seconds: 1);

    return 2;
});

$waitGroup->waitResults();

$seconds = round(microtime(true) - $start, 2);

echo "готово за {$seconds} c" . PHP_EOL;
```

Вывод: `готово за 1 c` — две секундные операции выполнились параллельно.

## Что заменяет

Операции и клиенты — обёрнутые в корутину (`$waitGroup->add()` +
`$waitGroup->wait*()`), работают конкурентно, а не блокируют процесс:

| Обычный PHP | SConcur | Что меняется |
| --- | --- | --- |
| `sleep()`, `usleep()` | `Sleeper::sleep()`, `Sleeper::usleep()` | пауза на секунды или микросекунды |
| `PDO` / `mysqli` (MySQL) | `Features\Mysql\Connection` | запросы, транзакции, стриминг SELECT; пул соединений в расширении |
| `PDO` (PostgreSQL) | `Features\Pgsql\Connection` | та же SQL-фича на драйвере pgx |
| `mongodb/mongodb`, `ext-mongodb` | `Features\Mongodb\Connection\*` | CRUD, агрегации, курсоры; BSON-значения — `SConcur\Bson\*` |
| `curl`, `file_get_contents`, Guzzle | `Features\HttpClient\HttpClient` (PSR-18) | стриминг ответа, скачивание в файл внутри расширения |
| `fsockopen`, `stream_socket_client` | `Features\SocketClient\SocketClient` | TCP с length-prefix кадрами |
| WS-клиент (библиотека) | `Features\WsClient\WsClient` | обмен text/binary сообщениями |
| `ext-amqp`, `php-amqplib` (RabbitMQ) | `Features\Amqp\*` | консьюмер приостанавливает свою корутину, а не воркер; подтверждение принадлежит доставке |

Долгоживущие серверы:

| Обычный PHP | SConcur | Что меняется |
| --- | --- | --- |
| PHP-FPM, RoadRunner, Swoole, Workerman | `Features\HttpServer\HttpServer` (PSR-7) | HTTP-сервер |
| `stream_socket_server` | `Features\SocketServer\SocketServer` | TCP-сервер |
| Ratchet, Workerman (WS) | `Features\WsServer\WsServer` | WebSocket-сервер |

## Как это работает

`WaitGroup` оборачивает каждое замыкание в `Fiber`. При вызове асинхронной фичи
корутина приостанавливается, а задача уходит в расширение, в отдельную задачу
рантайма. Каждый
`WaitGroup` владеет одним флоу — так называется группа принадлежащих ему задач
на стороне расширения. Единый процессный `Scheduler` ждёт расширение (`waitAnyBatch`):
блокируется, пока не будет готов первый результат любого флоу, вместе с ним за
то же пересечение границы забирает те результаты, что уже готовы, и возобновляет
нужные корутины по `taskKey`. Результаты приходят в порядке завершения задач, а
не в порядке `add()`.

Число одновременно живых корутин группы по умолчанию не ограничено. Чтобы
ограничить память или пул соединений БД, задайте лимит:
`WaitGroup::create(maxConcurrency: N)` — лишние `add()` встают в очередь и
запускаются по мере освобождения слотов.

Подробности — схемы «PHP Fiber ↔ задача рантайма», слои и жизненный цикл задачи —
в [docs/architecture.ru.md](docs/architecture.ru.md).

## Зачем расширение и почему Rust

Вся модель конкурентности сводится к одному примитиву — каналу. Каждая задача
исполняется своей задачей рантайма, а результаты всех флоу складываются в
один общий буферизованный канал. PHP не крутит event-loop и ничего не
опрашивает: единый процессный `Scheduler` блокируется на чтении сообщения из
этого канала (`waitAnyBatch`) и просыпается на первом готовом результате,
забирая вместе с ним за то же пересечение границы те результаты, что уже готовы.
Кто закончил первым — решает канал; PHP только возобновляет соответствующую
корутину по `taskKey`.

Отсюда следует остальное:

- Фича — одна асинхронная функция на Rust. Пишется обработчик, рантайм запускает
  его отдельной задачей и кладёт результат в канал. Ни промисов, ни колбэков, ни
  рассуждений про event-loop на стороне PHP.
- Зрелые драйверы берутся как есть — драйвер MongoDB, sqlx, hyper, reqwest,
  lapin, fastwebsockets — и сразу работают конкурентно. Не нужно ждать
  асинхронных PHP-драйверов и расширений.
- C-клей заморожен: `push`, `wait`, `waitAny`/`waitAnyBatch`, `next`, `stopFlow`
  плюс жизненный цикл `version`/`destroy`. Новая фича — это данные (значение
  `MethodEnum`, payload-DTO в MessagePack, обработчик на Rust), а не новый C-символ,
  поэтому набор экспортов не разрастается. Отдельный долгоживущий сервер
  добавляет максимум одну control-функцию вроде `httpStopAccepting`: она
  прекращает приём новых соединений, пока уже начатые доводятся до конца.
- Один транспорт и одна модель стриминга на всё: MessagePack-DTO плюс потоковые
  состояния за `next()` — курсоры MongoDB, тела HTTP, кадры сокета, сообщения WS
  едут по одному механизму, и отправитель ждёт, если читатель не успевает.
- Единый интерфейс для sync и async: нет отдельных «асинхронного» и
  «синхронного» вариантов одной функции. Один и тот же вызов работает внутри
  `WaitGroup` (конкурентно) и вне его (обычный блокирующий); конкурентность
  выбирает вызывающий, а не автор фичи.
- Фича бесплатно получает весь рантайм: вложенные корутины, отмена по контексту,
  проброс дедлайна, graceful-shutdown с разматыванием.
- Клиент- и сервер-фичи отдают PSR-интерфейсы (PSR-7/17, PSR-18) с инъекцией
  фабрик, поэтому встраиваются в любое приложение без адаптеров.

## Применение и ограничения

- Рассчитано на долгоживущие процессы, и на них же протестировано: воркеры,
  демоны, консольные команды и сами HTTP-, WebSocket- и сокет-серверы — обычные
  PHP-скрипты, слушающие порт (модель Swoole / ReactPHP). Библиотека также
  встраивается в уже имеющийся долгоживущий процесс, в том числе в воркер
  RoadRunner. SAPI при этом нигде не проверяется: это про то, для чего оно
  сделано, а не про то, что оно запрещает.
- PHP-FPM работает — с оговоркой, которую стоит понимать. Пул из 4 статических
  воркеров, в каждом запросе веер из двенадцати 100-мс корутин: каждый запрос
  укладывается в ~102 мс вместо 1200 (`ext/check/fpm-check.sh`). Воркер
  пересобирает рантайм после форка мастера, и конкурентность внутри одного
  запроса настоящая. Чего FPM дать не может — конкурентности *между* запросами:
  веер обязан закончиться раньше запроса, и каждый воркер держит свой рантайм.
  То есть выигрыш примерно как от `curl_multi`, а окупается библиотека на
  серверах выше. ZTS-сборки (mod_php на потоковом MPM) не поддерживаются вовсе.
- `pcntl_fork` поддерживается, в том числе после того, как расширение уже
  выполняло работу. В потомка переходит только форкавший поток, поэтому у
  унаследованного рантайма не остаётся рабочих потоков; расширение это замечает и
  пересобирает его при первом же вызове в потомке. Родителя это не задевает.
- Только NTS (non-thread-safe), ZTS-сборка не поддерживается.
- Только Linux — определение числа ядер, сигналы/`posix`, `SO_REUSEPORT`, `flock`
  мастера.
- `exit()`/`die()` при активных задачах безопасен, но теряет их результаты.
  Shutdown-хендлер разматывает незавершённые корутины (finally-блоки выполняются,
  транзакции откатываются, курсоры и флоу освобождаются), после чего процесс
  завершается штатно. Лучше довести задачи до конца или остановить явно
  (`WaitGroup::stop()`).
- Конкурентный режим необязателен. Любую фичу можно вызвать вне `WaitGroup` как
  обычный синхронный вызов: вне Fiber `FeatureExecutor` определяет неасинхронный
  контекст и просто дожидается результата (`Extension::wait`).

```php
// синхронно, без WaitGroup — вернёт результат сразу
$collection->insertOne(['name' => 'example']);
```

## Планы

- Фича `Std` — SConcur-эквиваленты стандартных функций PHP, которые блокируют
  воркер или являются CPU-bound непрерываемыми монолитами (sleep, json, hash,
  gzip, хеширование паролей, файловый I/O), с выполнением в расширении; поглощает
  `Sleeper`.
- Fiber-safe мост к Laravel — отдельный пакет, изолирующий состояние
  фреймворка одной джобы от другой, чтобы воркер очереди тянул несколько
  очередей сразу. Сторона брокера сделана, см. [AMQP](docs/amqp.ru.md).
- Авто-восстановление зависших воркеров — watchdog мастера по heartbeat:
  `SIGKILL` и respawn воркера, у которого завис PHP-поток.
- Разнести ядро и фичи по отдельным пакетам.
- Остановка отдельной корутины из любой точки, а не только всего флоу. Вторая
  половина — срок на одну корутину — сделана, см.
  [таймаут корутины](docs/coroutine-timeout.ru.md).
- Оптимизация синхронного пути — вызов вне корутины идёт в расширение напрямую, минуя
  шедулер и машинерию Fiber.
- Попробовать кросс-процессный режим конкурентности, чтобы одновременные
  операции задействовали несколько процессов (и ядер), а не задачи рантайма одного
  процесса.
