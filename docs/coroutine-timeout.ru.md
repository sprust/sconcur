# Таймаут корутины

Работе можно задать срок. По его истечении планировщик разматывает корутину там,
где она стоит, бросая в неё `CoroutineTimeoutException`, а код решает, что это
означает.

```php
use SConcur\Deadline;
use SConcur\Exceptions\CoroutineTimeoutException;

try {
    return Deadline::run(timeoutMs: 1000, callback: fn() => handle($job));
} catch (CoroutineTimeoutException) {
    return null;   // не уложились
}
```

Срок принадлежит той корутине, которая исполняется, поэтому это работает везде,
где работает корутина: внутри члена `WaitGroup`, внутри обработчика сервера,
внутри вложенной группы.

Долгоживущие воркеры задают его сами: `handlerTimeoutMs` у HTTP-, сокет- и
WebSocket-сервера и у [консьюмера очередей AMQP](amqp.ru.md#супервизируемый-консьюмер) —
это тот же срок на корутине, в которой обрабатывается запрос, соединение или сообщение.

Сокращение для «весь колбэк укладывается в секунду» — аргумент у `add()`:

```php
$waitGroup->add(
    function () use ($job) {
        try {
            return handle($job);
        } catch (CoroutineTimeoutException) {
            return null;
        }
    },
    timeoutMs: 1000,
);
```

Под обоими одна механика. `Deadline::run()` ограничивает кусок работы и
композируется; `add(timeoutMs: …)` ограничивает колбэк с первой его строки — то,
что нужно, когда срок назначает вызывающий, а не сам колбэк. Оба понимают `0` как
«срока нет» и отказываются от отрицательного.

## Поймать — значит оставить это при себе

Корутина, поймавшая свой таймаут и вернувшая значение, завершается как любая
другая, и соседи об этом не узнают:

```php
$waitGroup->add(function () {
    try {
        return Deadline::run(timeoutMs: 300, callback: fn() => slow());
    } catch (CoroutineTimeoutException) {
        return 'сдались';
    }
});

$waitGroup->add(fn() => fast());     // срок соседа его не касается

$waitGroup->waitAll();
```

Корутина, выпустившая исключение наружу, проваливает свою группу — а провал группы
разматывает всех остальных её членов, потому что `WaitGroup::iterate()` на выходе
останавливает группу. Так что выпустить таймаут наружу — это решение:

```php
try {
    $waitGroup->waitAll();
} catch (CoroutineTimeoutException $exception) {
    // одна корутина не уложилась и не поймала;
    // остальных остановили вместе с ней
}
```

Оба варианта законны. Ловить внутри — когда одна медленная задача должна стоить
только себя; выпускать — когда группа имеет смысл только целиком.

В корутине, запущенной планировщиком (обработчик запроса сервера), группы нет, и
непойманный таймаут отбрасывается, как и любое другое непойманное там исключение.
Обработчики ловят своё сами.

## Вложенность

Области вкладываются, и побеждает меньший срок:

```php
Deadline::run(timeoutMs: 1000, callback: function () {
    // Просит десять секунд внутри области, у которой есть одна; получает остаток той.
    return Deadline::run(timeoutMs: 10_000, callback: fn() => work());
});
```

Внутренняя область не может выторговать себе больше времени, чем держит внешняя, —
внешний срок это чьё-то обещание. На выходе прежний срок возвращается на место, так
что область, уложившаяся вовремя, оставляет корутину снова неограниченной.

Срок срабатывает один раз. Если внутренняя область просила больше, чем было у внешней,
момент у них общий, и на выходе внешний срок обратно не взводится — иначе второй
`CoroutineTimeoutException` прилетел бы ровно в ту очистку, которую начал первый.

## Исключение

`SConcur\Exceptions\CoroutineTimeoutException` наследует `FlowStoppedException` —
принятый в проекте сигнал намеренной размотки. Отсюда три следствия:

- всё, что уже перебрасывает остановку как есть, продолжает работать без правок —
  исполнитель фич, канал AMQP, рантайм консьюмера;
- `catch (FlowStoppedException)` ловит и таймаут, так что очистка, написанная для
  одного, покрывает и другое;
- до группы он доходит неупакованным, откуда бы ни вылетел — из корутины, которая уже
  чего-то ждала, и из той, которую срезали на самом первом прогоне, до первого ожидания.
  Любое другое непойманное исключение приходит как `CallbackExecutionException` с
  оригиналом внутри; намеренная размотка вместо этого остаётся узнаваемой.

## Когда начинается отсчёт

У `Deadline::run()` — при входе в область. У `add(timeoutMs: …)` — когда колбэк
начинает исполняться, а не в момент `add()`.

Разница видна при ограничении конкурентности. Группа, созданная как
`WaitGroup::create(maxConcurrency: 4)`, держит пятый колбэк в очереди до
освобождения слота; отсчёт от `add()` выдал бы ему срок, уже потраченный на
ожидание своей очереди, и загруженная группа обрывала бы колбэки, не выполнившие ни
строчки.

Ещё против срока корутины, запущенной из другой корутины, играет одно: её первый вызов
передаётся планировщику, а не уходит со стека самого файбера, — и отправляется на
следующем его обороте. Всё, что родитель успеет сделать до своего подвеса, — это время,
которое ребёнку уже засчитано.

## Докуда срок достаёт

Планировщик применяет его там, где и так получает управление:

| Корутина | Что происходит |
| --- | --- |
| ждёт задачу (любой ввод-вывод SConcur, `Sleeper`) | разматывается по сроку, где бы ни ждала |
| припаркована через `Scheduler::switch()` | разматывается до того, как её бы возобновили |
| исполняет PHP, преемпция включена | разматывается хуком преемпции, между двумя опкодами |
| исполняет PHP, преемпции нет | разматывается на ближайшем подвесе |
| внутри вызова через границу | **не** разматывается, пока вызов не вернётся |

Последние две строки — честные пределы.

**Без преемпции** срок кооперативный. Серверы и консьюмер очередей AMQP включают
преемпцию на время своей работы (опция `preemptionQuantumMs`), поэтому там код
обработчика прерываем; CLI-скрипт и библиотечный код должны попросить сами —
`Scheduler::get()->enablePreemption()`, см.
[переключение корутин](coroutine-switching.ru.md). Без неё считающий цикл, который
никогда не ждёт, доработает до конца, и таймаут придёт после.

**Внутри вызова через границу** PHP не исполняется вовсе, поэтому доставить туда нечего.
Запрос, обращение или публикация, которые зависли, ограничиваются собственным
таймаутом своей фичи на стороне расширения — `rpcTimeoutSeconds` и `readTimeoutSeconds` у соединения
AMQP, собственные сроки HTTP-клиента, — а не этим. Срок корутины ограничивает
PHP-корутину, и это не то же самое, что ограничить всё, чего она может ждать.

Вне корутины разматывать нечего, поэтому `Deadline::run()` просто выполняет колбэк
без ограничения — по тому же правилу, которому следует вся остальная библиотека для
кода вне конкурентного контекста.

## Чего он не освобождает

Размотка выполняет `finally` корутины и уничтожает её локальные переменные — этим и
возвращаются транзакция, блокировка, канал. Но размотанная корутина оставляет свои
объекты в цикле ссылок, поэтому освобождение случается тогда, когда до них доберётся
сборщик мусора, а не в момент таймаута. Там, где это важно — доставка AMQP числится
за брокером, пока не закроется её канал, — фича освобождает своё сама; где не важно,
разницы не видно.

## Стоимость

Корутина без срока не стоит ничего: планировщик держит сроки отдельным индексом, и
каждая проверка начинается с того, что индекс пуст.

Корутина со сроком стоит сравнения в каждой точке решения планировщика — сколько бы
корутин срок ни держали: планировщик помнит ближайший из них и обходит индекс только
тогда, когда что-то действительно вышло за срок. Это важно, потому что сервер с
заданным `handlerTimeoutMs` выдаёт срок каждому обрабатываемому запросу, а проверка
идёт на каждом доставленном результате.

Ещё срок укорачивает блокирующее ожидание планировщика до ближайшего из них — именно
это заставляет таймаут сработать в простаивающем процессе, где разбудить цикл было бы
нечему.

## Остановка всей группы

Легко перепутать с предыдущим: `WaitGroup::stop()` разматывает всех членов сразу,
обычным `FlowStoppedException`. Это инструмент для «бросить эту работу», а срок —
для «вот этой одной задаче даётся секунда».
