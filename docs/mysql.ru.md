# MySQL (универсальная SQL-фича)

Асинхронная работа с реляционной БД поверх sqlx. Каждый запрос уходит
в расширение и выполняется в задаче рантайма, пока вызывающая корутина (PHP-файбер,
который планировщик приостанавливает, пока работает расширение) ждёт, поэтому
десятки запросов идут параллельно. Вне `WaitGroup` тот же API работает синхронно.

Фича (модуль расширения со своим PHP API) не зависит от драйвера: ядро
`SConcur\Features\Sql` ничего не знает о конкретной БД, а
`SConcur\Features\Mysql\Connection` — тонкий фасад, задающий драйвер MySQL
(`MethodEnum::Mysql`). [PostgreSQL](pgsql.ru.md) — зеркальный фасад поверх того же
ядра.

## Быстрый старт

```php
$connection = new \SConcur\Features\Mysql\Connection(
    dsn: 'user:pass@tcp(127.0.0.1:3306)/app',
    timeoutMs: 5000,
);

// стриминг строк (крупные выборки не буферизуются целиком)
foreach ($connection->query('SELECT id, name FROM users WHERE age > ?', [18]) as $row) {
    echo $row['name'] . PHP_EOL;
}

// вся выборка сразу
$rows = $connection->fetchAll('SELECT * FROM users WHERE id = ?', [$id]);

// мутация: affectedRows + lastInsertId
$result = $connection->exec('INSERT INTO users (name) VALUES (?)', ['Ann']);
echo $result->lastInsertId;
```

Внутри `WaitGroup::add(...)` те же вызовы идут конкурентно.

## DSN и биндинги

- DSN — в формате Go-драйвера go-sql-driver/mysql:
  `user:pass@tcp(host:port)/dbname`;
  `user:pass@unix(/var/run/mysqld/mysqld.sock)/dbname` подключается через
  unix-сокет. URL вида `mysql://` тоже принимается — тогда его параметры читает
  сам sqlx, и правила ниже к нему не относятся.
- Применяемые параметры: `charset`, `collation`, `time_zone` и `tls`. `tls` принимает
  `false`, `preferred`, `skip-verify` (шифровать без проверки сертификата) или `true`
  (проверять сертификат и имя хоста), а также написания `1`/`t` и `0`/`f` для `true` и
  `false`; именованная TLS-конфигурация здесь аналога не имеет и отклоняется, а не
  молча понижается до нешифрованного соединения.
- Любой другой параметр — системная переменная сессии, ровно как определяет этот
  формат DSN: он выполняется как `SET name=value` на каждом соединении, которое
  открывает пул, — после собственной настройки драйвера, поэтому перебивает её.
  Так задаются `sql_mode`, `transaction_isolation`, `group_concat_max_len` и
  прочие. `character_set_client`, `character_set_results` и `NAMES` вместо этого
  отклоняются — для них есть `charset` и `collation`, о которых драйвер обязан
  знать.
- Значения percent-декодируются, а системная переменная пишется в кавычках, как
  их пишет этот формат: `time_zone=%27%2B00%3A00%27` → `+00:00`,
  `sql_mode=%27TRADITIONAL%27`. В отличие от строки запроса URL, литеральный `+`
  остаётся `+`, а не превращается в пробел.
- Принимаются и ничего не делают, потому что настраивали сам Go-драйвер, а не
  сервер: `parseTime`, `loc`, `timeTruncate`, `interpolateParams`,
  `columnsWithAlias`, `allowNativePasswords`, `allowOldPasswords`,
  `allowCleartextPasswords`, `allowAllFiles`, `allowFallbackToPlaintext`,
  `checkConnLiveness`, `compress`, `connectionAttributes`, `maxAllowedPacket`,
  `rejectReadOnly`, `serverPubKey`, `timeout`, `readTimeout`, `writeTimeout`.
  Дедлайны query и exec задаёт `timeoutMs`, включая подключение.
- `multiStatements` и `clientFoundRows` принимаются со значением `true` и
  отклоняются со значением `false`: драйвер согласует оба безусловно и
  выключить их не может, а `clientFoundRows` определяет, что считает `exec()`, —
  см. [Настройки сессии](#настройки-сессии).
- Плейсхолдеры — `?`. Биндинги — позиционный список; SQL не переписывается, а
  значения доезжают до сервера параметрами prepared statement (целые
  64-битными, дробные — double), что защищает от SQL-инъекций. Запрос без
  биндингов уходит текстом — см.
  [Вложенные транзакции](#вложенные-транзакции).

## Настройки сессии

Драйвер настраивает каждое новое соединение, поэтому сессия здесь не совпадает с
PDO-сессией к тому же серверу:

| Настройка | Что делает драйвер | Как изменить |
|---|---|---|
| `sql_mode` | дописывает `NO_ENGINE_SUBSTITUTION` к тому, что стоит по умолчанию на сервере | параметр `sql_mode` в DSN — он применяется позже и заменяет всё целиком |
| `IGNORE_SPACE` | запрашивается в capabilities рукопожатия, поэтому виден и в `@@sql_mode` (разрешает пробел между именем встроенной функции и `(`) | не с этой стороны |
| совпавшие или изменённые строки | запрашивает `CLIENT_FOUND_ROWS`, поэтому `exec()->affectedRows` считает строки, которые запрос нашёл, а PDO считает те, которые он изменил: `UPDATE`, записавший то же значение, здесь вернёт 1, а там 0 | не с этой стороны |
| несколько операторов | запрашивает `CLIENT_MULTI_STATEMENTS`, поэтому текстовый запрос может нести несколько операторов через `;` — см. [Несколько операторов за один вызов](#несколько-операторов-за-один-вызов) | не с этой стороны |
| `time_zone` | ставится в `+00:00`, поэтому `TIMESTAMP` пишется и читается как UTC | параметр `time_zone` в DSN |
| кодировка | `SET NAMES utf8mb4`, коллация оставлена серверу (`utf8mb4_0900_ai_ci` на MySQL 8) | параметры `charset` и `collation` в DSN |
| TLS | пробуется всегда, когда сервер его предлагает, и опускается, когда нет, — тогда как этот формат DSN по умолчанию не использует TLS вовсе | параметр `tls` в DSN |

`PIPES_AS_CONCAT` намеренно не ставится, хотя sqlx ставит его по умолчанию: с ним `||`
— конкатенация строк вместо OR, как его понимает MySQL, и один и тот же запрос означал
бы здесь одно, а под PDO — другое.

## Транзакции

Транзакция закреплена за одним соединением на всю серию команд:

```php
$transaction = $connection->begin();

try {
    $transaction->exec('UPDATE accounts SET balance = balance - ? WHERE id = ?', [100, $from]);
    $transaction->exec('UPDATE accounts SET balance = balance + ? WHERE id = ?', [100, $to]);
    $transaction->commit();
} catch (\Throwable $exception) {
    $transaction->rollback();

    throw $exception;
}
```

`begin(int $isolationLevel = 0, bool $readOnly = false)` принимает уровень изоляции —
`1` READ UNCOMMITTED, `2` READ COMMITTED, `4` REPEATABLE READ, `6` SERIALIZABLE;
`0` или любое другое значение оставляет уровень сервера по умолчанию — и флаг
только-чтения. MySQL эти четыре уровня отклоняет — см. [Ограничения](#ограничения);
PostgreSQL применяет. У `Transaction` те же `query`/`fetchAll`/`exec`, что у
соединения.

Если транзакцию бросили без `commit()`/`rollback()` (исключение, ранний выход,
остановка `WaitGroup`), расширение откатывает её само: транзакция привязана к
контексту задачи begin, а он отменяется при остановке флоу (группы задач,
которой владеет `WaitGroup` на стороне расширения). На синхронном пути
деструктор `Transaction` дополнительно освобождает удерживаемый флоу. Внутри
одного `WaitGroup` каждая корутина держит свою транзакцию на своём соединении,
поэтому транзакции идут параллельно.

### Вложенные транзакции

Вложенного `begin()` нет. Вложенная транзакция — это savepoint внутри внешней,
ровно то, что выпускает фреймворк при вызове `transaction()` внутри другого
`transaction()`:

```php
$transaction = $connection->begin();

$transaction->exec('INSERT INTO notes (body) VALUES (?)', ['outer']);

$transaction->exec('SAVEPOINT sp1');
$transaction->exec('INSERT INTO notes (body) VALUES (?)', ['inner']);
$transaction->exec('ROLLBACK TO SAVEPOINT sp1');   // уходит только внутренняя строка

$transaction->commit();
```

Savepoint принадлежит соединению, а транзакция держит своё соединение всю свою жизнь,
поэтому конкурентные корутины могут использовать одни и те же имена savepoint'ов, не
сталкиваясь.

MySQL отклоняет часть команд в prepared-протоколе с ошибкой 1295, «This command is
not supported in the prepared statement protocol yet», — в их числе `SAVEPOINT`,
`RELEASE SAVEPOINT`, `ROLLBACK TO SAVEPOINT`, `LOCK TABLES` и `UNLOCK TABLES`.
Поэтому запрос без биндингов уходит текстом, который эти команды принимает; запрос
с биндингами остаётся prepared, так что значения по-прежнему едут параметрами.

### Несколько операторов за один вызов

Текстовый протокол вдобавок выполняет несколько операторов через `;` за один
вызов, тогда как prepared-запрос принимает ровно один. Отсюда два следствия:

- Собирайте такую строку только из значений, которые контролируете. Запрос,
  склеенный из пользовательского ввода и без биндингов, можно заставить нести
  второй оператор, а тот же ввод, переданный биндингом, — нельзя.
- `exec()` выполняет их все и отвечает за пачку: `affectedRows` — их сумма,
  `lastInsertId` — от последнего. `query()` отклоняет второй результирующий
  набор: курсор несёт один список колонок на весь поток, поэтому строки второго
  `SELECT` попали бы в PHP под именами колонок первого. Оператор, не
  возвращающий строк (`INSERT`, `SET`), — не результирующий набор, так что один
  `SELECT` после него обслуживается. Делайте один `SELECT` на запрос, а процедуру,
  возвращающую несколько наборов, вызывайте не отсюда.

### Блокировки таблиц

`LOCK TABLES` — из списка 1295 выше и работает по той же причине, но требует
внимания, которое пул только обостряет.

Он коммитит любую открытую транзакцию — это делает сам MySQL, ещё до того как
клиент что-либо узнал, поэтому драйвер не может его удержать, и PDO ведёт себя так
же. Транзакция, которая берёт блокировку таблицы посреди работы, к этому моменту
уже закоммичена, и следующий `rollback()` не отменяет ничего. Там, где нужна была
атомарность, инструмент — `SELECT … FOR UPDATE` внутри транзакции, а не блокировка
таблиц.

`LOCK TABLES` и `UNLOCK TABLES` вдобавок должны попасть на одно соединение, а пул
выдаёт то, которое свободно. Закрепляет соединение `begin()`: `Transaction` держит
своё соединение даже после того, как блокировка закоммитила транзакцию у него
из-под ног, — поэтому пара попадает вместе при любом размере пула.

**Оставленная блокировка остаётся на соединении в пуле.** Ни `commit()`, ни
`rollback()` блокировку таблицы не снимают, поэтому соединение, вернувшееся в пул
вместе с ней, вешает каждый следующий запрос к этой таблице — пока это соединение
остаётся в пуле, а в вызывающем коде на него уже ничто не указывает. Поэтому
`UNLOCK TABLES` — в `finally`:

```php
$transaction = $connection->begin();   // здесь только ради закрепления соединения

try {
    $transaction->exec('LOCK TABLES notes WRITE');
    // ... доступна только `notes`: любая другая таблица ответит 1100
} finally {
    $transaction->exec('UNLOCK TABLES');
    $transaction->rollback();
}
```

## Параметры соединения

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `dsn` | — | строка подключения драйвера |
| `timeoutMs` | 30000 | дедлайн одного exec; для query — на всю жизнь курсора |
| `maxOpenConns` | 0 → 32 | потолок соединений пула; `0` — это встроенные 32, а не «без лимита» |
| `maxIdleConns` | = `maxOpenConns` | принимается и не применяется: у драйвера нет потолка простаивающих соединений — он держит их до `maxOpenConns` и закрывает то, что простояло 10 минут. При этом входит в ключ пула, так что два значения — два пула |
| `connMaxLifetimeMs` | 0 (без лимита) | сколько соединение можно переиспользовать, прежде чем пул его заменит |

Для query `timeoutMs` покрывает каждый батч `next()` и потребление на стороне PHP,
так что медленный `foreach` по большой выборке может упереться в него посреди
итерации. На `begin()` он не распространяется, как и на жизнь открытой им
транзакции, — она живёт до commit/rollback или остановки флоу. `begin()` ограничен
только 30-секундным пределом пула на получение соединения, включая его открытие
(см. [Пул соединений и конкурентность](#пул-соединений-и-конкурентность)); когда
соединение уже получено, сервер, который не отвечает на `START TRANSACTION`, отсюда
не ограничен. `exec()` внутри транзакции ограничен как обычно, а `query()` на
транзакции — нет.

## Пул соединений и конкурентность

Каждая операция выполняется на соединении из пула, который живёт в
расширении и переиспользуется между задачами и корутинами. Пул общий для всех
`Connection` с одинаковыми драйвером, DSN, `maxOpenConns`, `maxIdleConns` и
`connMaxLifetimeMs`; неиспользуемый пул, к которому не обращались дольше 5 минут,
закрывается, а все пулы закрываются при остановке расширения. Пул стартует пустым,
растёт по требованию и держит простаивающее соединение до 10 минут (таймаут
простоя драйвера), поэтому следующая пачка одновременных запросов не платит за
рукопожатия заново.

В `WaitGroup` каждая autocommit-операция и каждая транзакция берут отдельное
соединение на время выполнения, поэтому `N` корутин открывают до `maxOpenConns`
соединений сразу. Потолок — на процесс: при пуле серверов умножьте его на их
число, прежде чем сравнивать с `max_connections`, иначе сервер ответит `1040 Too
many connections`, — как поделить бюджет на пул воркеров, описано в
[соединениях с базами данных](worker-master.ru.md#соединения-с-базами-данных).
Задавайте `maxOpenConns` под ожидаемый параллелизм:

```php
$connection = new \SConcur\Features\Mysql\Connection(
    dsn: 'user:pass@tcp(127.0.0.1:3306)/app',
    maxOpenConns: 50,
);
```

При насыщенном пуле autocommit-запрос ждёт освобождения соединения: не дольше
`timeoutMs` и не дольше 30 секунд — собственного предела пула на получение
соединения. На пределе пула вызов падает с `TaskErrorException`, сообщение которого
заканчивается на `pool timed out while waiting for an open connection` (внутри
`WaitGroup` оно приходит обёрнутым в `CallbackExecutionException`). Транзакция
держит соединение всю свою жизнь, поэтому при `maxOpenConns` меньше числа корутин
лишние `begin()` ждут и транзакции идут волнами; `begin()`, который ждёт дольше
30 секунд, падает так же. Держите пул не меньше ожидаемого числа одновременных
транзакций.

## Внутреннее устройство

- Реестр пулов (`ext/src/features/sql/pools.rs`) — по `sqlx::MySqlPool`/`PgPool`
  на ключ, с refcount, чтобы используемый пул не вымело; фоновая очистка обходит
  реестр раз в минуту.
- Стриминг SELECT (`rows_state.rs`) — стрим sqlx работает в отдельной задаче и
  передаёт строки через ограниченный канал; `RowsState` читает их и отдаёт
  строки батчами (аргумент `batchSize` у `query()`, по умолчанию 50; `<= 0` —
  один неограниченный батч) с заглядыванием на строку вперёд, чтобы понять, есть ли
  следующий батч. Закрывается при исчерпании, раннем `break` или остановке флоу.
- Транзакции (`transactions.rs`) — `begin` кладёт `TransactionSession` (с
  транзакцией sqlx) в реестр по ключу удерживающей задачи begin и держит эту
  задачу живой (`hasNext`), чтобы соединение пережило серию команд;
  `commit`/`rollback` финализируют сессию идемпотентно: хэндл забирается из
  слота, и второму финализатору делать уже нечего.

## Ограничения

- Типы значений. Целые → `int`, `FLOAT`/`DOUBLE` → `float`,
  `VARCHAR`/`TEXT`/`CHAR`/`ENUM`/`SET` и `BLOB`/`BINARY`/`JSON`/`BIT`/`GEOMETRY`
  → строка, байт в байт, `DECIMAL` → строка (чтобы не терять
  точность), `DATE`/`DATETIME`/`TIMESTAMP` → строка RFC3339 с обрезанными хвостовыми нулями
  в долях секунды (`2026-12-06T14:30:00.25Z`, `DATE` — на полночь UTC), `TIME` →
  `ЧЧ:ММ:СС` с шестизначной дробной частью, если она не нулевая
  (`14:30:00.500000`), и ведущим `-` для отрицательного интервала, `NULL` →
  `null`. `TINYINT(1)` — это `int`, а не `bool`.
- Беззнаковый `BIGINT` больше `PHP_INT_MAX` приходит десятичной строкой, так
  как не помещается в знаковый 64-битный int. Сравнивайте и храните такие
  значения как строки.
- `begin(isolationLevel:)` с любым из этих четырёх уровней на MySQL отклоняется.
  Уровень задаётся отдельным запросом до начала транзакции и на том же
  соединении, а драйвер отдаёт транзакцию, уже владеющую своим соединением из
  пула, — момента между ними нет. Задавайте уровень на сессии
  (`transaction_isolation` в DSN) или на сервере. `begin(readOnly:)` работает: он
  входит в `START TRANSACTION`.
- Курсор внутри транзакции нужно либо дочитать, либо заменить на `fetchAll` до
  следующей команды той же транзакции — иначе соединение занято открытым курсором.
- Действуют общие ограничения библиотеки — см. [README](../README.ru.md).
