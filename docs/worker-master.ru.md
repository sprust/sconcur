# Мастер воркеров

Супервизор, который поднимает и стережёт пул процессов-воркеров с одним скриптом.
Это пара к [`SO_REUSEPORT`](http-server.ru.md): воркеры биндят один порт, ядро
балансирует соединения между ними, и сервер масштабируется на все ядра без
внешнего балансировщика. Реализация — `src/Worker/` плюс универсальный CLI
`bin/sconcur-server`.

Каждый воркер — отдельный процесс, запущенный через `proc_open` (`pcntl_fork`
после загрузки расширения запрещён — Go-рантайм не переживает fork). Сам мастер
расширение не загружает: это чистый супервизор на `pcntl`/`posix` (оба обязательны,
иначе он бросает `MissingPcntlException`).

## Быстрый старт

Вы пишете только воркер-скрипт; мастер берётся готовым из `bin/`.

```php
// worker.php
use Nyholm\Psr7\Factory\Psr17Factory;
use Psr\Http\Message\ResponseInterface;
use Psr\Http\Message\ServerRequestInterface;
use SConcur\Features\HttpServer\HttpServer;

require __DIR__ . '/vendor/autoload.php';

$factory = new Psr17Factory();

// fromArgs() собирает сервер из argv: мастер передаёт сюда ключи блока `server`
// как флаги --key=value и свой pid как --masterPid.
$server = HttpServer::fromArgs(
    argv: $_SERVER['argv'],
    serverRequestFactory: $factory,
    responseFactory: $factory,
);

$server->serve(static fn (ServerRequestInterface $request): ResponseInterface =>
    $factory->createResponse(200)->withBody($factory->createStream('ok')));
```

> **В блоке `server` конфига обязателен `reusePort: true` — иначе 2-й воркер
> получит `EADDRINUSE`.**

```json
{
  "workerScript": "/app/worker.php",
  "workerCount": 8,
  "phpArgs": ["-d", "extension=/app/ext/build/sconcur.so"],
  "runtimeDir": "/run/sconcur",
  "logDir": "/var/log/sconcur",
  "rotateDays": 3,
  "server": {
    "address": "0.0.0.0:8080",
    "reusePort": true,
    "maxRequests": 10000
  }
}
```

```sh
vendor/bin/sconcur-server start --configPath=/app/master.json
```

`start` блокируется в foreground и стережёт пул до `SIGTERM`/`SIGINT`, до удаления
state-файла или пока все воркеры не завершатся так, что перезапускать нечего.

Программный API за CLI — `SConcur\Worker\WorkerMaster`:

```php
new WorkerMaster(
    workerScript: __DIR__ . '/worker.php',
    runtimeDir:   '/run/sconcur',
    logDir:       '/var/log/sconcur',
    workerCount:  0, // 0 = число ядер
    phpArgs:      ['-d', 'extension=' . __DIR__ . '/ext/build/sconcur.so'],
    workerArgs:   ['0.0.0.0:8080'],
)->run();
```

## Команды

Каждая команда принимает единственный флаг — `--configPath`. Один и тот же конфиг
во всех командах гарантирует согласованные `runtimeDir`/`name`, поэтому
`status`/`stop`/`reload` находят lock-, state- и триггер-файлы.

```sh
vendor/bin/sconcur-server start   --configPath=/app/master.json  # поднять пул (foreground)
vendor/bin/sconcur-server status  --configPath=/app/master.json  # running: pid=12345 workers=8
vendor/bin/sconcur-server stop    --configPath=/app/master.json  # удалить state-файл и дождаться выхода
vendor/bin/sconcur-server reload  --configPath=/app/master.json  # перезапустить воркеры по одному
```

Коды возврата: у `start` — собственный код мастера; `status` — `0` (работает) /
`3` (остановлен или протухший state); `stop` — `0` после остановки (или если никто
не работал), `1` по таймауту; `reload` — `0` по завершении, `3` если мастер не
запущен, `1` по таймауту или ошибке.

`reload` — мягкий перезапуск воркеров. Команда создаёт триггер-файл
`<runtimeDir>/<name>.reload`; мастер перезапускает воркеры по одному, посылая
каждому `SIGTERM` (тот заранее выходит из группы `SO_REUSEPORT` и доводит до
конца начатые запросы), ждёт до `shutdownTimeoutMs` (иначе `SIGKILL`) и
поднимает замену. Пока один воркер дорабатывает начатое, остальные держат трафик
— поэтому при N>1 перезапуск проходит без даунтайма, а свежий `php worker.php`
подхватывает новый код с диска. Сам конфиг мастера при этом не перечитывается:
`workerCount` и аргументы на лету не меняются.

## Параметры

Ключи JSON-конфига точно совпадают с параметрами конструктора `MasterConfig`.
Конфиг валидируется строго (ошибка → код выхода `2`): неизвестный ключ верхнего
уровня отвергается (защита от опечаток вроде `wokerCount`), `name` ограничен
набором `[A-Za-z0-9._-]` (это компонент пути и glob ротации), а `rotateDays`,
`shutdownTimeoutMs`, `restartBackoffMs`, `maxRestartBackoffMs` должны быть `>= 0`.

| Ключ | Дефолт | Назначение |
|---|---|---|
| `workerScript` | — (обязателен) | Воркер-скрипт потребителя. |
| `workerCount` | `0` (= число ядер) | Сколько воркеров поднять. |
| `phpBinary` | текущий `PHP_BINARY` | Интерпретатор для воркеров. |
| `phpArgs` | `[]` | Флаги интерпретатора, например `["-d", "extension=…"]`. |
| `workerArgs` | `[]` | Дополнительные сырые флаги `argv` воркера, после `server`. |
| `env` | `{}` | Доп. env воркера, поверх унаследованного. |
| `runtimeDir` | временный каталог | Каталог lock- и state-файлов (локальная ФС). |
| `logDir` | `runtimeDir` | Каталог логов. |
| `name` | `sconcur-server` | Префикс имён лога и state-файла. |
| `rotateDays` | `3` | Сколько дней хранить файлы лога. |
| `logTo` | `file` | `file` \| `stdout` \| `both` (для `docker logs` — `stdout`/`both`). |
| `restartPolicy` | `always` | `always` \| `on-failure` \| `never`. |
| `shutdownTimeoutMs` | `10000` | Сколько ждать завершения воркеров до `SIGKILL`. |
| `restartBackoffMs` | `200` | База экспоненциального backoff в crash-loop. |
| `maxRestartBackoffMs` | `30000` | Потолок backoff. |
| `panelPort` | `0` (выкл.) | Порт встроенной [панели телеметрии](admin-stats.ru.md); нужен вместе с `adminToken`. |
| `adminToken` | пусто (выкл.) | Bearer-токен панели; нужен вместе с `panelPort`. |
| `server` | `{}` | Параметры сервера → разворачиваются в `argv` воркера. |

Блок `server` — чистая переадресация: каждый ключ становится флагом
`--key=value` (булевы → `1`/`0`), позиционных аргументов нет, а нескалярное
значение — ошибка конфига. Мастер не разбирает и не хардкодит имена ключей,
поэтому тот же супервизор подходит любому воркеру, который парсит `--key=value`, а
набор ключей задаёт сам сервер ([HTTP](http-server.ru.md),
[сокет](socket-server.ru.md), [WebSocket](websocket-server.ru.md)). Поверх них
мастер добавляет `--masterPid=<pid>`; как его использовать, решает воркер-скрипт
(обычно — проверка на сироту ниже).

## Политика перезапуска и `maxRequests`

| Политика | Поведение |
|---|---|
| `always` (дефолт) | Перезапуск при любом выходе — штатном и аварийном. |
| `on-failure` | Только при ненулевом коде или смерти по сигналу. |
| `never` | Одноразовый запуск. |

`always` стоит дефолтом не случайно:
[`maxRequests`](http-server.ru.md#остановка-после-n-запросов) завершает воркер
штатно с кодом 0, и поднять замену может только `always`. Вместе с ранним
закрытием листенера и `SO_REUSEPORT` это даёт rolling-рестарт без потери трафика.

Защита от crash-loop: воркер, падающий сразу на старте, получает
экспоненциальный backoff по своему слоту (база `restartBackoffMs`, удвоение на
каждом быстром падении, потолок `maxRestartBackoffMs`). Воркер, проживший дольше
~1 c, считается здоровым, и backoff сбрасывается.

## Самозавершение осиротевших воркеров

Если мастер умирает внезапно (краш, `SIGKILL`, OOM), воркеры иначе продолжали бы
жить и держать порт. Чтобы этого не было, мастер передаёт свой pid флагом
`--masterPid`, и на каждом тике серверного цикла сервер сравнивает с ним
`posix_getppid()`: после смерти мастера ядро меняет родителя, `getppid()`
перестаёт совпадать (устойчиво к переиспользованию PID), и сервер штатно
завершается — доводит до конца уже принятые запросы и выходит, освобождая порт.
Вне мастера флага нет — проверка отключена.

## Зависший воркер

Обработчик, ушедший в нативный блокирующий вызов (`sleep()`, синхронный
PDO/`curl`) или в одиночный монолитный внутренний вызов (огромный `preg_match`,
`json_decode`), замораживает единственный PHP-поток воркера — нативный вызов
вытеснить нечем (userland CPU-цикл — другой случай, см.
[переключение корутин](coroutine-switching.ru.md)). `handlerTimeoutMs` на стороне
Go вернёт клиентам `504`, но сам воркер останется `running` и тихо выпадет из
обслуживания. Ни `maxRequests`, ни проверка на сироту тут не помогут: зависший
воркер не *завершает* запрос, а мастер жив.

Убить такой воркер можно только процессно:

- `reload` или `stop` — мастер шлёт `SIGTERM`, ждёт `shutdownTimeoutMs`, затем
  эскалирует до `SIGKILL`. Нативный `sleep` обычно снимается уже `SIGTERM`
  (сигнал прерывает системный вызов), CPU-цикл — только `SIGKILL`;
- `kill -9 <pid>` вручную → мастер видит смерть по сигналу и при `always`
  поднимает замену.

> Ограничение: «жив, но завис» мастер не детектит — он видит обычный процесс
> `running` и не трогает его до `reload`/`stop`/ручного kill. Автовосстановление
> (watchdog по heartbeat → `SIGKILL` + respawn) — в планах.

## Логирование

Мастер пишет в один дневной файл в `logDir`
(`sconcur-server-2026-06-18.log`); на границе суток открывается новый файл, а
файлы старше `rotateDays` удаляются. Формат строки —
`[Y-m-d H:i:s.uuuuuu] LEVEL [<scope>]: <message> [<context>]`, где `<scope>` — это
`master: <pid>` либо `worker: <pid> #<index>`:

```
[2026-06-18 12:00:00.180210] INFO [worker: 12346 #0]: spawned []
[2026-06-18 12:01:00.012044] ERROR [worker: 12346 #0]: exited code=1 uptime=0.3s; restarting in 200ms []
```

Мастер перехватывает `stdout`/`stderr` воркеров и переписывает их в тот же лог
(stderr → `ERROR`, stdout → `INFO`), поэтому вывод падения и access-лог воркера
сохраняются рядом с записью о выходе. Он также добавляет
`-d display_errors=stderr` в команду каждого воркера (перед `phpArgs`)
принудительно, чтобы собственные ошибки PHP всегда доходили до журнала, даже
если деплойный `php.ini` ставит `display_errors=Off`; более поздний `-d`
побеждает, так что `phpArgs` может это намеренно переопределить.

`logTo` задаёт приёмник: `file` (дефолт), `stdout` (собирается
`docker logs`/journald) или `both` — под `docker logs` нужен один из двух
последних. На производительность это не влияет: записи буферизуются и флашатся
раз в тик супервизии (~100 мс), а не построчно.

## Единственный инстанс и состояние

Единственность обеспечивает `flock`: на старте мастер берёт эксклюзивный
неблокирующий лок на `runtimeDir/<name>.lock`, и второй мастер с теми же
`runtimeDir`+`name` получает `MasterAlreadyRunningException`. Ядро освобождает лок
при смерти процесса (даже по `SIGKILL`), поэтому проблемы протухшего лока нет.

State-файл `runtimeDir/<name>-state.json` хранит pid, время старта, число
воркеров, путь к воркер-скрипту и статус; пишется атомарно, удаляется при штатном
выходе и остаётся после краша. Он же — канал управления: мастер проверяет его на
каждом тике, и удаление файла (логируется на уровне `WARN`) является сигналом
остановки — именно так работает `stop`. Поэтому если чистильщик `/tmp` сотрёт
файл, мастер штатно остановится вместе со всеми воркерами.

Жив ли мастер, `status` и `stop` определяют, пробуя взять тот же `flock`, а не по
pid из state-файла — это устойчиво и к протухшему state, и к переиспользованию
PID. Внешний сторож (cron/таймер) может перезапускать мастера по коду возврата
`status`, а `flock` защищает от гонки двух сторожей:

```sh
vendor/bin/sconcur-server status --configPath=/app/master.json >/dev/null \
  || vendor/bin/sconcur-server start --configPath=/app/master.json
```

Учтите, что такая модель поднимает мастера и после намеренного `stop` — если
нужен намеренный выключатель, используйте отдельный маркер или управляйте через
systemd. Внешний супервизор в принципе тоже подходит; встроенный мастер удобен,
когда нужно поднять пул одной командой, иметь единый graceful, общий лог и
согласованный поочерёдный перезапуск внутри одного дерева процессов, а также
тесную связку с фичами библиотеки (`maxRequests`, страж `masterPid`).

## Graceful shutdown

Триггеры остановки — `SIGTERM`/`SIGINT` либо удаление state-файла. В обоих
случаях мастер перестаёт перезапускать воркеров, пересылает `SIGTERM` всем живым
(каждый доводит до конца свои начатые запросы, см.
[HTTP-сервер](http-server.ru.md#graceful-shutdown)), ждёт их до
`shutdownTimeoutMs`, добивая выживших `SIGKILL`, затем убирает state-файл,
освобождает лок и выходит с кодом `0`.

## Тестирование

Тесты не зависят от docker-сервиса: `SConcur\Tests\Impl\Worker\TestWorkerMaster`
запускает `bin/sconcur-server` отдельным процессом на loopback-порту, воркером
служит общий демо-сервер. Покрытие (`tests/feature/Worker/` +
`tests/feature/Features/HttpServer/`): супервизия (поднятие N воркеров,
перезапуск убитого, самовыход по `maxRequests` → перезапуск, политики
`on-failure` и `never`), остановка (штатное завершение по `SIGTERM` и по удалению
state-файла), единственность и состояние (отказ второму инстансу, `status`/`stop`,
`status` после краша), устойчивость (backoff в crash-loop, валидация конфига,
самозавершение сироты) и логгер (формат строки, JSON контекста, дневная ротация).
