# Нагрузочное тестирование: поведение сервера под нагрузкой

Как долбить HTTP-сервер всеми async-I/O-фичами сразу, снимая при этом память и
CPU, и что показал эталонный прогон.

Инструменты:

- ручка `/all` демо-сервера (`tests/servers/http/http-server.php`) — на каждый
  запрос она гоняет веером (вложенный `WaitGroup`) MongoDB (insert + findOne),
  MySQL (`INSERT` + `SELECT 1`) и PostgreSQL (`INSERT` + `SELECT 1`). HTTP-клиент
  намеренно исключён: его удар в собственный `/` заставлял бы каждый `/all`
  обслуживать второй запрос и искажал бы rps. Соединения создаются лениво, по
  одному разу на воркер;
- ручка `/all-nowg` — те же шесть операций, но последовательно и без
  `WaitGroup`, так что остаётся только конкурентность между запросами. Запуск:
  `ROUTE=/all-nowg tests/benchmarks/http-load-stats.sh`;
- скрипт `tests/benchmarks/http-load-stats.sh` (`make bench-http-load-stats`) —
  поднимает пул серверов (`SO_REUSEPORT`, по процессу на ядро), гоняет `wrk` и во
  время прогона семплит `docker stats` (CPU%/MEM серверного и БД-контейнеров) плюс
  суммарный RSS воркеров из `/proc/<pid>/status` (детект утечек);
- скрипты `rr-load-stats.sh` и `swoole-load-stats.sh` (`make bench-rr-load-stats` /
  `make bench-swoole-load-stats`) — тот же гарнесс против эталонных стеков
  RoadRunner и Swoole на нативных драйверах, с `ROUTE=/all-coro`
  (`make bench-swoole-coro-load-stats`) для собственного веера Swoole.

## Как запускать

Нужен `wrk` на хосте и поднятые сервисы (`make up`). Запускать с хоста; серверы
работают в контейнере, где собрано расширение.

```sh
make bench-http-load-stats
# тюнинг через env:
SERVERS=12 WRK_THREADS=4 CONNECTIONS=256 DURATION=20 SAMPLE_INTERVAL=2 \
    tests/benchmarks/http-load-stats.sh

# базовый прогон по пустой ручке "/":
make bench-http-load-stats-empty

# soak: длинный прогон с трендом RSS и наклоном (MiB/мин) — детект медленной утечки
make bench-http-load-soak               # 10 минут по умолчанию
DURATION=3600 make bench-http-load-soak # часовой прогон
```

`MODE=soak` дополнительно печатает таблицу `trend (elapsed → RSS)` и наклон по
методу наименьших квадратов в MiB/мин с вердиктом: `stable` /
`growth — possible leak` / `declining (GC/memory return)`.

Методология совпадает с `http-throughput.sh`: серверы и генератор нагрузки
закреплены за непересекающимися ядрами (`taskset`), а `wrk` бьёт по bridge-IP
контейнера напрямую, минуя docker-proxy (NAT режет пропускную способность).

## Базовый прогон (пустая ручка)

Ноутбук Intel i7-13620H (16 потоков), сервисы в Docker, 12 серверов / 4 ядра под
wrk, 256 соединений, 20 c. `/` отвечает `ok` без I/O и заметного CPU — это потолок
связки HTTP-сервер + фреймворк, пол, поверх которого ложится налог фич у `/all`.

| Метрика | `/` (пусто) | `/all` (все фичи) |
|---|---|---|
| Пропускная способность | ≈99 900 req/sec | 2 666 req/sec |
| Латентность | p50 2.6 · p90 4.0 · p99 11.5 мс | p50 87 · p90 163 · p99 277 мс |
| CPU серверов (`php`) | avg ~1214 % | avg 754 % |
| RSS воркеров (сумма 12) | ~589 MiB (плоско) | ~650 MiB |

Три прогона держали ~100 тыс. req/sec, 0 ошибок. Разрыв в ~37× — это цена веера по
фичам: на `/all` каждый запрос делает трёхсторонний веер через границу PHP↔Go плюс
fsync трёх дисковых записей, и пропускная способность упирается именно в это, а не
в дешёвое чтение из БД. У пустой ручки ничего этого нет, она упирается в CPU на
~1200 %.

## Эталонный прогон

Те же машина и параметры, `wrk` бьёт по `/all` — трёхсторонний веер по 6
БД-операциям, из них 3 дисковые записи.

| Метрика | Значение |
|---|---|
| Пропускная способность | 2 666 req/sec (0 ошибок — все 3 фичи `ok`) |
| Латентность | p50 87 · p90 163 · p99 277 мс |
| RSS воркеров (сумма 12) | first 642.2 / peak 649.8 / last 649.8 MiB → дрейф +7.6 MiB |
| CPU серверов (`php`) | avg 754 % / peak 784 % (≈ 7–8 из 12 ядер) |
| CPU бэкендов | MongoDB 107 %/144 peak · MySQL 70 %/73 · PostgreSQL 50 %/54 |
| MEM (контейнеры) | php 255 · mongo 174 · mysql 501 · pg 130 MiB |

Дрейф RSS за 20 c — шум прогрева; авторитетный вердикт по утечкам даёт soak ниже.

## Soak-прогон (10 минут)

То же окружение, сустейнутая нагрузка в 128 соединений на 600 c — 1 738 813
запросов (~5.2M операций фич).

| Метрика | Значение |
|---|---|
| Пропускная способность | 2 897 req/sec · p50 40 · p90 72 · p99 127 мс |
| RSS воркеров (тренд за 10 мин) | first 618.5 / peak 621.8 / last 620.6 MiB |
| Дрейф / наклон | +2.1 MiB / +0.11 MiB/мин → вердикт stable |
| CPU серверов (`php`) | avg 741 % / peak 768 % |

RSS оставался плоским (618–622 MiB) на всей дистанции — наклон в пределах шума,
медленной утечки нет. MEM контейнера `mongodb` при этом вырос до ~372 MiB из-за
безлимитных вставок `/all` в коллекцию `load_all`, а RSS воркеров не сдвинулся:
данные копит БД, а не SConcur (коллекцию можно дропнуть после прогонов).

## Fan-out против последовательных вызовов (`/all` против `/all-nowg`)

Те же машина и параметры, дисковые бэкенды, сброс состояния (`make bench-reset`)
между прогонами.

| Метрика | `/all` (веер) | `/all-nowg` (последовательно) |
|---|---|---|
| Пропускная способность | 2 620 req/sec | 2 570 req/sec (−2 %) |
| Латентность | p50 87.6 · p90 174.8 · p99 294.8 мс | p50 90.8 · p90 164.5 · p99 261.2 мс |
| CPU серверов (`php`) | avg 717 % | avg 503 % (−30 %) |
| Дрейф RSS воркеров (20 c) | +3.3 MiB | +0.0 MiB |

Одно соединение (1 сервер / 1 тред wrk / 1 соединение / 5 c):

| Метрика | `/all` (веер) | `/all-nowg` (последовательно) |
|---|---|---|
| Латентность avg | 9.9 мс | 12.2 мс (+23 %) |
| Пропускная способность | 101 req/sec | 82 req/sec |

1. Под насыщением пропускная способность одинакова: потолок задают дисковые
   коммиты бэкендов, и 256 корутин запросов в полёте загружают их без всякого
   внутризапросного веера — фичи, вызванные вне `WaitGroup`, всё равно
   приостанавливают корутину и уступают.
2. Веер покупает латентность запроса — 9.9 против 12.2 мс на одном соединении, где
   три блока фич накладывают свои дисковые коммиты.
3. Последовательные вызовы дешевле по CPU: avg 503 % против 717 % при тех же rps,
   примерно два ядра запаса (нет `WaitGroup` и трёх лишних корутин на запрос).
4. На tmpfs-бэкендах картина переворачивается: операции субмиллисекундные,
   машинерия веера стоит дороже, чем возвращает параллелизм, и последовательный
   путь выигрывает прямо (6 200 против 3 860 req/sec, 0.9 против 1.5 мс на одном
   соединении). Разветвляйте, когда в запросе есть по-настоящему медленный I/O.

## Выводы

1. Память стабильна — главный результат. ~50 MiB RSS на воркер, а 10-минутный
   soak (1.74M запросов) держал RSS плоско при +0.11 MiB/мин (= шум). Для
   долгоживущего сервера это ключевой сигнал: связка Go-рантайм + PHP-файберы +
   пулы соединений + граница PHP↔Go ничего не накапливает. Согласуется с
   `MemLeakTest`.
2. Устойчивость: насыщение трёхсторонним веером на запрос → 0 ошибок, p99
   ≈ 130 мс под длительной soak-нагрузкой.
3. На дисковых бэкендах узкое место — fsync, а не CPU. Серверы берут ~7–8 из 12
   ядер против ~0.5–1.5 на каждой БД — потолок в ~2.7 тыс. rps задают 3 дисковых
   коммита на запрос плюс оверхед фреймворка (msgpack, spawn/планирование
   файберов, 3 пересечения границы PHP↔Go), а не чтения `SELECT 1`/`findOne`.

Оговорки: прогоны синтетические и на ноутбуке (потребительский CPU занижает
масштабирование по ядрам); тривиальные запросы занижают смысл SConcur —
I/O-bound сценарий закрывают отдельные бенчи `bench-http-server-io`; а для
абсолютной уверенности по утечкам в проде нужен многочасовой прогон
(`DURATION=3600 make bench-http-load-soak` и дольше).

## WebSocket-сервер под нагрузкой

Та же связка «нагрузка + ресурсы», но `wrk` умеет только HTTP, поэтому генератор
свой — `ext/cmd/ws-load` (Go, на `coder/websocket`), WS-аналог `wrk`: держит N
постоянных соединений, гоняет по ним round-trip'ы подряд и печатает пропускную
способность и p50/p90/p99.

Команда `all` демо-сервера (`tests/servers/ws/ws-server.php`) гоняет веером те же
backend-фичи на каждое сообщение, плюс `Sleeper`. Скрипт
`tests/benchmarks/ws-load-stats.sh` (`make bench-ws-load-stats`) поднимает пул и
семплит те же метрики, что и `http-load-stats.sh`. Отличие от HTTP-варианта: и
пул, и генератор живут в контейнере `php`, закреплены за непересекающимися ядрами,
а генератор бьёт по пулу через loopback.

```sh
make bench-ws-load-stats
SERVERS=12 CONNECTIONS=256 DURATION=20 SAMPLE_INTERVAL=2 tests/benchmarks/ws-load-stats.sh

make bench-ws-load-stats-empty  # базовый прогон по "ping"
make bench-ws-load-soak         # soak, 10 минут по умолчанию
```

Метрики читаются так же, как у HTTP: `ping` против `all` показывает цену веера по
фичам, а наклон RSS в soak-режиме — авторитетный вердикт по утечкам. WS- и
HTTP-сервера здесь устроены одинаково, поэтому и выводы переносятся.
