# Нагрузочное тестирование: поведение сервера под нагрузкой

Как нагружать HTTP-сервер всеми async-I/O-фичами сразу, снимая при этом память и
CPU, и что показал эталонный прогон.

Инструменты:

- эндпоинт `/all` демо-сервера (`tests/servers/http/http-server.php`) — на
  каждый запрос он выполняет шесть операций одновременно (вложенный
  `WaitGroup`): MongoDB (insert + findOne), MySQL (`INSERT` + `SELECT 1`) и
  PostgreSQL (`INSERT` + `SELECT 1`). HTTP-клиент намеренно исключён: его удар в
  собственный `/` заставлял бы каждый `/all` обслуживать второй запрос и искажал
  бы rps. Соединения создаются лениво, по одному разу на воркер;
- эндпоинт `/all-nowg` — те же шесть операций, но одна за другой и без
  `WaitGroup`, так что остаётся только конкурентность между разными запросами.
  Запуск: `ROUTE=/all-nowg tests/benchmarks/http/load-stats.sh`;
- скрипт `tests/benchmarks/http/load-stats.sh` (`make bench-http-load-stats`) —
  поднимает пул серверов (`SO_REUSEPORT`, по процессу на ядро), гоняет `wrk` и во
  время прогона семплит `docker stats` (CPU%/MEM серверного и БД-контейнеров) плюс
  суммарный RSS воркеров из `/proc/<pid>/status` (детект утечек);
- скрипты `rr-load-stats.sh` и `swoole-load-stats.sh`
  (`make bench-rr-load-stats` / `make bench-swoole-load-stats`) — тот же стенд
  против эталонных стеков RoadRunner и Swoole на нативных драйверах, с
  `ROUTE=/all-coro` (`make bench-swoole-coro-load-stats`) для варианта, где
  Swoole выполняет те же шесть операций одновременно в своих корутинах.

## Как запускать

Нужен `wrk` на хосте и поднятые сервисы (`make up`). Запускать с хоста; серверы
работают в контейнере, где собрано расширение.

```sh
make bench-http-load-stats
# тюнинг через env:
SERVERS=12 WRK_THREADS=4 CONNECTIONS=256 DURATION=20 SAMPLE_INTERVAL=2 \
    tests/benchmarks/http/load-stats.sh

# базовый прогон по пустому эндпоинту "/":
make bench-http-load-stats-empty

# soak: длинный прогон с трендом RSS и наклоном (MiB/мин) — детект медленной утечки
make bench-http-load-soak               # 10 минут по умолчанию
DURATION=3600 make bench-http-load-soak # часовой прогон
```

`MODE=soak` дополнительно печатает таблицу `trend (elapsed → RSS)` и наклон по
методу наименьших квадратов в MiB/мин с вердиктом: `stable` /
`growth — possible leak` / `declining (GC/memory return)`.

Методология совпадает с `http-throughput.sh`: серверы и генератор нагрузки
закреплены за непересекающимися ядрами (`taskset`), а `wrk` бьёт по bridge-IP
контейнера напрямую, минуя docker-proxy (NAT режет пропускную способность).

## Закрепление за ядрами (пиннинг)

Обычно ядро ОС само решает, на каком процессорном ядре выполнять процесс, и может
перекидывать его с одного на другое. Пиннинг — это когда процессу говорят «живи на
этом ядре и никуда не уходи»; в Linux это `taskset`.

Харнесс пиннит ради одного — повторяемости. Иначе двенадцать серверов и `wrk` на
одной машине дерутся за те же ядра, генератор отбирает процессор у того, что
измеряется, и число зависит от того, кому в этот раз повезло. Развести их по
непересекающимся наборам — серверам `0..SERVERS-1`, `wrk` остальные — это и есть
то, что делает прогон сравнимым со следующим.

Со сравнимостью с другими стеками хуже, и таблица режимов ниже объясняет почему:
`rr-load-stats.sh` и `swoole-load-stats.sh` отдают серверу целиком
`taskset -c 0-$((WORKERS-1))` и позволяют планировщику расставлять воркеров
внутри — это режим `group`, — тогда как здесь по умолчанию `1`. Бюджет ядер
одинаковый, размещение — нет, а размещение стоит около двадцати процентов.

Размещение выбирается через `PIN_SERVERS`. Все режимы берут из одного бюджета
(`cpu 0..SERVERS-1`), поэтому различаются только тем, где внутри него сидят
воркеры:

| `PIN_SERVERS` | размещение |
|---|---|
| `1` (по умолчанию) | по одному логическому CPU на воркер — `taskset -c $i` |
| `physical` | по физическому ядру на воркер: вся пара сиблингов, прочитанная из `/sys/devices/system/cpu/cpuN/topology/thread_siblings_list` |
| `group` | пул заперт в бюджете, а размещает воркеров внутри него планировщик |
| `0` | без пиннинга — так, как их запускает мастер воркеров |

```shell
PIN_SERVERS=group ROUTE=/ tests/benchmarks/http/load-stats.sh
```

### Что измерено и почему в библиотеке нет настройки пиннинга

Пустая ручка, 12 воркеров, во всех плечах один и тот же бюджет `cpu0-11`, `wrk` на
12-19, три чередующихся раунда по 20 с:

| размещение | rps по раундам | медиана |
|---|---|---:|
| `1` — по одному логическому CPU | 121 446 / 125 284 / 123 185 | 123 185 |
| `physical` — пара сиблингов на воркер | 123 055 / 120 984 / 115 566 | 120 984 |
| `group` — размещает планировщик | 151 761 / 146 644 / 147 654 | **147 654** |

`physical` от `1` не отличается — диапазоны перекрываются, медиана даже чуть ниже.
`group` обгоняет оба на 19.9%, и его диапазон с ними не пересекается вовсе:
худший его раунд, 146 644, выше их лучшего, 125 284.

То есть разрыв берётся не с детали наивного пиннинга, которую починило бы более
умное размещение. Он берётся с пиннинга как такового. Объяснение, согласующееся с
обоими замерами: у каждого воркера два потока — PHP и поток рантайма, — то есть
двенадцать воркеров дают около двадцати четырёх готовых к исполнению потоков на
двенадцать логических CPU. Статическое размещение не умеет перебалансировать
неровную нагрузку, а планировщик умеет: приколоченный простаивающий воркер не
может одолжить своё ядро занятому соседу.

Поэтому настройки `cpuAffinity` нет. Давать ключ, который на равном бюджете ядер
включает то, что медленнее на двадцать процентов, — это не выбор. Текущее
поведение — `WorkerMaster` не пиннит ничего — и есть измеренный оптимум.

О двух вещах здесь ничего не сказано, потому что они не измерялись: воркер на
физическое ядро без соседа (это другое число воркеров, то есть другой
эксперимент) и машина, отданная одному пулу целиком.

### Подвох, о котором стоит знать

Приколоченный процесс видит только свои ядра:

```
без пиннинга:        nproc → 16
под taskset -c 3:    nproc → 1
```

Расширение выводит из этого числа размер своего рантайма. Под харнессом ему
отвечали «одно» — и оно заводило один поток; в проде, где никто не пиннит,
отвечали «шестнадцать» — и каждый из двенадцати процессов заводил шестнадцать.
Число было правильным в каждом замере и неправильным в каждой эксплуатации, и
увидеть это по самим числам было нечем. Теперь поток один в любом случае, а
поднимает это число `SCONCUR_RUNTIME_THREADS` — для процесса, который хочет
отдать расширению больше одного ядра.

Следствие пошире: все цифры в [бенчмарках](benchmarks.ru.md) сняты с пиннингом, а
прод не пиннит. Для сравнения стеков между собой это правильная методика, но это
не та конфигурация, в которой живёт библиотека, и разница между ними не нулевая.
Сравнивать между собой можно только прогоны с одинаковым `PIN_SERVERS`.

## Базовый прогон (пустой эндпоинт)

Ноутбук Intel i7-13620H (16 потоков), сервисы в Docker, 12 серверов / 4 ядра под
wrk, 256 соединений, 20 c. `/` отвечает `ok` без I/O и заметного CPU — это
потолок связки HTTP-сервер + фреймворк и пол, поверх которого добавляется
стоимость вызовов фич у `/all`.

| Метрика | `/` (пусто) | `/all` (все фичи) |
|---|---|---|
| Пропускная способность | ≈133 500 req/sec | ≈3 010 req/sec |
| Латентность | p50 1.8 · p90 7.1 · p99 30.1 мс | p50 76 · p90 155 · p99 267 мс |
| CPU серверов (`php`) | avg ~1218 % | avg ~563 % |
| RSS воркеров (сумма 12) | ~590 MiB (не растёт) | ~660 MiB |

Три прогона держали ~133 тыс. req/sec, 0 ошибок. Разрыв в ~44× — это цена
вызовов фич: на `/all` каждый запрос пересекает границу PHP↔расширение сразу для трёх
блоков фич и платит fsync трёх дисковых записей. Пропускная способность
упирается именно в это, а не в дешёвое чтение из БД. У пустого эндпоинта ничего
этого нет, он упирается в CPU на ~1200 %.

## Эталонный прогон

Те же машина и параметры, `wrk` бьёт по `/all` — 6 БД-операций одновременно в
трёх блоках фич, из них 3 дисковые записи.

| Метрика | Значение |
|---|---|
| Пропускная способность | ≈3 010 req/sec (0 ошибок — все 3 фичи `ok`) |
| Латентность | p50 76 · p90 155 · p99 267 мс |
| RSS воркеров (сумма 12) | first 652.6 / peak 659.7 / last 659.7 MiB → дрейф +7.0 MiB |
| CPU серверов (`php`) | avg 561 % / peak 582 % (≈ 5–6 из 12 ядер) |
| CPU бэкендов | MongoDB 189 %/222 peak · MySQL 120 %/124 · PostgreSQL 84 %/93 |
| MEM (контейнеры) | php 279 · mongo 178 · mysql 667 · pg 139 MiB |

Дрейф RSS за 20 c — шум прогрева; авторитетный вердикт по утечкам даёт soak ниже.

## Soak-прогон (10 минут)

То же окружение, сустейнутая нагрузка в 128 соединений на 600 c — 1 738 813
запросов (~5.2M операций фич).

| Метрика | Значение |
|---|---|
| Пропускная способность | 2 897 req/sec · p50 40 · p90 72 · p99 127 мс |
| RSS воркеров (тренд за 10 мин) | first 618.5 / peak 621.8 / last 620.6 MiB |
| Дрейф / наклон | +2.1 MiB / +0.11 MiB/мин → вердикт stable |
| CPU серверов (`php`) | avg 741 % / peak 768 % |

RSS не рос (618–622 MiB) на всей дистанции — наклон в пределах шума, медленной
утечки нет. MEM контейнера `mongodb` при этом вырос до ~372 MiB из-за
безлимитных вставок `/all` в коллекцию `load_all`, а RSS воркеров не сдвинулся:
данные копит БД, а не SConcur (коллекцию можно удалить после прогонов).

## Параллельно против последовательно (`/all` против `/all-nowg`)

Те же машина и параметры, дисковые бэкенды, сброс состояния (`make bench-reset`)
между прогонами.

| Метрика | `/all` (одновременно) | `/all-nowg` (последовательно) |
|---|---|---|
| Пропускная способность | 2 620 req/sec | 2 570 req/sec (−2 %) |
| Латентность | p50 87.6 · p90 174.8 · p99 294.8 мс | p50 90.8 · p90 164.5 · p99 261.2 мс |
| CPU серверов (`php`) | avg 717 % | avg 503 % (−30 %) |
| Дрейф RSS воркеров (20 c) | +3.3 MiB | +0.0 MiB |

Одно соединение (1 сервер / 1 тред wrk / 1 соединение / 5 c):

| Метрика | `/all` (одновременно) | `/all-nowg` (последовательно) |
|---|---|---|
| Латентность avg | 9.9 мс | 12.2 мс (+23 %) |
| Пропускная способность | 101 req/sec | 82 req/sec |

1. Под насыщением пропускная способность одинакова: потолок задают дисковые
   коммиты бэкендов, и 256 одновременно обслуживаемых корутин-запросов загружают
   их даже без одновременного выполнения вызовов внутри одного запроса — фича,
   вызванная вне `WaitGroup`, всё равно приостанавливает свою корутину, и
   процесс в это время обслуживает другие запросы.
2. Одновременное выполнение выигрывает в латентности запроса — 9.9 против
   12.2 мс на одном соединении, где три блока фич ждут свои дисковые коммиты
   параллельно.
3. Последовательные вызовы дешевле по CPU: avg 503 % против 717 % при тех же rps,
   примерно два ядра запаса (нет `WaitGroup` и трёх лишних корутин на запрос).
4. На tmpfs-бэкендах картина переворачивается: операции субмиллисекундные,
   координация стоит дороже, чем возвращает параллелизм, и последовательный
   эндпоинт выигрывает прямо (6 200 против 3 860 req/sec, 0.9 против 1.5 мс на
   одном соединении). Выполняйте вызовы одного запроса одновременно, когда в нём
   есть по-настоящему медленный I/O.

## Выводы

1. Память стабильна — главный результат. ~50 MiB RSS на воркер, а 10-минутный
   soak (1.74M запросов) держал RSS без роста при +0.11 MiB/мин (= шум). Для
   долгоживущего сервера это ключевой сигнал: связка рантайм расширения + PHP-файберы +
   пулы соединений + граница PHP↔расширение ничего не накапливает. Согласуется с
   `MemLeakTest`.
2. Устойчивость: насыщение тремя одновременными блоками фич на запрос → 0
   ошибок, p99 ≈ 130 мс под длительной soak-нагрузкой.
3. На дисковых бэкендах узкое место — fsync, а не CPU. Серверы берут ~7–8 из 12
   ядер против ~0.5–1.5 на каждой БД — потолок в ~2.7 тыс. rps задают 3 дисковых
   коммита на запрос плюс накладные расходы фреймворка (msgpack, создание и
   планирование файберов, 3 пересечения границы PHP↔расширение), а не чтения
   `SELECT 1`/`findOne`.

Оговорки: прогоны синтетические и на ноутбуке (потребительский CPU занижает
масштабирование по ядрам); тривиальные запросы занижают смысл SConcur —
I/O-bound сценарий закрывают отдельные бенчи `bench-http-server-io`; а для
абсолютной уверенности по утечкам в проде нужен многочасовой прогон
(`DURATION=3600 make bench-http-load-soak` и дольше).

## WebSocket-сервер под нагрузкой

Та же связка «нагрузка + ресурсы», но `wrk` умеет только HTTP, поэтому генератор
свой — `tests/benchmarks/ws/ws-load/`: держит N постоянных соединений, гоняет по
ним round-trip'ы подряд и печатает пропускную способность с p50/p90/p99. Харнесс
собирает его перед прогоном.

Это отдельный крейт, не часть ядра, и намеренно: ядро собирается с fat LTO на
каждый `make ext-build`, и бенчмарочному инструменту незачем это замедлять.
Задержки складываются в фиксированную гистограмму (0.1 мс на корзину), а не в
список замеров: на сотнях тысяч round-trip'ов список был бы самой большой
аллокацией в генераторе, а перцентилю он не нужен.

Команда `all` демо-сервера (`tests/servers/ws/ws-server.php`) выполняет те же
backend-фичи одновременно на каждое сообщение, плюс `Sleeper`. Скрипт
`tests/benchmarks/ws/load-stats.sh` (`make bench-ws-load-stats`) поднимает пул и
семплит те же метрики, что и `http-load-stats.sh`. Отличие от HTTP-варианта: и
пул, и генератор живут в контейнере `php`, закреплены за непересекающимися
ядрами, а генератор бьёт по пулу через loopback.

```sh
make bench-ws-load-stats
SERVERS=12 CONNECTIONS=256 DURATION=20 SAMPLE_INTERVAL=2 tests/benchmarks/ws/load-stats.sh

make bench-ws-load-stats-empty  # базовый прогон по "ping"
make bench-ws-load-soak         # soak, 10 минут по умолчанию
```

Метрики читаются так же, как у HTTP: `ping` против `all` показывает цену вызовов
фич, а наклон RSS в soak-режиме — авторитетный вердикт по утечкам. WS- и
HTTP-сервера здесь устроены одинаково, поэтому и выводы переносятся.
